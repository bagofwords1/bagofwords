Running shared dashboards under the viewer's own identity

A shared dashboard used to show everyone the creator's data snapshot. It now offers a per-viewer Run — each viewer re-executes the queries under their own data-source credentials, sees only their own rows, and never touches what the owner or anyone else sees. Verified end-to-end against a real Postgres with row-level security, across multiple users and a group.

What shipped

  • Per-viewer runs. A signed-in viewer of a shared dashboard clicks Run; the saved query code re-executes and the result is stored in a per-(step, user) row (step_user_results). The shared snapshot the owner and other viewers see is never modified.
  • Whose credentials. A "Run on my behalf" toggle in the share dialog sets shared_run_identity = viewer (each viewer's own credentials) or creator (on behalf of the owner). Creator-mode runs are refused for signed-in strangers outside the report's org.
  • Strict mode withholds the snapshot. When a dashboard runs on user-scoped credentials, non-owners never receive the creator snapshot — they get a "run with your credentials" prompt until they run as themselves.
  • Row-level security honored. Because each viewer queries under their own database login, the warehouse's RLS decides what they see — the same dashboard renders different rows per person.

Data-leak surfaces found & closed

Hardening the feature surfaced several ways the creator's snapshot could still reach a viewer. All are now gated through one policy (viewer_data_policy.resolve_step_data); two were pre-existing bugs independent of this feature.

End-to-end verification

The full stack (FastAPI + Nuxt) was booted against a real PostgreSQL 16 with a row-level-security policy USING (sales_rep = current_user) and three database logins — alice, bob, carol — each seeing a different set of rows. In the app: an owner, three org members mapped to those logins, and an Analysts group, sharing one user-scoped dashboard. A Playwright driver exercised every path:

The proof: one dashboard, three identities

The same shared dashboard, opened by three different members. Row-level security in Postgres returns a different result set to each — because each is querying under their own stored credentials.

Test coverage

  • 12 dedicated e2e tests in test_viewer_run_shared_artifacts.py: per-viewer isolation, visibility gating (401 / 403 / 404), identity persistence, cross-org refusal, snapshot withholding, export authorization, fork-copy & no-mutation, thumbnail drop.
  • Regression suites green after merging main (442 commits): report rerun, sharing, RBAC admin-view, step export, and fork.
  • Migration chain unified — a merge migration resolves the two Alembic heads; upgrade head applies cleanly.

Accepted residuals

Three items are deliberately out of scope and don't affect the strict-mode guarantee: Slack step notifications (owner → owner's own channel); the unauthenticated /thumbnails route for ordinary private reports (a separate pre-existing concern — strict dashboards now have no thumbnail at all); and AI-written artifact prose that may embed creator-derived values at generation time, which can't be scrubbed mechanically and is a product decision.
