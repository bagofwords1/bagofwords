# Glassbox vendor Artifactory (glassbox.jfrog.io) — exhaustive SDK mining for server-side surface and data model

Research date: 2026-11-17. Method: anonymous HTTP GET only against `https://glassbox.jfrog.io/artifactory/` (repository list API, per-folder HTML listings crawled recursively for all 15 repos = 5,973 files, then download of the latest artifacts). Artifacts were unpacked and inspected with `unzip`/`tar`/`strings`/`grep` plus a read-only Java constant-pool string extractor; nothing was executed, built or installed, and all downloads were deleted afterwards. No tenant or R&D hostname found in the artifacts was contacted.

Legend: **[V]** = read directly from the named artifact/file on 2026-11-17; **[I]** = inference. "String constant" means a literal recovered from compiled code: the literal is verified, but how the code fills its `%s`/`%@` placeholders is inferred from neighbouring literals unless stated.

## What exactly is in each of the 15 repos? Any docs, PDFs, OpenAPI, Postman, server tools or CLIs besides SDK binaries?

### Takeaway
The Artifactory holds **only client-side deliverables**: SDK binaries, hybrid-framework plugins with bundled example apps, three macOS source-instrumentation CLIs, one CI Docker image and two sample apps. There is **no PDF, OpenAPI/Swagger file, Postman collection, server tool, API client or admin CLI** anywhere in the 5,973 files; the only documentation is a handful of Markdown READMEs inside the npm/pub packages.

## Every distinct URL / host / path pattern found in the artifacts (with file of origin)

### Takeaway
All SDK traffic goes to one customer-specific **report URL** under a `/thickclient/` path family (mobile) or the `reportURI` (web): `…/thickclient/report/<appId>`, `…/thickclient/configuration/<appId>`, `…/thickclient/key/<appId>`, and (VoC) `…/glassvox/configuration/…`. The only **console-side** paths in the code are session-replay deep links: `https://<console>/webinterface/webui/#/sessions/<query>/replay?…` and a short form `https://<console>/s/…`. No `/api/`, `/rest/`, `Authorization`, bearer-token or API-key string exists in any SDK binary.

### Inferences
- **[I]** The mobile replay link is `<integrations[crashlytics].domain>/integration_id:<integrationId>/replay?timeframe=month_1`, i.e. `https://<console-host>[:8443]/webinterface/webui/#/sessions/integration_id:<id>/replay?timeframe=month_1`. The binding of the first placeholder to `domain` is inferred from adjacent literals and the sample config, not from decompiled control flow.
- **[I]** The console's session search accepts a `field:value` query language with `AND` (`cls_s:<sessionId> AND <attr>:<value>`), searchable keys including `cls_s` (web session id) and `integration_id` (mobile), with either an absolute window (`from`/`till` epoch ms; the SDK uses now ± 79,200,000 ms = 22 h) or a relative one (`timeframe=month_1`). - **[I]** `cuid` (8-char tenant code in the URL path) + `appId` (GUID) is the tenant/app addressing scheme on multi-tenant SaaS; single-tenant/on-prem URLs omit the cuid segment.

## What does the remote-configuration fetch look like, and does it reveal console/API hostnames or tenant structure?

### Takeaway
Mobile SDKs fetch config with an HTTP GET to **`<reportUrl>/[<cuid>/]thickclient/configuration/<appId>`** (or to an override `applicationConfigUrl`), authenticated only by app identity headers and cookies — there is no secret. A sibling **`/thickclient/key/<appId>`** returns an RSA public key for field encryption. The config response is a flat JSON document of capture settings; its only server-side pointer is `integrations[].domain` (the console sessions URL) and `customerId`.

### Inferences
- **[I]** Likely server-side entities a read connector should expect (names as the SDK emits them): **session** (`sessionId`/`_cls_s`, `integrationId`, `deviceId`, visitor `_cls_v`, app `appId`, device/app attributes, `userDefinedProperties`), **page/screen view** (`applicationPage` on mobile, `pageName`/segment/title on web, with render/dwell metrics), **interaction event** (action type + `visualName`/`selector`/`accLabel` + coordinates), **struggle** (type + target), **error/crash/ANR**, **network call** (URL, status, duration, optional masked payload), **custom event** (name + flat parameters; timed events add `gb_*` keys), **third-party/data-layer attribute**, **survey response**, **accessibility issue**. This is a derived list; Glassbox's server-side field names (e.g. report columns) may differ.
- **[I]** Mobile and web use different wire encodings (JSON vs. coded beacons) and different id formats (mobile `sessionId` UUID-style; web `_cls_s` cookie), so a connector should not assume one id format; hybrid apps link the two via `gbSessionId`/`mobileHybridId`.
- **[I]** Struggle-type values differ in case between platforms (`RAGE_CLICK` vs `rageClick`); normalising them in the connector would help downstream users.

### Gaps
- Exact JSON nesting of a mobile event and the wire format of a web beacon were not reconstructed (no decompilation, no live traffic); the lists above are key vocabularies, not schemas.
- Server-computed metrics (e.g. frustration scores, funnels, journey maps) are not visible in client code.
