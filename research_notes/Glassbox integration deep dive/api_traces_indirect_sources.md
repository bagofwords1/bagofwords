# Glassbox server-side / reporting / export API: traces in indirect public sources

Research date: 2026-11-17. Scope: Glassbox (glassbox.com, formerly Clarisite) digital experience analytics. Passive public sources only; no Glassbox or customer tenant host was contacted.

**Headline:** Still no public endpoint path, auth header, request/response sample or export format for any Glassbox *read* API. This pass found (a) a second, previously unrecorded console deep-link format, (b) the browser-side `_detector` JavaScript API and the `cls_report` ingest parameter names, (c) the backend storage stack from job postings (OpenSearch, ClickHouse, Kafka, Cassandra; search-snippet level), (d) one vendor case study confirming real-time streaming to a customer data lake, and (e) fuller snippets of the Splunk Community thread. Everything else is a recorded negative.

Evidence labels: **[FULL]** = primary file/page read in full (or the relevant section read directly); **[SNIPPET]** = seen only in search-result summaries, wording may be paraphrased by the search tool; **[NEG]** = searched, nothing found.

Access limits in this environment (affect what "not found" means):
- `web.archive.org` (CDX API and Wayback pages) is blocked: curl returned "Blocked by egress policy" and the fetch tool refused the domain. **No archive research was possible.**
- HTTP 403 (bot wall) on: Splunk Community thread, Blue Triangle/Aternity help article, Dynamic Yield "Glassbox Connector" article, patents.justia.com, jobleads, huntukvisasponsors.
- HTTP 404 on every `glassbox.com/careers/<id>/...` job URL returned by search (postings removed).
- `discover.glassbox.com` (Marketo PDF host) returned proxy 502. Adobe Exchange and YouTube pages are JavaScript-rendered and returned no body text.
- GitHub: only the search API was usable; file contents were read through `raw.githubusercontent.com`.

## 1. GitHub code search: what endpoints, components or storage engines appear?

### Takeaway
About 34 code-search queries produced no server-side API call, no on-prem deployment manifest and no component names. The useful finds are client-side: a second console replay-link format built from the web session id, the `_detector` browser API, and the ingest (`cls_report`) parameter names. The only code that reads data out of Glassbox remains a Selenium scraper of the console UI.

### Inferences
- Two console deep-link forms now exist in public code: by internal session id (`/webinterface/webui/sessions/<32-hex>/replay/mobile?sessionStartTime=<ms>&source_node=0`, from the earlier notes) and by web cookie id with a time window (`/webinterface/webui/#/sessions/cls_s:<id>/replay?from=<ms>&till=<ms>`). The `cls_s:` prefix looks like a search-key syntax ("find the session whose `_cls_s` equals X within this window"), which suggests the console's session search accepts field-prefixed keys. That is an inference from one URL.
- A connector can construct replay links from either identifier without any API, which is exactly what every partner integration does.
- The console exposes at least three per-session data panels (GIA insights, Expert View client events, Server View requests with status and timing), so the underlying web application must serve that data over internal HTTP calls under `/webinterface/`; none of those calls is visible in public code.

### Gaps
- No Terraform, Helm, Kubernetes, Docker Compose or runbook for on-prem Glassbox was found; component and service names (the suggested "clingine", "cls", "glassbox-" containers) are unconfirmed.
- No customer wiki or runbook page naming an API path was found.
- GitHub issues/commits search was not run separately (budget); code search covered the same terms.
