# PBIRS embedded Analysis Services: XMLA / live-DAX access to the semantic model of a published .pbix

Scope: on-premises Power BI Report Server (PBIRS) only. Where a capability is Power BI Service / Fabric cloud-only, it is flagged as such. "Official" = learn.microsoft.com or Microsoft-employee statement; "community" = forum/blog. Note: the Fabric/Power BI community forum (community.fabric.microsoft.com) sits behind a Cloudflare challenge and returned HTTP 403 to every direct fetch attempt; quotes from those threads below are taken from search-engine snippets of the threads, not from the full page, and are marked "(snippet)".

## Key Question 1: Is the embedded SSAS instance in PBIRS reachable over TCP? Which port, fixed or dynamic, localhost-only, and is it supported?

### Takeaway
PBIRS runs a private, embedded Analysis Services Tabular process (msmdsrv.exe) from `<install>\PBIRS\ASEngine\workspaces`, on a fixed port that Microsoft itself documents as `localhost:5132`; Microsoft officially documents connecting to it only for SQL Server Profiler tracing, and `Port` and `PrivateProcess` are reset by PBIRS at every engine launch, so the instance is in practice loopback/local-only. Community answers (including Microsoft-affiliated posters) say you cannot connect from other machines and cannot deploy custom models to it; any direct use beyond Profiler diagnostics is an unsupported hack.

### Inferences
- Port 5132 is effectively fixed (Microsoft hard-codes it in the Profiler instructions and lists `Port` as a setting PBIRS rewrites on every launch), unlike Power BI Desktop's per-session random port. This means the Desktop-style "%LOCALAPPDATA%\...\msmdsrv.port.txt" discovery is unnecessary for PBIRS; the port is simply 5132 (verify per server with netstat against the msmdsrv.exe PID, as the community suggests).
- `PrivateProcess` being among the forced settings is the mechanism that makes the instance "hidden"/private (SSAS `PrivateProcess` is the setting that Power BI Desktop and Excel Power Pivot also use for embedded engines); together with the "cannot connect from other machines" statements, the strong inference is that the listener is bound for local use only and remote TCP access is neither designed nor supported. I found no source demonstrating a successful remote (non-localhost) TCP connection to port 5132.
- Because Microsoft documents only a Profiler trace against localhost:5132, any SSMS/DAX Studio/ADOMD query use of that endpoint is a by-product of it being a standard SSAS Tabular listener, not a supported interface. Microsoft's stated support position (external tools unsupported with PBIRS; "cannot deploy custom models") makes this an unsupported hack even when it technically works locally.

### Gaps
- No source explicitly states whether msmdsrv.exe binds to 127.0.0.1 only vs 0.0.0.0 with firewall/auth restrictions; "remote connections are not allowed by default" (community snippet) is the closest statement. Direct netstat evidence would be needed.
- The full text of the key community threads could not be retrieved (Cloudflare 403); exact author names/dates for the snippets are therefore not recorded.
- No source describes what authorization model applies to a local connection (whether only the PBIRS service account/local admins are SSAS server administrators on the instance).

## Key Question 2: Can msmdpump.dll (HTTP XMLA pump) be configured against the PBIRS-embedded Analysis Services instance?

### Takeaway
Nothing official or community-published describes putting msmdpump.dll in front of the PBIRS embedded engine; Microsoft documents msmdpump only for standalone SQL Server Analysis Services (explicitly not for Fabric/Power BI), and I found zero blog posts or forum threads of anyone attempting it against PBIRS. Technically msmdpump is a generic TCP-to-HTTP redirector whose target is a `<ServerName>host:port</ServerName>` entry, so pointing it at `localhost:5132` on the PBIRS box is conceivable but entirely undocumented and unsupported.

### Cited Findings
- Official scope line on the msmdpump page: "Applies to: [yes] SQL Server Analysis Services [no] Azure Analysis Services [no] Fabric/Power BI Premium" — [Microsoft Learn: Configure HTTP Access to Analysis Services on IIS 8.0](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)
- Official: "MSMDPUMP is an ISAPI extension that loads into IIS and provides redirection to a local or remote Analysis Services instance. ... On IIS, MSMDPUMP connects to Analysis Services using the Analysis Services OLE DB provider over TCP/IP." — [Microsoft Learn: msmdpump](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)
- Official: "You can configure HTTP access for any supported version or edition of Analysis Services, running either tabular mode or multidimensional mode. Local cubes are an exception." — [Microsoft Learn: msmdpump](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)
- Official (target is just a host:port string): "If you configured a named or default instance of Analysis Services to listen on a fixed port, you must add the port number to the server name (for example, <ServerName>AW-SRV01:55555</ServerName>)". Files to copy: "MSMDPUMP.DLL, MSMDPUMP.INI, and a Resources folder" from `<drive>:\Program Files\Microsoft SQL Server\<instance>\OLAP\bin\isapi`. — [Microsoft Learn: msmdpump](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)
- Official (2025 change relevant to any new pump deployment): "Starting with SQL Server Analysis Services 2025, HTTP connections through msmdpump.dll will be disabled by default." Error text: "Connections to SQL Server Analysis Services through msmdpump.dll must use secure channels, for example HTTPS." Override: `<RequireSecureChannel>false</RequireSecureChannel>` in msmdpump.ini (test environments only). — [Microsoft Learn: msmdpump](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)
- Official (connection string shape for the pump): "`Data Source=https://<servername>/olap/msmdpump.dll; Initial Catalog=AdventureWorksDW2012; Integrated Security=Basic; User ID=XXXX; Password=XXXXX;`" — [Microsoft Learn: msmdpump](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)
- A web search for the exact phrase pair "Power BI Report Server" + "msmdpump" returned only generic PBIRS doc pages and one thread about msmdpump in front of SSAS 2016 Multidimensional feeding Power BI Desktop (unrelated to PBIRS's embedded engine). — [Fabric Community: Using HTTP data pump msmdpump.dll leads to can't display visual](https://community.fabric.microsoft.com/t5/Desktop/Using-HTTP-data-pump-msmdpump-dll-leads-to-can-t-display-visual/m-p/2383733)

### Inferences
- Because PBIRS ships only the engine (`PBIRS\ASEngine`) and the msmdpump binaries come from a SQL Server Analysis Services install (`...\OLAP\bin\isapi`), a pump setup would require a separate SSAS installation (or copy of its isapi folder) plus IIS on the PBIRS host, with `<ServerName>localhost:5132</ServerName>`. Even if it worked, the PBIRS engine's `PrivateProcess` mode, GUID database names that change on reload, on-demand loading/eviction (see Q4), and Microsoft's "cannot connect from other machines" position make it an unsupported configuration that could break on every PBIRS upgrade (msmdsrv.ini resets on upgrade).
- Microsoft's non-support of the pump for "Fabric/Power BI Premium" is about the cloud; it says nothing either way about PBIRS, which is simply absent from all pump documentation.

### Gaps
- No evidence (positive or negative) of anyone actually running msmdpump against localhost:5132 on a PBIRS server. Whether the embedded engine would accept connections from the IIS app-pool identity, and whether GUID catalogs are browsable through the pump, is untested in any source found.

## Key Question 4: Are pbix databases loaded on demand and unloaded after inactivity? What settings govern this, and would an external DAX query trigger a load?

### Takeaway
Yes: the model is streamed from the report-server catalog into the embedded engine when a report is viewed or refreshed (ExecutionLog `ASModelStream`), and evicted after `ModelExpirationMinutes` (default 60) of non-use, checked every `ModelCleanupCycleMinutes` (default 15); both are SSMS server properties of the report server (not SSAS properties). Because loading is driven by RSPowerBI/the report server (TOM "streaming model to Analysis Server"), not by the engine, an external DAX query to localhost:5132 cannot cause a load — if the GUID database is not currently loaded, there is nothing to query.

### Cited Findings
- Official (settings): "ModelCleanupCycleMinutes — Defines how often the model is checked to evict it from memory. Default is 15 minutes." "ModelExpirationMinutes — Defines how long until the model expires based on the last time used and is evicted. Default is 60 minutes." "ScheduleRefreshTimeoutMinutes — Defines how long the data refresh can take for a mode. Default is 120 minutes. There's no upper limit." "MaxFileSizeMb — Maximum file size for uploaded reports. Default is 1,000 MB (1 GB). Maximum value is 2000 MB (2 GB)." These are "Settings within SSMS" and "apply to all report servers within a scale-out deployment." — [Microsoft Learn: Troubleshoot scheduled refresh in Power BI Report Server](https://learn.microsoft.com/en-us/power-bi/report-server/scheduled-refresh-troubleshoot)

### Inferences
- The engine is a cache: the authoritative copy of each model is the .pbix in the ReportServer catalog DB; RSPowerBI streams it into msmdsrv on first view/refresh (ASModelStream), and the report server (not SSAS) evicts it on its own timer. An external XMLA client therefore sees a transient, GUID-named database that may vanish at the next cleanup cycle, and can see no database at all for reports nobody has opened in the last ~60 minutes. Only a report render (or scheduled refresh) triggers a load; a DAX query from DAX Studio/SSMS cannot.
- Raising ModelExpirationMinutes to a very large value (community workaround) keeps models resident and would make an unsupported localhost:5132 query path more predictable, at the cost of memory; it does not survive reboot.
- GUID naming is the standard Power BI engine behaviour (documented for Desktop) and PBIRS refresh logs refer to `RefreshDatabase(String databaseName, ...)`; the mapping GUID -> report is not surfaced anywhere official, so an external client cannot reliably pick the right catalog by name.

### Gaps
- No official statement of exactly how the GUID database name is derived in PBIRS, whether it is stable across reloads of the same report, or whether it is stored in the catalog (e.g. in `dbo.DataModelDataSource`/`Catalog`). Community threads hint at the metadata tables but the full text was not retrievable.
- Whether multiple models share one msmdsrv process or whether PBIRS ever spawns more than one engine process is not stated in official docs.

## Key Question 5: What does Microsoft officially say about querying PBIRS models programmatically (XMLA endpoint, DAX query API, Ideas)?

### Takeaway
Microsoft has published nothing that presents the PBIRS embedded engine as a queryable endpoint: the PBIRS REST API has no DAX/XMLA/ExecuteQueries equivalent, PBIRS cannot even consume its own PBIX datasets as a data source, and both the XMLA endpoint and the ExecuteQueries REST API are Power BI Service/Fabric (Premium/PPU) cloud-only. The consistent official guidance for anything needing a reusable, queryable on-prem model is "host it in SQL Server Analysis Services and use a live connection."

## Key Question 6: Does PBIRS support Power BI reports with live connection to SSAS, and how does that change the picture?

### Takeaway
Yes — PBIRS officially supports Power BI reports with a live connection to SQL Server Analysis Services (and Azure AS), and this is the sanctioned way to get a model that external tools can query over XMLA: the model lives in a standalone SSAS instance (default TCP 2383, named instances via SQL Browser, optional msmdpump HTTP), fully supported for SSMS/DAX Studio/Tabular Editor/ALM Toolkit, with Kerberos constrained delegation required for "as the user viewing the report" in distributed deployments.

### Cited Findings
- Official: "Data can be imported or data can be queried directly using DirectQuery, or a live connection to SQL Server Analysis Services." Table rows: "SQL Server Analysis Services — ✅ ✅ ✅" and "Azure Analysis Services database — ✅ ❌ ✅" (cached / scheduled refresh / live-DirectQuery). — [Microsoft Learn: Power BI report data sources in Power BI Report Server](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)
- Official (authoring): "Select your data source -- in this example, Analysis Services. ... Fill in Server, and optionally, Database. Make sure Connect live is selected > OK." — [Microsoft Learn: Create a Power BI report for Power BI Report Server](https://learn.microsoft.com/en-us/power-bi/report-server/quickstart-create-powerbi-report)
- Official (scheduled refresh does not apply): "Your report contains one or more Analysis Services data sources, which use a live connection." is listed under reports for which you can't create a scheduled refresh plan. — [Microsoft Learn: scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/scheduled-refresh)
- Official (Kerberos): "Power BI Report Server can host Power BI reports that connect to data sources like SQL Server Analysis Services. ... when you install these services on separate machines (a distributed environment), you need Kerberos authentication. Specifically, you need to configure Kerberos constrained delegation." Error without it: "We couldn't connect to the Analysis Services server. The server forcibly closed the connection. To connect as the user viewing the report, your organization must have configured Kerberos constrained delegation." SPNs: report server `HTTP/<host>`; SSAS `MSOLAPSvc.3/<host>` (named instance `MSOLAPSvc.3/<host>:INSTANCENAME`); SQL Browser `MSOLAPDisco.3/<host>`. — [Microsoft Learn: Configure Kerberos to use Power BI reports](https://learn.microsoft.com/en-us/power-bi/report-server/configure-kerberos-powerbi-reports)
- Official (RLS on live connections): "Row-level security configured at the data source should work for certain DirectQuery (SQL Server, Azure SQL Database, Oracle, and Teradata) and live connections assuming Kerberos is configured properly in your environment." — [Microsoft Learn: data sources](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)
- Official (live SSAS auth options): for DirectQuery/live, "SQL Server Analysis Services — Username and password ✅, Windows authentication ✅, Integrated Windows authentication ✅". — [Microsoft Learn: data sources](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)
- Official (standalone SSAS is the XMLA target): "By default, Analysis Services listens on TCP/IP port 2383." and msmdpump "You can configure HTTP access for any supported version or edition of Analysis Services, running either tabular mode or multidimensional mode." — [Microsoft Learn: Configure HTTP Access to Analysis Services on IIS 8.0](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)
- Official changelog item: May 2021 (1.11.7815.26414) "Fixed a permission issue for live connect of SSAS tabular PBIX reports." — [Microsoft Learn: Change log for Power BI Report Server](https://learn.microsoft.com/en-us/power-bi/report-server/changelog)
- Community (snippet), consistent recommendation: "install an Analysis Services server and host your model there, then you could connect your pbix file in live connect mode" (Power BI team member). — [Fabric Community: Connect to PBI model in PBIRS](https://community.fabric.microsoft.com/t5/Report-Server/Connect-to-PBI-model-in-PBIRS/m-p/911467/highlight/true)
- Community (snippet), a PBIRS live-connection quirk: "Test Connection" under Manage > Data sources can report "Data source AnalysisServices is not supported" even though the live report renders. — [Fabric Community: Live connection to SSAS](https://community.fabric.microsoft.com/t5/Report-Server/Live-connection-to-SSAS/m-p/4733142)

### Inferences
- With live connection, the .pbix published to PBIRS contains only report layout plus a connection string; the semantic model (and all DAX) executes on the external SSAS server, which any XMLA client can query directly with standard, supported tooling and normal SSAS security (roles, RLS, Kerberos). This fully sidesteps the embedded-engine limitations (GUID names, eviction, 2 GB cap, no remote access).
- The trade-off is operational: a separately licensed and administered SSAS instance, SPN/delegation setup for per-user identity, and no PBIRS scheduled refresh (refresh is done on SSAS).

### Gaps
- Whether PBIRS live connections to SSAS Multidimensional (vs Tabular) are supported is not stated explicitly on the pages fetched; the data-source table says "SQL Server Analysis Services" generically.
