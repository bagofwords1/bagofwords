## KQ1. Does PBIRS write refreshed data back into the stored .pbix so a REST download returns fresh data, or does it keep the refreshed model only inside its Analysis Services instance / catalog?

### Takeaway
Microsoft's own PBIRS documentation states that downloading a .pbix from the server returns **the originally uploaded file**, and that server-side scheduled refreshes are **not** reflected in it. The refreshed model *is* persisted (the refresh status table says the refreshed model is "saved back to the report server catalog database"), but it is stored as a separate DataModel blob in the ReportServer DB, not written into the downloadable .pbix. So the "download-and-parse" approach reads stale (upload-time) data for any report that is refreshed on the server.

### Cited Findings
- Official, explicit: "You can open and edit Power BI report (.pbix) files from the server, but you get back the original file you uploaded. **If the data has been refreshed by the server, the data won't be refreshed when you first open the file**. You need to manually refresh it locally to see the change." — [What's new in Power BI Report Server (October 2017 section, "Open and edit .pbix files from the server"), learn.microsoft.com](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- Official refresh-status semantics (shows the refreshed model *is* persisted somewhere in the catalog DB): status "Streaming model to Analysis Server — Copying the model from the report server catalog database to the hosted Analysis Services instance"; "Refreshing data — Refreshing the data within the model"; "Removing credentials from the model — Removed the credentials used to connect to the data source from the model"; "Saving model to the catalog — Refreshing of data is complete and the refreshed model is being saved back to the report server catalog database." — [How to configure Power BI report scheduled refresh, learn.microsoft.com (ms.date 2025-11-01)](https://learn.microsoft.com/en-us/power-bi/report-server/configure-scheduled-refresh)
- Official (REST API intent): "The developer API (REST API) introduced for SSRS 2017 has been extended for Power BI Report Server to work with both Excel files and .pbix files. One potential use case is to programmatically download files from the server, refresh them, and then republish them. This is the only way to refresh Excel workbooks with PowerPivot models, for example." — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- Official (architecture): "Power BI Report Server now hosts SQL Server Analysis Services (SSAS) internally. This isn't specific to scheduled refresh. Hosting SSAS can greatly expand the report server memory footprint. The AS.ini configuration file is available on the server nodes, so if you're familiar with SSAS, you may want to update the settings, including maximum memory limit and disk caching etc." — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- Official (scale-out shows models are streamed from catalog DB to each node's SSAS): "you not only see an overuse of memory across nodes as the model is loaded N times, but performance will slow in between connections as the model is streamed as it hits a new node in between requests." — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- Community (Microsoft Fabric Community, PBIRS 15.0.1106.169 / May 2021 build): original poster: after a successful scheduled refresh "the web view shows updated visuals, but the downloaded PBIX is still the old version"; in ExecutionLog3 the Request Type was "Refresh Cache". Answer by community user "Icey": "I'm afraid that it is not supported to download .pbix file with the latest data from Power BI Report Server currently." and "the data will only be updated in Server Model". — [Visual updated in scheduled refresh, PBIX still old — Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Visual-updated-in-scheduled-refresh-PBIX-still-old/td-p/2280996)
- Community (storage layout, practitioner account quoted by "Icey"): on upload, the ReportServer DB stores the report in `dbo.Catalog` and two rows are created in `dbo.CatalogItemExtendedContent`: "One of these is the visuals, m code etc, the other is the data blob." The data blob is "a super compressed blob of data" (the `DataModel` file from the unzipped PBIX). The author *assumes* "this is so that you can setup a scheduled refresh of the data and it just overwrites the data blob." The server "looks like it does is fire up a captive instance of SSAS tabular and feeds it the data blob." — [How is data stored in Report Server between scheduled refreshes — Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/How-is-data-stored-in-Report-Server-between-scheduled-refreshes/m-p/1454162)
- Community (storage layout, second thread via search snippet): "the actual report definition and data model of the PBIX file are stored in the dbo.CatalogItemExtendedContent table, with rows typed CatalogItem, DataModel, and PowerBIReportDefinition"; "For PBIX files which contain live connection, there is no DataModel entry in the dbo.CatalogItemExtendedContent table"; "PBI Server checks whether the DataModel is already loaded and, if not, loads it (including data) from the CatalogItemExtendedContent table into an internal SSAS in-memory instance." — [How Report server store and run the Power BI reports — Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/How-Report-server-store-and-run-the-Power-BI-reports/td-p/1707223) (search-snippet level; page itself returned HTTP 403 to my fetch)
- Community (how to pull the pbix out of the DB): a query selecting the `Content` column, cast to `varbinary(max)`, joined to `Catalog` on `ItemID`, with "Type value 13 indicates a PBI report"; saving that binary "should yield a working PBIX". — [Where Can I find the published report in PowerBI Server — Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Where-Can-I-find-the-published-report-in-PowerBI-Server/m-p/397107/highlight/true) (search-snippet level)
- REST download behaviour: GET `.../Reports/api/v2.0/PowerBIReports({report-id})/Content/$value` returns a binary file with a `Content-Disposition` attachment and a `.pbix` filename; a community moderator said the endpoint "behaves more equivalent to the ExportReport API in PowerBI as it will only download the PBIX file." — [usage of REST API output from report server PowerBIReports(ID) — Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/usage-of-REST-API-output-from-report-server-PowerBIReports-ID/td-p/317413) (search-snippet level, 2017 thread)
- Official REST API overview: "The REST API provides programmatic access to the objects in a Power BI Report Server catalog... you can, for example, navigate the folder hierarchy, discover the contents of a folder, or download a report definition." The API "is built on the OpenAPI specification (also known as the swagger specification) and documentation is available on Microsoft Learn." — [Develop with the REST APIs for Power BI Report Server](https://learn.microsoft.com/en-us/power-bi/report-server/rest-api)
- (Cloud-only, for contrast) In the Power BI service a downloaded PBIX "contains only a snapshot of the data at the time of download", and large-model-format datasets "can't be downloaded as a Power BI Desktop (.pbix) file from the Power BI service." — [Fabric Community thread (service)](https://community.fabric.microsoft.com/t5/Service/Issue-of-Actual-Data-Refresh-After-Downloading-the-pbix-file/m-p/5145103); [Large semantic models in Power BI Premium](https://learn.microsoft.com/en-us/power-bi/enterprise/service-premium-large-models)

### Inferences
- The two official statements are consistent once you separate storage from download: the refreshed Vertipaq model is written back to the catalog DB (as the `DataModel` extended-content row, per community evidence), but the download endpoint (`CatalogItems({id})/Content/$value` / `PowerBIReports({id})/Content/$value`) serves the original uploaded `.pbix` blob. Therefore the download approach yields upload-time data for any import-mode report that is refreshed on the server; the only way to get fresh data via a downloaded file is the Microsoft-described loop "download → refresh locally in Power BI Desktop for RS → republish", which requires a Windows machine with Desktop and source credentials.
- Reading the refreshed `DataModel` blob directly from `dbo.CatalogItemExtendedContent` (bypassing REST) would in principle give the refreshed Vertipaq model. That blob is the same ABF/Vertipaq format pbixray already parses (pbixray reads `.abf` too). But this is an undocumented, unsupported path requiring SQL access to the ReportServer DB, and the refresh flow strips credentials and rewrites the model, so blob structure after refresh is not guaranteed to match what Desktop wrote. Speculation: the community poster's claim that refresh "just overwrites the data blob" is an assumption, not confirmed.
- The ExecutionLog3 "Refresh Cache" request type is consistent with "model refresh on the server, no rewrite of the uploaded report item".

### Gaps
- I found no Microsoft documentation of the `CatalogItemExtendedContent` schema or an official statement on exactly which table/row the refreshed model is written to; all table-level detail is from community posts.
- The official Swagger page for `GetCatalogItemContent` / `GetPowerBIReportContent` on learn.microsoft.com returned 404 to my fetch (URL guesses), so I could not quote the operation's documented description or stated permission.
- No source confirmed whether the PBIRS "Download" button and the REST `Content/$value` call are literally the same code path, though the official "you get back the original file you uploaded" statement is about the server download in general.

## KQ2. pbixray: concrete capabilities, limitations, recent bug reports (2024–2026), and support for current PBIX formats

### Takeaway
pbixray (Hugoberry) is actively maintained (32 PyPI releases, the latest 0.15.5 on 2026-08-27) and is a read-only extractor of the embedded Vertipaq `DataModel` (metadata + decoded table data, incl. RLS roles, measures as text). It explicitly does **not** evaluate DAX, parse the report layer, or handle `.pbit`/`.pbip`; live-connection pbix files fail with "DataModel not found in the archive". 2026 issues show a run of silent-wrong-value / misalignment bugs on large multi-segment tables (>1M and ~8M rows), several fixed quickly, one (#53) still open and one on hidden-table relationships (#64) open as of Sep 2026.

### Cited Findings
**Capabilities / scope (README)**
- Tagline: "Read Power BI semantic models without Power BI." Description: "A Python library to parse and analyze PBIX files used with Microsoft Power BI and Excel PowerPivot." — [pbixray on PyPI](https://pypi.org/project/pbixray/)
- Supported inputs: `.pbix`, `.abf` (Analysis Services backup) and `.xlsx` (PowerPivot): "File type is detected from the contents, so the same code works across all three." Not supported: `.pbit`, `.pbids`, `.pbip`. — [Hugoberry/pbixray README](https://github.com/Hugoberry/pbixray)
- Platforms: "Python 3.8 through 3.13, on macOS, Linux and Windows." "Prebuilt wheels, so there is nothing to compile." — [README](https://github.com/Hugoberry/pbixray)
- Decompression: Xpress decompression uses "Microsoft's own MIT-licensed Xpress reference implementations" wrapped as `xpress8` and `xpress9`; Huffman dictionary decoding uses `xmhuffman`, a native kernel that "fans out across cores." — [README](https://github.com/Hugoberry/pbixray)
- Exposes: measures, calculated columns, calculated tables, calculation groups; "all M code", M parameters, DataMashup queries "including DirectQuery and native SQL"; tables, columns, schema, relationships, hierarchies, perspectives, aggregations; row-level security, object-level security, roles and role memberships; per-column cardinality, dictionary/hash-index/data sizes and "total model size"; decoded table contents "whole or in chunks (`iter_table`, `on_disk=True`)"; "all 40 `$System.TMSCHEMA_*` endpoints" (DMV emulation). — [README](https://github.com/Hugoberry/pbixray)
- Explicit non-goals ("Scope" section): PBIXRay is "a read-only extractor for the data model." It does not: write, modify, or repack files; evaluate DAX ("expressions come back as source text"); run a query engine; connect to Power BI Service, Analysis Services, gateways, or workspaces; refresh anything; parse the report layer (visuals, pages, bookmarks, themes). — [README](https://github.com/Hugoberry/pbixray)
- Format status: the PBIX format is "undocumented and reverse-engineered", so the test corpus serves as the specification. — [README](https://github.com/Hugoberry/pbixray)
- Repo stats at fetch time: 180 commits, 174 stars, 22 forks, 2 open issues, 1 open PR. — [README](https://github.com/Hugoberry/pbixray)

**Release cadence (PyPI)**

- PBIRS adopted the enhanced format in the January 2021 release (preview) with the intent to make it "generally available as the only option in the next release of Report Server"; "Power BI Desktop for Report Server will automatically upgrade an existing dataset to the enhanced format for you." — [What's new in PBIRS (January 2021)](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- Tabular Editor docs: a .pbix "does not contain the model metadata in this format, and therefore, a .pbix file cannot be loaded directly in Tabular Editor in any way"; the JSON TOM metadata is in a `.pbit`. — [Tabular Editor: Power BI Desktop limitations](https://docs.tabulareditor.com/te3/desktop-limitations.html)

### Inferences
- pbixray reads the Vertipaq `DataModel` (which for enhanced-metadata files contains TMSCHEMA system tables), which is why it can emit `$System.TMSCHEMA_*` DMVs; there is no separate "v3 toggle" in its docs. Since Desktop for RS has used enhanced metadata since 2021, PBIRS-era files are in the format pbixray's corpus targets. However, every PBIRS-matched Desktop release (e.g. 2.158 Sep 2026) can tweak Vertipaq encodings, and the 2026 issue stream (#23, #37, #53, #59) shows the decoder is still catching up with real-world encodings — some failing *silently* (wrong values, dropped rows) rather than with an exception, which is the most dangerous failure mode for an analytics backend.
- Memory/performance: pre-0.15 pbixray materialised whole tables as pandas DataFrames; 0.15 added chunked/on-disk iteration. The DuckDB extension still decompresses the whole model in memory. Expect peak RAM of at least the uncompressed model size (the DataModel is Xpress-compressed; a 1 GB pbix can expand to several GB).
- DirectQuery / composite / live pbix: live-connection files have no `DataModel` → pbixray raises; DirectQuery files have a `DataModel` with metadata but no Vertipaq data for DQ partitions (pbixray can extract the M/native SQL of the DQ queries, per README, but not rows). I found no pbixray statement about incremental-refresh partitions or calculated-table data specifically.

### Gaps
- No statement from the maintainer about which Power BI Desktop versions are tested; the README says the test corpus is the spec but does not publish version coverage.
- No published benchmark on parse time/memory for 1–2 GB files; the "lazy/streaming reader" issue (#43) is the only evidence of large-file concerns.
- GitHub issue page 2 (4 older issues) was not fetched.

## KQ3. Can DAX measures be evaluated offline (no Analysis Services engine), especially on Linux?

### Takeaway
No. I found no open-source or third-party DAX *evaluation* engine for any platform; everything available is either a parser/lexer (sidemantic-dax, pbi_parsers, daxparser) or a client that sends DAX to a running Analysis Services/Power BI engine (DAX Studio, pymsasdax, Tabular Editor). pbixray explicitly returns measures as source text and "does not evaluate DAX".

### Cited Findings
- pbixray: does not "evaluate DAX, so expressions come back as source text" and does not "run a query engine". — [pbixray README](https://github.com/Hugoberry/pbixray)
- `bmsuisse/daxparser` "describes itself as a DAX parser, but it is actually a lexer only"; `sidemantic-dax` provides "Python bindings for a dax-parser crate" parsing "expressions and queries into typed AST nodes" (AGPL-3.0, Linux wheels); `pbi_parsers` "is designed to support code introspection and analysis, not execution"; `pymsasdax` runs DAX "against Microsoft Analysis Services, using COM Interop" (Windows MSOLAP dependency). — [GitHub bmsuisse/daxparser](https://github.com/bmsuisse/daxparser); [sidemantic-dax on PyPI](https://pypi.org/project/sidemantic-dax/0.13.0/); [pbi_parsers docs](https://douglassimonsen.github.io/pbi_parsers/); [pymsasdax on PyPI](https://pypi.org/project/pymsasdax/)
- DAX Studio is "a free, open-source tool for writing, testing, and optimizing DAX queries" that "runs against Power BI Desktop, Power BI Service (via XMLA endpoints), and SQL Server Analysis Services" — i.e. a client, not an engine; it is a Windows desktop app. — [DAX Studio – SQLBI](https://www.sqlbi.com/tools/dax-studio/); [Excelerator BI: Getting started with DAX Studio](https://exceleratorbi.com.au/getting-started-dax-studio/)
- Tabular Editor 2 "can edit a BIM file without accessing any data from the model" (offline *metadata* editing only); SQLBI: using Tabular Editor to modify a Power BI Desktop model "is not supported". — [SQLBI: Offline model editor experience for Power BI](https://www.sqlbi.com/blog/marco/2017/10/10/offline-model-editor-experience-for-power-bi/); [SQLBI Tabular Editor page](https://www.sqlbi.com/tools/tabular-editor/)
- DAX ties to the Microsoft engine: "the same Analysis Services engine for Tabular models is also used in Power BI and Power Pivot for Excel." — [Wikipedia: Power Pivot](https://en.wikipedia.org/wiki/Power_Pivot)
- "DAX query view" (Desktop for RS, Sept 2024 release feature list: "New INFO functions DAX query view is available in live connect Add or update multiple measures in DAX query view") runs inside Power BI Desktop's own embedded AS instance, Windows-only. — [What's new in PBIRS (September 2024)](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- PBIRS does not expose a model query endpoint: a community thread states "you cannot run DAX queries against a data model hosted in the on-prem Report Server. It does not expose an XMLA endpoint." — [Fabric Community: Retrieving report content from API or tables](https://community.fabric.microsoft.com/t5/Report-Server/Retrieving-report-content-from-API-or-tables-associated-from/td-p/3994850) (search-snippet level)
- pbi-tools: a "command-line DevOps tool that facilitates automation and version control"; prerequisites are Windows-oriented (".Net 4.7.2 Targeting Pack", ".Net 9.0 SDK", Power BI Desktop "Must be installed in default location for local development"); has `build.sh` as well as `build.cmd`; `extract` supports `-modelSerialization Raw`; the repo had 714 commits, 168 open issues, 451 stars and an **empty Releases section** at fetch time. It extracts/serialises; it is not a DAX evaluator. — [pbi-tools/pbi-tools on GitHub](https://github.com/pbi-tools/pbi-tools)

### Inferences
- The only ways to *evaluate* a measure from a PBIRS pbix are: (a) load the model into a real Analysis Services engine (Power BI Desktop, SSAS Tabular, Azure AS, or Fabric/Power BI service XMLA — all Windows/Microsoft-hosted); or (b) hand-translate each measure into SQL over the extracted tables (e.g. in DuckDB/Polars), which is only tractable for simple SUM/COUNT-style measures and breaks for CALCULATE/filter-context semantics. No "DAX-to-SQL translator" project surfaced in searches.
- pbi-tools' Linux build appears to be a build artefact rather than a documented Linux feature; its functionality depends on Power BI Desktop/AS assemblies for model work.

### Gaps
- I did not find a comprehensive survey proving a negative; the claim "no offline DAX engine exists" is supported by absence in two targeted searches plus pbixray's/Tabular Editor's own scope statements.
- pbi-tools README didn't state platform support or latest release; the repo's release list was empty at fetch.

## KQ4. PBIRS settings governing pbix size and model memory, and how they constrain the download approach

### Takeaway
Uploads are capped by the SSMS Advanced property `MaxFileSizeMb` (default 1000 MB, maximum 2 GB); models live in an internal SSAS whose memory is tuned via the AS.ini/msmdsrv config, with eviction controlled by `ModelCleanupCycleMinutes`/`ModelExpirationMinutes`. For the download approach the ceiling is therefore ~2 GB per compressed pbix, and the parser must be able to decompress a model of that size in RAM. The cloud "large dataset storage format" does not exist on PBIRS (cloud-only), and there is a separate "PBIX data limit" feature since Jan 2025.

### Cited Findings
- "You can upload files up to 2 GB in size, though by default this limit is set to 1 GB in the Report Server settings in SQL Server Management Studio (SSMS). These files are stored in the database just as they are for SharePoint, and no special configuration for the SQL Server catalog is required." — [What's new in PBIRS ("Large file upload/download")](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- SSMS Advanced Properties: "EnableCustomVisuals: True/False; EnablePowerBIReportEmbeddedModels: True/False; EnablePowerBIReportExportData: True/False; MaxFileSizeMb: Default is now 1000; ModelCleanupCycleMinutes: How often it checks to evict models from memory; ModelExpirationMinutes: How long until model expires and is evicted, based on last time used; ScheduleRefreshTimeoutMinutes: How long data refresh can take for a model. The default is two hours. There is no hard upper limit." — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- `rsreportserver.config` refresh-service knobs: `<PollingInterval>10</PollingInterval> <IsDataModelRefreshService>false</IsDataModelRefreshService> <MaxQueueThreads>0</MaxQueueThreads>`. — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- "There is a new separate API for large files, which will be updated in the Power BI Report Server version of Swagger." — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- Memory: "Hosting SSAS can greatly expand the report server memory footprint. The AS.ini configuration file is available on the server nodes ... update the settings, including maximum memory limit and disk caching etc." — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- RSReportServer.config memory settings (WorkingSetMaximum etc.) "apply only to paginated reports"; "Power BI (PBIX) reports and their scheduled refresh activities within Power BI Report Server are not affected by these settings." — [Configure available memory for report server applications](https://learn.microsoft.com/nl-nl/sql/reporting-services/report-server/configure-available-memory-for-report-server-applications?view=sql-server-2016) (search-snippet level)
- Community guidance (not official): adjust `msmdsrv.ini` to limit the Analysis Services engine to ~75% of RAM; later reply suggests TotalMemoryLimit 90–95% on a dedicated server with LowMemoryLimit 60–70%. — [Fabric Community: Power BI Report Server slow](https://community.fabric.microsoft.com/discussions/reportserver/power-bi-report-server-slow/4696078) (search-snippet level)
- Community on the limit: "With the latest Power BI report server version 14.0.600.442, default file size limit is 1 GB, and wen can increase it further to 2 GB"; another reply: MaxFileSizeMB default 1 GB and "a maximum supported size of 2GB is a hardcoded limit that cannot be changed"; a support reply: "1000 MB figure is not really 1000 MB for file size. Because we need other memory to run the queries." ### Inferences
- Constraint on the download approach: the artefact you can pull is at most ~2 GB compressed, and whatever you pull is stored "in the database just as they are for SharePoint" — i.e. the file as uploaded. Decompressing a 1–2 GB DataModel with pbixray/DuckDB-pbix requires RAM of several GB on the parsing host (both tools decompress in memory; pbixray ≥0.15 can iterate chunks).
- "Data limit" (Sept 2024 / Jan 2025) is the Desktop-side setting that caps rows loaded per table when authoring for the Report Server; I could not find its documentation page, so its interaction with model size is unverified.
- The "large dataset storage format" question is moot on PBIRS; models are standard Vertipaq blobs, so parseability is governed only by size and encoding, not a special on-disk format.

### Gaps
- The dedicated Microsoft Learn page on changing the PBIRS upload size limit (the URL I guessed returned 404) was not located; the only official text is in the "What's new" page.
- No official doc on the "PBIX data limit feature" semantics was found.
- No official per-model memory limit for PBIRS-hosted SSAS beyond "edit AS.ini".

## KQ5. Security implications of downloading the pbix (RLS bypass) and which PBIRS permission is needed for REST download

### Takeaway
A downloaded pbix contains the entire Vertipaq dataset; RLS/OLS roles are just metadata inside it (pbixray even lists them) and nothing enforces them offline, so anyone who can download gets unfiltered data. SSRS/PBIRS item security distinguishes "View reports" (Read Content + Read Properties — in the default Browser role) from "Consume reports"/"Manage reports" (which add Read Report Definition(s)); the official per-operation permission for `Content/$value` could not be retrieved, so which exact task the download requires is a gap.

### Cited Findings
- Item-level tasks and permissions: "Consume reports | Reports | Read Content Read Report Definitions Read Properties"; "Manage reports | Reports | Read Properties Delete Update Properties Update Parameters Read Data Sources Update Data Sources Read Report Definition Update Report Definition Execute Read Policy Update Policy"; "View reports | Reports | Read Content Read Properties". Page applies to "SQL Server 2016 (13.x) Reporting Services and later versions" and "Power BI Report Server". — [Item-level tasks (SSRS/PBIRS)](https://learn.microsoft.com/en-us/sql/reporting-services/security/tasks-and-permissions-item-level-tasks)
- Predefined roles: Browser includes "Comment on reports, Manage individual subscriptions, View folders, View models, View reports, View resources" (no Consume/Manage reports). Report Builder role adds "Consume reports — Reads report definitions"; "The most important task in this role definition is Consume reports, which allows a user to load a report definition from the report server into a local Report Builder instance." Content Manager: "All item-level tasks are selected by default". Publisher includes "Manage reports" ("view and modify report definitions"). "Manage all subscriptions" and "Manage individual subscriptions" also support "the editing and execution of scheduled refresh for Power BI (.pbix) files in Power BI Report Server". — [Predefined roles in Reporting Services](https://learn.microsoft.com/en-us/sql/reporting-services/security/role-definitions-predefined-roles)
- Scheduled-refresh permissions: "You need the necessary permissions to create a scheduled refresh plan. Permissions are defined in the role definitions for the report server." — [Configure scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/configure-scheduled-refresh)
- RLS in PBIRS is model-side (enforced by the hosted SSAS at view time) and for DQ/live is source-side: "Row-level security configured at the data source should work for certain DirectQuery (SQL Server, Azure SQL Database, Oracle, and Teradata) and live connections assuming Kerberos is configured properly in your environment." — [Power BI report data sources in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources). Change log Mar 2026: "Fixed issue where Power BI reports with RLS get stuck spinning." — [PBIRS change log](https://learn.microsoft.com/en-us/power-bi/report-server/changelog)
- pbixray extracts "row-level security, object-level security, roles, and role memberships" and decoded table contents — i.e. the roles are readable metadata, and the data they are meant to filter is fully readable alongside them. — [pbixray README](https://github.com/Hugoberry/pbixray)
- Scheduled refresh strips credentials before persisting: "Removing credentials from the model — Removed the credentials used to connect to the data source from the model." — [Configure scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/configure-scheduled-refresh)
- The server-side export-data switch exists separately: `EnablePowerBIReportExportData: True/False`. — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)

### Inferences
- Security: downloading a pbix is equivalent to handing the caller the full dataset with RLS removed. A service account used by an integration to download pbix files needs a role that allows reading the report definition (Content Manager / Publisher / Report Builder-style "Consume reports"), which is strictly more privilege than the Browser role needed to *view* the report with RLS applied. Any product that queries via downloaded pbix must re-implement RLS itself (it has the role DAX filter expressions as text, but, per KQ3, cannot evaluate them) or restrict the feature to users who are entitled to the whole model.
- The uploaded pbix may embed data-source connection details (M code / connection strings) — pbixray exposes "all M code" and native SQL — so the download also leaks source topology; the credential-stripping statement applies to the refreshed catalog model, not necessarily to the originally uploaded file (Speculation: Desktop normally does not store credentials in the pbix, but connection strings are present).
- Download permission: the "View reports" task (Read Content) is what lets the Browser role render a report; the official swagger (not retrievable here) is the authority on whether `Content/$value` needs Read Report Definition. Treat "at least Read Report Definition (Consume reports or Manage reports task)" as the working assumption and verify on a test server.

### Gaps
- The official REST reference entry for `CatalogItems({Id})/Content/$value` / `PowerBIReports({Id})/Content/$value` with its permission requirement was not retrievable (404 on learn.microsoft.com and swaggerhub URL guesses).
- No source found that explicitly says "Browser role can/cannot download the pbix" for PBIRS.

## KQ6. DirectQuery / live-connection / composite pbix on PBIRS under the download approach, and how common they are

### Takeaway
PBIRS supports import, DirectQuery and live connection to SSAS; for live-connection reports there is no `DataModel` in the pbix at all (pbixray fails with "DataModel not found in the archive"), and for DirectQuery the pbix holds metadata and queries but no row data, so the download approach returns nothing queryable. Composite models and Power BI datasets-as-source are not supported on PBIRS. I found no statistics on how common DQ/live reports are in PBIRS deployments.

### Cited Findings
- "Data can be imported or data can be queried directly using DirectQuery, or a live connection to SQL Server Analysis Services. Some data sources are available in Power BI Desktop that is optimized for use with Power BI Report Server, but they aren't supported when published to Power BI Report Server." "Important: All data sources in a Power BI Desktop report must support configuring scheduled refresh." — [Power BI report data sources in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)
- Live/DirectQuery-capable sources on PBIRS (table column "Live/DirectQuery ✅"): SQL Server Database, SQL Server Analysis Services, Azure SQL Database, Azure Analysis Services database, Azure Synapse Analytics, Oracle Database, PostgreSQL Database, SAP Business Warehouse server, SAP HANA Database, Teradata. "Power BI dataset in the Power BI service ❌ ❌ ❌" and "Power BI dataset in Power BI Report Server ❌ ❌ ❌". — [Power BI report data sources in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)
- "Power BI DirectQuery reports must include 'Encrypt=True;TrustServerCertificate=True' as part of the connection string on data sources, or apply the 'PBI_SQL_TRUSTED_SERVERS' environment variable on their Power BI Report Server." "Power BI Report Server doesn't support OAuth-based authentication for DirectQuery." — [Power BI report data sources in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)
- Scheduled refresh is for embedded models only: "you can set up scheduled data refresh to keep data up-to-date in Power BI reports with an embedded model rather than a live connection or DirectQuery. With an embedded model, you import the data, so it's disconnected from the original data source." — [What's new in PBIRS (October 2017)](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- "For PBIX files which contain live connection, there is no DataModel entry in the dbo.CatalogItemExtendedContent table". — [Fabric Community: How Report server store and run the Power BI reports](https://community.fabric.microsoft.com/t5/Report-Server/How-Report-server-store-and-run-the-Power-BI-reports/td-p/1707223) (search-snippet level)
- pbixray on a live-connection report: "DataModel not found in the archive." — [pbixray issue #7](https://github.com/Hugoberry/pbixray/issues/7)
- pbixray extracts DataMashup/M queries "including DirectQuery and native SQL" (metadata only). — [pbixray README](https://github.com/Hugoberry/pbixray)
- Connection-string management for DQ/refresh on the server: "In the October release of Power BI Report Server, we're enabling the ability to update connections for Power BI reports for DirectQuery and Refresh." — [What's new in PBIRS (October 2020)](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)

### Inferences
- Alternative path for *live-connection* reports: the real model is on an external SSAS Tabular (or Azure AS) server that already exposes XMLA/DAX; the pbix only carries a connection string. A live DAX integration should target that SSAS server directly rather than the PBIRS pbix.
- Alternative path for *import* models: Microsoft's documented pattern is to publish the model to a standalone SSAS Tabular instance and have PBIRS reports live-connect to it; this restores XMLA/DAX access and server-enforced RLS, at the cost of running SSAS (SQL Server Enterprise/Standard licensing) and converting the pbix model to a Tabular database (e.g. via Tabular Editor from a .pbit, since TE "cannot be loaded directly" from a .pbix).
- Composite models (import + DQ) are a Desktop feature; the PBIRS data-source table's "Power BI dataset ❌" rows indicate chaining to Power BI datasets is unsupported on PBIRS, but I found no explicit PBIRS statement on composite (mixed-storage-mode) models — treat as a gap.

### Gaps
- No survey/statistics on the share of DQ vs live vs import reports in PBIRS installations.
- No explicit PBIRS doc on composite models or incremental refresh support (cloud incremental refresh docs exist, but the PBIRS data-source page does not mention incremental refresh).

## KQ7. PBIP / PBIR / TMDL project formats — does PBIRS accept them?

### Takeaway
PBIP (folder project with PBIR report + TMDL model) is a Power BI Desktop/Fabric feature; I found **no** PBIRS documentation, change-log entry (2024–2026) or community source saying PBIRS accepts PBIP/PBIR/TMDL uploads. pbixray does not read `.pbip` either, so the project formats do not offer a PBIRS-side shortcut.

### Cited Findings
- "Power BI Projects (PBIP) support saving the report and semantic model into a folder using source-control friendly formats: PBIR for the report. TMDL for the semantic model." "Unlike PBIR-legacy format (report.json), PBIR is a publicly documented format." — [Power BI enhanced report format (PBIR), learn.microsoft.com](https://learn.microsoft.com/en-us/power-bi/developer/embedded/projects-enhanced-report-format)
- Microsoft (cloud/Desktop): "starting in January 2026, all new reports created in both Power BI Service and Desktop will use the PBIR format by default, and existing reports will be automatically converted to PBIR when edited and saved." — [Power BI blog, developer mode tag](https://australia.powerbi.microsoft.com/zh-cn/blog/tag/developer-mode) (search-snippet level; cloud/Desktop statement)
- PBIRS change log entries for 2024–2026 (full list fetched) contain no mention of PBIP, PBIR, TMDL or Power BI projects; items are bug fixes, SQL Server 2025 product IDs, `DisableMSRBConnect`, `EnableRefererValidation`, card visual support, scale-out fixes, etc. — [PBIRS change log](https://learn.microsoft.com/en-us/power-bi/report-server/changelog)
- PBIRS "What's new" (2024–2026 sections) has no PBIP/PBIR/TMDL entries (grep of the full page). — [What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)
- pbixray: not supported — `.pbit`, `.pbids`, `.pbip`. — [pbixray README](https://github.com/Hugoberry/pbixray)
- SQL Server 2025 consolidation: "Starting with SQL Server 2025, Microsoft is consolidating all on-premises reporting services under Power BI Report Server (PBIRS). No new versions of SQL Server Reporting Services (SSRS) will be released." — [What's new in PBIRS (September 2025)](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)

### Inferences
- Even if a team authors in PBIP, deployment to PBIRS still goes through a compiled `.pbix` from Desktop for RS; the TMDL files in source control describe the model *metadata* only (no data), so they are useful for schema/measure discovery but not for data access.

### Gaps
- Absence of evidence is not proof: no page explicitly says "PBIRS does not support PBIP". No Desktop-for-RS release note about enabling the PBIP save option was found.

## Summary matrix (for the report writer)

| Capability | Download pbix + parse (pbixray etc.) | Live DAX via engine (SSAS Tabular / external AS) |
|---|---|---|
| Data freshness on PBIRS-refreshed import model | Stale: returns originally uploaded file ([MS doc](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)) | Fresh (engine holds refreshed model) |
| Table rows | Yes (import partitions only; silent-decode bugs reported in 2026 on >1M/8M-row tables) | Yes via DAX/EVALUATE |
| Measures | Source text only; cannot evaluate | Evaluated by engine |
| RLS/OLS | Readable metadata, **not enforced** | Enforced by engine |
| DirectQuery / live pbix | No data (live: no `DataModel` at all) | Query the source SSAS/DB directly |
| Size ceiling | ≤2 GB pbix (`MaxFileSizeMb`, default 1000) and host RAM for decompression | Engine memory limits (AS.ini) |
| Permission needed | Read report definition (Consume/Manage reports-level task; Browser insufficient — inferred) | Engine-side role membership |
| Linux support | Yes (pbixray wheels Linux/macOS/Windows) | No open-source DAX engine on Linux; client libs only |
| PBIRS XMLA endpoint | n/a | Not exposed by PBIRS (community); must deploy to standalone SSAS |
