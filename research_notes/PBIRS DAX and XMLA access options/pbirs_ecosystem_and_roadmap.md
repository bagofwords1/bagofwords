# PBIRS ecosystem integration patterns and PBIRS roadmap/lifecycle status (as of October 2026)

Scope note: "PBIRS" = on-premises Power BI Report Server. Where a fact concerns SQL Server Reporting Services (SSRS) or the cloud Power BI service / Fabric, it is marked **[SSRS]** or **[cloud]**. Microsoft Fabric Community forum pages (community.fabric.microsoft.com) returned HTTP 403 to direct fetches during this research, so community-thread facts below come from search-result snippets and are marked **[community snippet]**; treat them as lower-confidence than Microsoft Learn pages.

## KQ1: Which concrete mechanisms do catalog/lineage/BI vendors use to extract metadata and data from PBIRS? Does anyone run DAX against PBIRS-hosted models?

### Takeaway
Every vendor connector found (Collibra, Alation, Talend/Qlik Data Catalog, DataHub, OpenMetadata/Collate) reaches PBIRS through the **PBIRS REST API v2.0** (the SSRS-derived `/Reports/api/v2.0` OData-style catalog API) with Windows/NTLM/Basic/Kerberos credentials, and all of them document that the API is "very limited" compared with the cloud Power BI Admin/Scanner APIs; the only path to model internals (tables, measures) is **downloading the .pbix via `PowerBIReports({id})/Content/$value` and parsing it offline**. No vendor found runs DAX against a PBIRS-hosted model, and no BI tool (Tableau, Qlik, Metabase, Superset, ThoughtSpot) or AI/NL-to-DAX product with Report Server support was found.

### Cited Findings

**Microsoft's own API surface (what vendors have to work with)**
- Microsoft: "The REST API provides programmatic access to the objects in a Power BI Report Server catalog. Examples of objects are folders, reports, KPIs, data sources, datasets, refresh plans, subscriptions, and more. Using the REST API, you can, for example, navigate the folder hierarchy, discover the contents of a folder, or download a report definition." Supported HTTP verbs: "DELETE, GET, HEAD, PUT, POST, and PATCH". The API "is built on the OpenAPI specification (also known as the swagger specification)". Page dated 2025-11-01. — [Develop with the REST APIs for Power BI Report Server](https://learn.microsoft.com/en-us/power-bi/report-server/rest-api)
- Microsoft REST reference landing page: "The REST API is a RESTful successor to the legacy SOAP API." Lists capabilities: "Navigate the folder hierarchy; Discover the contents of a folder; Download a report definition; Modify default report parameters; Change or execute a refresh plan". API samples at github.com/Microsoft/Reporting-Services. Page dated 2024-01-26. — [Power BI Report Server REST API documentation](https://learn.microsoft.com/en-us/rest/api/power-bi-report/)
- Microsoft documents the `DataModelParameters` REST API (via PowerShell `Get-RsRestItemDataModelParameters` / `Set-RsRestItemDataModelParameters`) for reading/changing a Power BI report's parameterized connection values after publishing; prerequisites: report saved with "Enhanced DataSet Metadata enabled" and "Only reports with parameterized connections and databases can be updated after publishing." "This example uses the Reporting Services PowerShell tools. You can achieve the same by using the new REST APIs." — [Change data source connection strings with PowerShell](https://learn.microsoft.com/en-us/power-bi/report-server/connect-data-source-apis)
- The open-source `ReportingServicesTools` PowerShell module (microsoft/ReportingServicesTools) exposes `Get-RsRestItemDataSource` ("Fetches embedded data sources associated with a Paginated report or a Power BI report using the REST Endpoint"), `Test-RsRestItemDataSource`, `Set-RsRestItemDataSource`, and `Write-RsRestCatalogItem` (upload) — [PowerShell Gallery: Get-RsRestItemDataSource.ps1](https://powershellgallery.com/packages/ReportingServicesTools/0.0.9.3/Content/Functions/CatalogItems/Rest/Get-RsRestItemDataSource.ps1); [microsoft/ReportingServicesTools](https://github.com/microsoft/ReportingServicesTools)
- **[community snippet]** The pbix download endpoint form is `.../Reports/api/v2.0/PowerBIReports({report-id})/Content/$value`; a reply notes this "downloads only the PBIX file, similar to the ExportReport operation in the cloud Power BI service", and that on-premises Report Server data models "cannot be queried with DAX, because they don't expose an XMLA endpoint" (community reply, not official). — [Retrieving report content from API or tables](https://community.fabric.microsoft.com/t5/Report-Server/Retrieving-report-content-from-API-or-tables-associated-from/m-p/4034239); [usage of REST API output](https://community.fabric.microsoft.com/t5/Report-Server/usage-of-REST-API-output-from-report-server-PowerBIReports-ID/m-p/318645)
- **[SSRS/legacy SOAP]** The SOAP endpoints `ReportService2010` (management) and `ReportExecution2005` (render) are the legacy API; a PBIRS user reported `ReportExecution2005` returning "This operation is not supported on a report server that runs in native mode" (`rsOperationNotSupportedNativeMode`) after upgrade **[community snippet, single user]**. — [Report Server Web service endpoints](https://learn.microsoft.com/hu-hu/sql/reporting-services/report-server-web-service/methods/report-server-web-service-endpoints?view=sql-server-2017); [SOAP Api not supported thread](https://community.fabric.microsoft.com/t5/Report-Server/SOAP-Api-This-operation-is-not-supported-on-a-report-server-that/m-p/765949)

**Data-catalog / lineage vendors**
- **Talend Data Catalog / Qlik (MITI bridge) "Microsoft Power BI Report Server (Repository) - Import"**: metadata read "via Java REST API"; default server URL `http://localhost:80/Reports`; Windows authentication with `DomainName\UserName`; imports Folders, Power BI reports, paginated RDL reports, DataSets, DataSources. Explicitly: the Report Server REST APIs are "very limited compared to" the Azure Power BI Admin REST API and the PBIX/PBIT file bridge; lineage is connection-level only — it extracts only the names of data connections, which is "often not enough to connect/stitch to the source data stores". It can download PBIX files via REST but warns they "can be very large as they may contain data." — [Talend/Qlik help: PBIRS Import bridge](https://help.qlik.com/talend/en-US/talend-data-catalog/8.0/Content/MIRMicrosoftPowerBIReportServerImport.htm)
- **Collibra Data Lineage "SSRS-PBRS" integration (Edge/Cloud site, docs version 2026.08/latest)**: connection "retrieve[s] metadata from SQL Server Reporting Services or Power BI Report Server"; steps: preflight checks → connection → "Technical Lineage for SSRS/PBRS" capability → scheduled sync. Stated limitations: "Transformations are not included in the integration."; "Some of the more complex SQL queries might not be supported."; "There are known limitations to the metadata returned by the API when integrating PBRS."; and critically: "Power BI reports in PBRS are ingested as Power BI Report assets in Data Catalog, but there is no technical lineage for the reports." — [Collibra: Steps overview SSRS-PBRS via Edge](https://productresources.collibra.com/docs/collibra/latest/Content/CollibraDataLineage/DataSources/SSRS-PBRS/ref_ssrs-pbrs-steps.htm). Older (2023.05) doc: "the lineage harvester connects to the SSRS or PBRS web portal"; user needs system role ≥ System user and item role ≥ Content Manager. — [Collibra 2023.05 overview](https://productresources.collibra.com/docs/collibra/2023.05/Content/CollibraDataLineage/SSRS-PBRS/ref_overview-ssrs-pbrs-steps.htm). A 2021.07 doc said PBRS ingestion was preview-only "without stitching or technical lineage". — [Collibra 2021.07 PBRS](https://productresources.collibra.com/docs/collibra/2021.07/Content/Catalog/PBRS/to_power-bi-report-server.htm)
- **Alation "Power BI On-Prem" Enhanced Connector** (an enhanced connector that "require[s] a separate entitlement in addition to your Alation platform license"; supports "Power BI On-Premise from 2023 onward", needs Alation 2023.1.0+): uses the Power BI Report Server REST API ("programmatic access to the report server catalog"); auth NTLM, Basic, Kerberos; extracts folders, reports, "PowerBI Reports (PBIX) and their dimensions and measures", datasets, data sources, SQL query text from datasets. Measures/dimensions "require access to the underlying PBIX files, and 'DAX expressions are not available.'" Dataset fields "are populated only from fields that appear in reports, because Microsoft provides no separate API for them." Lineage: table-level report→data source "but not for PBIX report types"; "Column-level lineage is not available because Microsoft provides no API for the required data source information." — [Alation PBI On-Prem OCF Connector Overview](https://docs.alation.com/en/latest/fde/EnhancedConnectors/PBIOnPremOCFConnector/PBIOnPremOCFConnectorOverview.html). Alation's cloud Power BI Scanner connector separately "does not support Power BI On-Premise instances." — [Alation Power BI Scanner OCF](https://docs.alation.com/en/latest/sources/OpenConnectorFramework/PowerBIScannerOCFConnector/PowerBIScannerConnectorOverview.html)
- **DataHub "PowerBI Report Server" source (Beta)**: config `username`, `password`, `workstation_name` (Windows account), `host_port` (e.g. `localhost:80`), `report_virtual_directory_name`, `report_server_virtual_directory_name`, `server_alias`, `report_pattern`, `extract_ownership`. Extracts report name/description/ownership/folder/webUrl for Power BI (.pbix), paginated (.rdl), mobile and linked reports — all mapped to DataHub `Dashboard`; Dataset and Datasource map to "N/A". It states tiles, a report's datasource and a report's dataset "cannot be ingested because of REST API limits" and upstream lineage is "limited compared with cloud Power BI ingestion." — [DataHub docs: PowerBI Report Server](https://docs.datahub.com/docs/generated/ingestion/sources/powerbi-report-server)
- **OpenMetadata / Collate "PowerBI Report Server" connector**: labelled BETA; "The PowerBI Report Server should be accessible from the ingestion environment"; installed via `collate-ingestion[powerbi-report-server]`. Hosted on Collate's docs; the OpenMetadata-site connector page for `powerbireportserver` returned 404 at `latest/`. — [Collate docs: PowerBI Report Server connector](https://docs.getcollate.io/connectors/dashboard/powerbireportserver); [YAML](https://docs.getcollate.io/connectors/dashboard/powerbireportserver/yaml)
- **Microsoft Purview** (Microsoft's own catalog): the Power BI/Fabric source scans a *tenant* via Power BI Admin/metadata-scanner APIs (requires "Allow service principals to use read-only Power BI admin APIs", `*.powerbi.com`, `*.analysis.windows.net`); the page never mentions Power BI Report Server and the self-hosted integration runtime is only for reaching a private-endpoint cloud tenant. ### Inferences
- The de-facto integration stack for PBIRS is: (1) REST v2.0 catalog walk for folders/reports/data sources/refresh plans, (2) `Content/$value` pbix download + offline parse of `DataModelSchema`/`Report/Layout` for model metadata, (3) optionally the ReportServer SQL database for usage. No vendor has a way to execute DAX on the server-hosted model, consistent with the absence of an XMLA endpoint.
- Alation's note that DAX expressions are "not available" even after pbix access suggests vendors parse the pbix's model schema only for object names; the compressed `DataModel` blob (Vertipaq/ABF) is not parsed by any catalog vendor found.
- Because Desktop for RS lacks preview features and the enhanced-metadata toggle in older versions, pbix files from PBIRS may be in legacy (non-"DataModelSchema" JSON) format for older reports, complicating offline parsing (inference from the Tabular Editor thread; not directly documented).

### Gaps
- No vendor doc confirmed whether PBIRS pbix downloads include the data model (the Talend note "may contain data" implies yes for import-mode reports, but it is not explicit for every report type).
- Could not fetch the Fabric Community threads directly (403) to verify the exact quotes attributed to Microsoft employees.
- No official Microsoft page enumerating which SOAP operations PBIRS supports for Power BI items; the swagger spec for PBIRS v2.0 could not be fetched (SwaggerHub/GitHub paths 404).
- OpenMetadata's own (non-Collate) docs page for the Report Server connector was not reachable; version added unknown.

## KQ2: Is reading the ReportServer catalog SQL database directly a common and supported integration pattern, and what useful tables exist?

### Takeaway
Querying the `ReportServer` database is extremely common in the community (especially `ExecutionLog3` for usage/audit, and `Catalog` + `CatalogItemExtendedContent` for locating pbix blobs), but Microsoft states the schema is undocumented and unsupported; Microsoft staff warn that modifying it "could put your data/catalog in a bad state". The tables `DataModelDataSource` and `SchedRefreshPlans` named in the assignment could not be confirmed to exist under those names in any source.

### Cited Findings
- Redgate Simple Talk: "Microsoft does not formally document the _ReportServer_ database." and "This is undocumented and not supported by Microsoft." Catalog `Type` codes listed: 1 Folder, 2 Report, 3 File, 4 Linked Report, 5 Data Source, 6 Report Model, 7 Report Part, 8 Shared Data Set, 9 Report Part, 11 KPI, 12 Mobile Report Folder, **13 PowerBI Desktop Document**. `Catalog` columns used: ItemID, ParentID, Path, Name, Type, Description, Hidden, CreationDate, ModifiedDate, ContentSize. `Users` (UserID, UserName, UserType, AuthType). `Subscriptions` (SubscriptionID, Description, LastStatus, EventType, LastRunTime, Parameters, OwnerID, Report_OID, ModifiedByID). `ReportSchedule` links subscriptions to SQL Agent jobs (ScheduleID, SubscriptionID, ReportID). `ExecutionLogStorage` is the base table with views `ExecutionLog`, `ExecutionLog2`, `ExecutionLog3`. Permissions via `PolicyUserRole`, `Roles`, `Catalog.PolicyID`. — [Insights from the SSRS database (Redgate)](https://www.red-gate.com/simple-talk/databases/sql-server/bi-sql-server/insights-from-the-ssrs-database/) **[SSRS-origin, applies to PBIRS]**
- Microsoft's own PBIRS doc uses `Sql.Database("localhost","ReportServer")` → `dbo.ExecutionLog3` as its worked example of a Power BI report data source, implicitly endorsing read access to that view. — [Change data source connection strings with PowerShell](https://learn.microsoft.com/en-us/power-bi/report-server/connect-data-source-apis)
- Data Mozart (PBIRS usage metrics): uses `ExecutionLog3` ("retrieve data from the underlying table ExecutionlogStorage") with columns InstanceName, ItemPath, UserName, RequestType, Parameters, ItemAction, TimeStart, TimeEnd, TimeDataRetrieval, TimeProcessing, TimeRendering, Source, Status, ByteCount, RowCount; joins to `Catalog` on `ItemPath = Path`; RequestType 0=Interactive, 1=Subscription, 2=Refresh Cache. — [Check Power BI usage metrics on Report Server](https://data-mozart.com/check-power-bi-usage-metrics-on-report-server/)
- **[community snippet]** PBIRS-specific `ItemAction` values seen in `ExecutionLog3`: QueryData, ASModelStream, DataRefresh, SaveToCatalog, ConceptualSchema, Execute, Render, Toggle; "the official documentation didn't cover them"; also "the various Time fields (TimeDataRetrieval, TimeProcessing, TimeRendering) in dbo.ExecutionLog3 are blank for items with the source PBIX." No built-in audit UI: "this information is not currently exposed on the front end of Report Server." — [Power BI Report Server Execution Log thread](https://community.fabric.microsoft.com/t5/Report-Server/Power-BI-Report-Server-Execution-Log/m-p/376976); [Audit log - Report server](https://community.fabric.microsoft.com/t5/Report-Server/Audit-log-Report-server/m-p/1756310)
- Default execution-log retention is 60 days; `ExecutionLog3` is "the newest version, with ExecutionLog and ExecutionLog2 kept for backward compatibility". — [Curated SQL: Troubleshooting slow PBIRS reports](https://curatedsql.com/2020/02/06/troubleshooting-slow-power-bi-report-server-reports/); [InterfaceTT SSRS audit](https://www.interfacett.com/class-content/how-to-audit-report-execution-in-sql-server-reporting-services-ssrs/)
- **[community snippet]** pbix storage: `dbo.Catalog` (Type 13) joined to `dbo.CatalogItemExtendedContent` on ItemID; three rows per Power BI report — `CatalogItem` (full pbix), `DataModel` (split-out data blob), `PowerBIReportDefinition` (pbix without the model); live-connection reports have no `DataModel` row. A Power BI team member confirmed "the report definition and data model are stored in the CatalogItemExtendedContent table" and warned that extracting it "is not supported and could put you data/catalog in a bad state." — [Where can I find the published report in PowerBI Server](https://community.fabric.microsoft.com/t5/Report-Server/Where-Can-I-find-the-published-report-in-PowerBI-Server/m-p/397140); [How Report server store and run the Power BI reports](https://community.fabric.microsoft.com/t5/Report-Server/How-Report-server-store-and-run-the-Power-BI-reports/m-p/1709036)
- Microsoft describes the refresh pipeline in terms that confirm the catalog-DB-as-store design: status "Streaming model to Analysis Server — Copying the model from the report server catalog database to the hosted Analysis Services instance" and "Saving model to the catalog — ... the refreshed model is being saved back to the report server catalog database." — [Configure scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/configure-scheduled-refresh)
- **[community snippet]** Refresh-schedule/history investigation uses `ReportSchedule`, `Schedule`, `Catalog`, `ExecutionLogStorage` filtered on `DataModel` format and `DataModelRefresh` event type; refresh jobs are SQL Agent jobs with GUID names traceable to `Schedule`; `dbo.SubscriptionsHistory` seemed to keep ~10 days on one server; stuck refreshes relate to the `Event` table. — [Report Server does not complete Data Refresh](https://community.fabric.microsoft.com/t5/Report-Server/Report-Server-does-not-complete-Data-Refresh/m-p/4035295); [SubscriptionsHistory thread](https://community.fabric.microsoft.com/t5/Report-Server/dbo-SubscriptionsHistory-table-depuration/m-p/746785); [List of current Scheduled Refresh jobs](https://community.fabric.microsoft.com/t5/Report-Server/List-of-current-Sheduled-Refresh-jobs/m-p/586578/highlight/true)
- Collibra, Alation, Talend, DataHub and OpenMetadata all connect through the web portal/REST API, **not** the SQL database (see KQ1 sources).

### Inferences
- Reading `ExecutionLog3` (and `Catalog`) read-only is a widely used, Microsoft-tolerated pattern for usage/audit analytics, but no commercial catalog vendor relies on it — probably because it requires DB-level access and the schema is unsupported.
- For a product integration, the ReportServer DB is best treated as an optional, read-only enrichment source (usage, refresh history), with the REST API as the primary interface.

### Gaps
- Could not confirm tables named `DataModelDataSource` or `SchedRefreshPlans` exist; the REST API exposes `DataModelDataSources` and `CacheRefreshPlans` as *API* resources, but the backing table names were not found in any source.
- No full column list for `CatalogItemExtendedContent` or for the PBIRS-specific `ExecutionLog3` `ItemAction` semantics from Microsoft.

## KQ3: What is the lifecycle status of PBIRS as of 2026 and what did Microsoft say most recently about its future and licensing?

### Takeaway
PBIRS is alive and arguably more strategic than before: in 2025 Microsoft made it the sole on-premises reporting product ("No new versions of SQL Server Reporting Services (SSRS) will be released. PBIRS becomes the default on-premises reporting solution for SQL Server"), extended licensing to SQL Server 2025 Standard **and** Enterprise, and kept the capacity entitlement alive via Fabric F64+ reserved instances after P-SKU retirement. It ships three times a year (Jan/May/Sep), with Sep 2026 (v1.27) the latest; the Microsoft Lifecycle page shows "In Support" under the Modern Lifecycle Policy with no retirement date. There is no public roadmap, Fabric-on-prem statement, or end-of-life announcement; releases are small (visual/accessibility roll-ups, security/config fixes).

### Cited Findings

**Lifecycle policy**
- "Power BI Report Server releases a few times per year. Security and critical updates are available until the next release becomes generally available (GA). After the next release, the previous release continues to receive security updates for the remainder of the 12-month release lifespan." — [Support timeline for Power BI Report Server](https://learn.microsoft.com/en-us/power-bi/report-server/support-timeline) (page dated 2025-11-01)
- Microsoft Lifecycle: "Power BI Report Server follows the Modern Lifecycle Policy." Support Dates: Start 6/12/2017, Retirement Date "In Support". — [Microsoft Lifecycle: Power BI Report Server](https://learn.microsoft.com/en-us/lifecycle/products/power-bi-report-server)
- Release cadence: "Three times a year (January, May, September)"; "Latest features and fixes come to the Power BI service first. A rollup of features from Power BI Desktop releases for the service comes to Power BI Report Server in each release; most other features are only meant for the Power BI service." — [Compare PBIRS and the Power BI service](https://learn.microsoft.com/en-us/power-bi/report-server/compare-report-server-service)
- **[community snippet]** No published roadmap: a community answer says PBIRS "follows behind the service, and features that have reached GA since the last release and don't require cloud infrastructure are evaluated for inclusion." — [Power BI Report Server roadmap thread](https://community.fabric.microsoft.com/t5/Report-Server/Power-BI-Report-Server-roadmap/m-p/3444027)

## KQ4: What does Microsoft's official comparison page list as unsupported in PBIRS that matters for programmatic data access?

### Takeaway

## KQ6 (section 4 of assignment): The embedded Analysis Services instance — ecosystem tools and documented behavior

### Takeaway
PBIRS runs a private Analysis Services engine (`msmdsrv.exe` under `...\PBIRS\ASEngine\`, configured by `msmdsrv.ini`, with a dynamic port); Microsoft describes it only indirectly (model is "streamed" from the catalog DB to the "hosted Analysis Services instance" and saved back). Community members have located its port via `msmdsrv.ini`/`netstat` and connected locally, but Microsoft-aligned community answers say it "is only used for running .pbix based reports", is not reachable from other machines, is not a Windows service, and stopping it breaks pbix reports. No ecosystem tool was found that documents or supports connecting to it.

### Cited Findings
- Microsoft (refresh status table): "Streaming model to Analysis Server — Copying the model from the report server catalog database to the hosted Analysis Services instance." "Refreshing data — Refreshing the data within the model." "Removing credentials from the model" then "Saving model to the catalog." — [Configure scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/configure-scheduled-refresh)
- **[community snippet]** "There is a embedded version of the SSAS engine inside PBIRS, but that is only used for running .pbix based reports. You cannot connect to that from other machines and you cannot deploy custom models to that instance." "It is an internal process entirely managed by Power BI Report Server and if you attempt to stop it all your pbix reports will stop working." Port discovery: "Search for port number in C:\Program Files\Microsoft Power BI Report Server\PBIRS\ASEngine\workspaces\msmdsrv.ini - <Port>5132</Port>. Or find the PID of msmdsrv.exe running process and in cmd start this 'netstat /ano | findstr "13944"'". — [Is SSAS service included in Power BI Report Server on-premise](https://community.fabric.microsoft.com/t5/Report-Server/Is-SSAS-service-included-in-Power-BI-Report-Server-on-premise/m-p/754288)
- **[community snippet]** Operational thread "Microsoft.PowerBI.ReportServer.AsServer.AsConnectionException": msmdsrv.exe failing to restart after server restart breaks Import-mode reports; workaround edits `<CriticalErrorHandling>` in `Program Files\Microsoft Power BI Report Server\PBIRS\ASEngine\msmdsrv.ini`. — [AsConnectionException thread](https://community.fabric.microsoft.com/t5/Report-Server/Microsoft-PowerBI-ReportServer-AsServer-AsConnectionException/m-p/3304565)
- `ExecutionLog3` `ItemAction` values `ASModelStream` and `ConceptualSchema` for pbix items corroborate the stream-model-to-AS lifecycle **[community snippet]**. — [PBIRS Execution Log thread](https://community.fabric.microsoft.com/t5/Report-Server/Power-BI-Report-Server-Execution-Log/m-p/376976)
- SSMS connects to PBIRS only as a *Reporting Services* server type via the web service URL, not as Analysis Services. — [Connect to Power BI Report Server with SSMS (SQLServerCentral)](https://www.sqlservercentral.com/blogs/connect-to-power-bi-report-server-with-ssms)
- Contrast **[Desktop, not server]**: Power BI Desktop's local AS instance uses "a random port number" and a GUID model name, and the External Tools ribbon passes server/port/model to tools — this mechanism is what DAX Studio/Tabular Editor rely on, and it is "not supported in Power BI Desktop for Power BI Report Server." — [External tools](https://learn.microsoft.com/en-us/power-bi/transform-model/desktop-external-tools)
- DAX Studio documents connecting to Power BI Desktop (auto-discovered port) and to Analysis Services instances by name; no PBIRS connection mode is documented. — [DAX Studio: Getting Connected](https://daxstudio.org/tutorials/getting-connected/)

### Inferences
- Technically, a process on the PBIRS host could open a TCP connection to the embedded engine (port from `msmdsrv.ini`), but model databases are loaded/unloaded dynamically by the server (names are internal, credentials stripped, models unloaded when idle — cf. Jan 2025 fix "viewing PBIX reports when the underlying model had been unloaded"), so any such integration would be fragile, local-only, and unsupported.
- No vendor (catalog, lineage, BI, AI) has built on this path, which is itself strong evidence that it is not a viable commercial integration surface.

### Gaps
- No Microsoft documentation of the ASEngine folder, `msmdsrv.ini`, port behavior, or model-naming scheme was found; all details are community-sourced and could not be verified by direct fetch (403).
- No source confirms whether the embedded engine accepts XMLA/TOM connections at all (e.g., whether `msmdsrv.ini` restricts to localhost or uses a non-standard protocol).
