# How AI-analytics peers publish evals, and how coding agents perform on data work (as of 2026-10-08)

Scope note: this file covers (1) what peer AI-analytics / text-to-SQL products have published as benchmarks or eval methodology, (2) measured evidence on general coding agents (Claude Code, Codex, Cursor, Gemini CLI, etc.) doing SQL / data-analysis / dashboard work, (3) quantified evidence that context / semantic layers / instructions raise accuracy, (4) MCP-tool benchmarks and whether they touch databases, (5) evidence on self-improving / context-optimization loops. Every claim is dated and labeled **[measured]** (a number from a described methodology), **[vendor-internal]** (a number from the vendor's own undisclosed or partially disclosed test), or **[marketing]** (an unquantified or unsourced claim). Research was conducted 2026-10-08 via web search and page fetches; items I could not verify are in Gaps.

---

## Key Question 1 — Peers: what have AI-analytics startups and open-source text-to-SQL projects published?

### Takeaway
Almost no peer has published a reproducible, third-party-checkable accuracy benchmark of its own product. The pattern is: (a) a few vendor-run comparative benchmarks that rank the vendor first (Basedash BI Bench, Databricks Genie One, Snowflake Cortex Analyst, Energent), (b) eval *tooling* and methodology posts without headline numbers (Hex, Defog sql-eval, Databricks Genie benchmarks feature, Snowflake Cortex Analyst evaluations), (c) public-leaderboard entries on DABstep / Spider 2.0 by products (getdot.ai, H2O, NVIDIA, Zoom, JetBrains, Genloop, etc.), and (d) nothing at all for most of the long tail (Julius, Vanna, Wren, Zenlytic, Fabi, Count, Briefer, Deepnote, Querio-as-product, DataLine, Text2SQL.ai, Omni, Metabase, Lightdash, Preset/Superset, Sigma).

### Cited Findings

**Hex (Notebook Agent / Hex Agent / Evals)**
- Hex published "How we evaluate data agents" (Izzy Miller, 2026-05-22; page modified 2026-08-10). It describes an internal eval system ("Shoebox") doing pairwise candidate-vs-baseline runs on a synthetic company ("Shorelane Commerce", ~$129M revenue, "30,000 handcrafted lines of data generators", dbt models, docs, personas). Rubrics are deterministic, LLM-judged, or hybrid. It explicitly says "Our eval sets are also relatively small compared to public benchmarks" and reports **no overall accuracy score**. The only number is illustrative: a judge accepted a 2.03%-vs-2.04% near-miss as correct 35% of the time; authors admit "we still sometimes struggle to calibrate and align our LLM judges." The post criticizes Spider/BIRD as "demo shaped" and says "the performance of agents in Hex is more a function of the rich context stores they access" than prompts or models. **[methodology only, no numbers]** — [Hex blog](https://hex.tech/blog/evaluate-data-agents/)
- Hex launched a customer-facing **Evals** product on 2026-08-04 (Team/Enterprise plans): version-controlled test cases run from the Hex CLI; simplest case is a numeric result or reference SQL with a tolerance; advanced cases use an LLM-as-judge that reads the whole conversation and checks which semantic model / guide the agent used, whether it asked for clarification, or appropriately refused. Each case can run up to 3 times. **No accuracy or pass-rate numbers and no vendor comparisons** are published. — [Hex "Introducing Evals"](https://hex.tech/blog/evals/); [Hex docs](https://learn.hex.tech/docs/agent-management/evals); [changelog 2026-08-04](https://learn.hex.tech/changelog/2026-08-04)
- Hex's AI lead Bryan Bischof publicly argues against single aggregate metrics and for whole-system evaluation (Humanloop interview). — [Humanloop](https://humanloop.com/blog/LLM-eval-done-right)
- Hex error-analysis post: clustered Notebook Agent errors (Python/SQL errors, cell timeouts, vague error messages) to drive fixes. — [plushcap summary of Hex post](https://www.plushcap.com/content/hex/blog/hex-improving-the-notebook-agent-error-clustering)
- Third-party measurement: in Basedash's BI Bench (vendor-run, undated page, 11 tools), Hex scored **80.6% accuracy at 198.2s avg/task**, 3rd place. **[measured by a competitor]** — [Basedash BI Bench](https://www.basedash.com/bi-bench)

**Vanna.ai**
- No official Vanna accuracy benchmark found. A 2024 academic study used Vanna with three local LLMs on 6 questions and found adding detailed schema *reduced* accuracy and increased latency for Llama3 — tiny sample, measures the LLM not Vanna. A Scopic practitioner review said Vanna "struggled with correctly identifying and mapping tables" on complex schemas. A blog's "91.4%" figure actually belongs to Defog SQLCoder, not Vanna. **[no vendor number]** — [IDEAS/RePEc study](https://ideas.repec.org/a/ers/journl/vxxviiy2024ispecialbp426-438.html); [Scopic review](https://scopicsoftware.com/blog/ai-sql-tools/); [themenonlab blog](https://themenonlab.blog/blog/text-to-sql-open-source-local)

**Defog (SQLCoder, sql-eval)**
- sql-eval (open-source, Postgres-first, Snowflake/BigQuery/MySQL/SQLite/SQL Server via DDL translation) runs generated SQL and gold SQL against the same DB and compares result dataframes with "exact" and "subset" match; ~200 questions derived from Spider with new data because Defog found data-quality problems in Spider's DBs; categories: joins, GROUP BY, ORDER BY, ratios, WHERE. Supports instruction files (`instruct_basic`, `instruct_advanced`), k-shot examples, and column pruning as prompt inputs. The methodology post (2023-08-20) explains why they rejected string match and GPT-4-as-judge (reproducibility, drift). **[methodology, open code]** — [defog-ai/sql-eval](https://github.com/defog-ai/sql-eval); [Defog "Open-sourcing SQL-Eval"](https://defog.ai/blog/open-sourcing-sqleval/)
- SQLCoder model-card numbers (held-out schemas, n=200, 4 beams): early README gpt-4 74.3 / defog-sqlcoder 64.6 / gpt-3.5 60.6; Oct-2023 README gpt-4 82.0 / sqlcoder2 77.5. Numbers across README versions are not comparable. **[vendor-run but open code]** — [defog-ai/sqlcoder](https://github.com/defog-ai/sqlcoder); [HF sqlcoder-7b-2](https://huggingface.co/defog/sqlcoder-7b-2)

**Benchmark reliability caveats peers should be judged against**

### Inferences
- The field's "publishing norm" is bifurcated: hyperscaler-adjacent vendors (Databricks, Snowflake) publish undisclosed-methodology internal numbers vs an anonymized "coding agent"; startups either publish eval *tooling* (Hex) or nothing. A launch that publishes (i) the question set, (ii) the grading code, (iii) per-run traces, and (iv) *named* coding-agent baselines would be differentiated against every peer found here.
- Public-leaderboard entries (DABstep, Spider 2.0) are the only place products are measured on a shared yardstick; DABstep hard is now saturated (16+ entries at 100%), so a DABstep entry is table stakes rather than differentiation. Spider 2.0-DBT (top 65.6%) and the new DAB benchmark (best 57% pass@1) are less saturated.
- Basedash's BI Bench shows that even a vendor-run test is being taken seriously because nothing else exists; BOW could run the same style but with disclosed questions and reproducible harness to outrank it on credibility.

## Key Question 2 — How do general coding agents perform (or get evaluated) on SQL / data-analysis / dashboard tasks?

### Takeaway
There is no standardized, independent benchmark of Claude Code / Codex / Cursor / Gemini CLI / Devin / Windsurf on data work. The measured evidence that exists is: (a) a handful of raw coding-agent leaderboard entries (Claude Code Agent + Sonnet at 61.2 on Spider 2.0-Lite; "Claude Code and Gemini" at 98.94% on DABstep hard; "Code Agent" GPT-5.5 at 79.37%), (b) vendor-run head-to-heads where a raw coding agent is the loser (Databricks 52.4% / 32.1% / 32%) or a strong contender (Basedash: Codex 90.9%, Claude Code 78.0%), (c) a Microsoft ISE study where GitHub Copilot CLI + Claude Sonnet 4.5 went 66.7%→80.8% with domain hints, and (d) a StepFun model-paper "Data Analysis Benchmark run inside Claude Code" (Opus 4.5 45.0). Qualitative failure modes are well documented: invented columns/joins, silent empty joins, metric ambiguity, non-reproducibility across sessions, and not reading docs.

### Cited Findings

**Leaderboard entries by raw coding agents**
- Spider 2.0-Lite: "Claude Code Agent + Sonnet" (Nodal Data) scores **61.2**, vs top Lite entry 76.23 (Tencent Tianqiong) and specialized agents in the 73–75 range; no Codex or Cursor entries listed. Spider 2.0 release baselines: o1-preview 17.1%, GPT-4o 10.1% (vs 86.6% on Spider 1.0). **[measured, public leaderboard, undated]** — [spider2-sql.github.io](https://spider2-sql.github.io/)
- DABstep (snapshot 2026-08-26): "Claude code and Gemini" (gemini-2.5-pro + claude 4.5) **98.94% hard / 100% easy**; "Clalude code and gemini" (Claude Opus 4.5) 98.94%; "VeigaPunk-GPT5-CodeAgent" 100%; Anonymous "Code Agent2" (GPT-5.5) 79.37%. These are personal submissions with unknown scaffolding. **[measured, public leaderboard]** — [benchmarklist DABstep](https://benchmarklist.com/benchmarks/dabstep/)
- DABstep launch (2025-02-04): 450+ tasks from Adyen payments data (payments.csv 138k rows, fees.json, manual.md); launch hard-set scores o3-mini 16%, DeepSeek R1 13%, Claude 3.5 Sonnet 12%, DeepSeek V3 6%; humans average 62% on Easy after 3+ hours; "None of the tasks can be solved with 1-shot of code"; reference hard solution is a 220-line program. Most residual failures were business-logic errors. Question count not stated. **[measured, methodology described]** — [Microsoft ISE blog](https://devblogs.microsoft.com/ise/llm-sql-query-generation/)

**Model-paper "Data Analysis Benchmark inside Claude Code"**

**Documented failure modes of raw coding agents / LLMs on data work**
- Practitioner (Towards AI): with Claude Code and no context, "the SQL queries were generating errors, and Claude Code had no context on what the correct tables to reference were, what the columns meant or what the values meant"; also needs an MCP SQL server to reach the DB at all. — [Towards AI](https://pub.towardsai.net/claude-code-as-a-data-analyst-from-zero-to-first-report-0aa55539a19f)
- HockeyStack (production coding-agent infra): agents "hallucinated join keys" (assumed `company_id` where one dataset used `account_domain`); ~4% of sessions still produce empty results from failed joins; "correct Python that operated on wrong assumptions." — [HockeyStack](https://www.hockeystack.com/applied-ai/we-broke-every-part-of-our-coding-agent-infrastructure-on-the-way-to-1m-sessions-a-day)
- DataSage paper: string-vs-datetime join returned empty set → misleading "no impact" conclusion; generated code lacks type checks/exception handling. — [arXiv 2511.14299](https://arxiv.org/pdf/2511.14299)
- Google's Karl Weinmeister "Six failures of text-to-SQL": schema hallucination; "giving the LLM 100 irrelevant tables to find the 2 relevant ones just drowns it in noise"; recommends a schema-fetch tool over static dumps. — [dev.to](https://dev.to/kweinmeister/the-six-failures-of-text-to-sql-and-how-to-fix-them-with-agents-1n0a)
- "Beyond Document Retrieval" (arXiv 2608.19235): a mature warehouse holds hundreds of plausible fields for one concept ("active users" — fraud included? lookback?); "there is often exactly one correct answer... and no compiler or test suite waiting to flag a wrong result." — [arXiv 2608.19235](https://arxiv.org/pdf/2608.19235)
- Querio (vendor): without scoped schema/metadata, ChatGPT and Claude "can invent columns and produce bad joins"; Claude "can choose different tables or logic from one session to the next without a persistent semantic layer"; metric drift across sessions. — [Querio](https://querio.ai/articles/chatgpt-vs-claude-vs-gemini-data-analysis-2026-benchmark)
- Gemini CLI has an official BigQuery Data Analytics extension that writes/runs SQL from NL; no accuracy numbers published. — [Google Cloud docs](https://cloud.google.com/bigquery/docs/develop-with-gemini-cli?hl=es)
- OpenAI Codex "as a data analyst" writeups (June 2026) describe MCP connections to Databricks etc.; no benchmark numbers. — [taxheal writeup](https://www.taxheal.com/?p=133259)

### Inferences
- The two most-cited "harness beats coding agent" numbers (Databricks 52.4% and 32.1%) are vendor-internal with anonymized baselines; the one semi-independent run that names the agents (Basedash) shows Codex and Claude Code *beating most BI products*. BOW's eval should expect raw coding agents with DB access to be strong, not weak, and the differentiation to appear on governance, reproducibility, latency/cost, and hard business-logic questions rather than on simple SQL.
- The Microsoft ISE result (Copilot CLI + Sonnet 4.5: 66.7% → 80.8% with hints; Agent Framework 38.5% without query execution) is the best public template for an ablation ladder: raw agent → + schema metadata → + domain instructions → + execution → + learned feedback. It also shows feedback loops producing the single largest jump (+19.3 pts), directly relevant to BOW's self-improving instruction loop.
- Supabase's finding that Claude Code reads docs <40% of the time even when skills are loaded is strong, citable evidence that "pointing a coding agent at docs" is not equivalent to a harness that *injects* context.

### Gaps
- No benchmark of Cursor, Devin, Windsurf, or Gemini CLI on data tasks was found at all.
- The Step 3.5 Flash Appendix E.3.1 table (Opus 4.5 = 45.0 etc.) could not be read from the primary PDF/HTML; it is reported only via a search summary.
- Supabase Evals' live leaderboard (supabase.com/evals) and GitHub repo were not fetched; SQL-category pass rates per agent are not in the blog post.
- Dashboard-building (as opposed to SQL/analysis) has no benchmark anywhere in the sources found.

## Key Question 3 — Evidence that context / instructions / semantic layer improves accuracy

### Takeaway
There is consistent, quantified evidence from four independent-ish sources that structured context moves text-to-SQL accuracy by 10–60 points: dbt Labs (open repo, 2026-04-07) shows a 25–50 pp semantic-layer advantage on unmodeled schemas and 90.0→98.2 / 84.1→100 on a modeled project; BIRD's own evidence ablation shows ~20 pp from per-question hints; Microsoft ISE shows 9.5→69.2→88.5 for Genie as metadata, instructions and feedback are added; Snowflake (via Atlan) reports 57→78 on BIRD from adding a semantic model. Caveat: dbt, Snowflake, Databricks, Atlan, Denodo and TextQL all sell context layers.

### Cited Findings
- **dbt Labs 2026 benchmark** (Jason Ganz & Benoit Perigaud, 2026-04-07; repo public): ACME Insurance dataset (data.world), 11 questions × 20 runs, 4 configs (text-to-SQL raw schema / minimal SL / modeled SL / text-to-SQL on modeled data), models Opus 4.6, Sonnet 4.6, GPT-5.3 Codex, GPT-5.2 across reasoning levels. Headline (modeled project): Sonnet 4.6 **text-to-SQL 90.0% vs Semantic Layer 98.2%**; GPT-5.3 Codex **84.1% vs 100.0%**. On the unmodeled schema, SL advantage ranged **24.7–50.0 pp** (e.g., gpt-5.3-codex none: SL 100 vs T2S 50). Raw text-to-SQL overall improved from 32.7% (GPT-4, Nov 2023) to 64.5% (Sonnet 4.6 / GPT-5.3 Codex, 2026); SL from 60.5% to 72.7% (0% on "too many hops" questions — SL refuses rather than guesses). Reasoning effort barely mattered; Sonnet 4.6 beat Opus 4.6 on SL. Caveat from authors: text-to-SQL was given the **entire schema**, "isn't practical for larger datasets." **[measured, open code]** — [dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026); repo [dbt-labs/dbt-llm-sl-bench](https://github.com/dbt-labs/dbt-llm-sl-bench); data [dbt-labs.github.io/dbt-llm-sl-bench](https://dbt-labs.github.io/dbt-llm-sl-bench/)
- **BIRD external-knowledge ablation**: GPT-4 execution accuracy with curated evidence hints 54.89% vs **34.88% without** (one secondary source), or 60.77% vs 40.20% (another) — ~20 pp either way; humans 90.27% vs 70.36%. Evidence = short per-question hints like "account.type = 'OWNER' means the account holder is the primary owner." **[measured, secondary reporting of BIRD paper]** — [beancount research log](https://beancount.io/bean-labs/research-logs/2026/06/06/bird-benchmark-text-to-sql-real-database-gap); [dev.to](https://dev.to/fastovetsilya/llms-for-text-to-sql-problems-the-benchmark-vs-real-world-performance-2064); BIRD paper [arXiv 2305.03111](https://arxiv.org/pdf/2305.03111)
- **Microsoft ISE (2026-05-07)**: Genie 9.50% (no metadata) → 69.23% (column descriptions + domain instructions) → 88.50% (+ stored SQL patterns/joins from feedback); Copilot CLI + Sonnet 4.5 66.70% → 80.77% with domain hints; Agent Framework 55.60% → 76.92% via hints, clarification tool, revised instructions; 38.46% without query execution. **[measured]** — [Microsoft ISE](https://devblogs.microsoft.com/ise/llm-sql-query-generation/)
- **Snowflake Cortex Analyst**: Atlan (July 2026) reports Snowflake's BIRD run showing the same LLM going **57% → 78%** by adding a semantic model; Snowflake's own blog claims "90%+ SQL accuracy" with semantic model and ~2x GPT-4o single-prompt (~51%). I could not find the 57/78 figure on a Snowflake page. **[vendor-internal / secondhand]** — [Atlan](https://atlan.com/know/snowflake/cortex-analyst-vs-text-to-sql/); [Snowflake eng blog](https://snowflake.com/en/engineering-blog/cortex-analyst-text-to-sql-accuracy-bi)
- **Databricks**: Genie accuracy "around 50% before the ontology context was added" vs 84.5% after (per Pebblous reading of Databricks); Databricks says only that Ontology "significantly improves agent performance" with no published ablation. **[vendor-internal]** — [Pebblous](https://blog.pebblous.ai/blog/databricks-genie-one-governed-data/en/); [Databricks](https://www.databricks.com/blog/introducing-genie-one-genie-ontology-and-genie-agents)
- **Google/Querio**: "Gemini + Looker: 66% reduction in text-to-SQL errors compared with direct generation" (quoted by Querio, attributed to Google). **[vendor claim, secondhand]** — [Querio](https://querio.ai/articles/chatgpt-vs-claude-vs-gemini-data-analysis-2026-benchmark)
- **Hex**: "the performance of agents in Hex is more a function of the rich context stores they access" than prompts/models; evals test whether the agent used the right of five "revenue" definitions via workspace guides/semantic models. **[qualitative]** — [Hex](https://hex.tech/blog/evaluate-data-agents/)
- **Counter-evidence (small n)**: 2024 study with Vanna + 3 local LLMs on 6 questions found detailed schema *reduced* accuracy (context overload), esp. Llama3. — [IDEAS/RePEc](https://ideas.repec.org/a/ers/journl/vxxviiy2024ispecialbp426-438.html)
- **Denodo** study extends BIRD/Spider to selecting the right tables among thousands (not tested by standard benchmarks); numeric results not in retrieved text. — [Denodo blog](https://www.datamanagementblog.com/improving-the-accuracy-of-llm-based-text-to-sql-generation-with-a-semantic-layer-in-the-denodo-platform/)
- **AtScale** launched a public NLQ leaderboard on TPC-DS scored by question/schema complexity. — [AtScale](https://atscale.com/?p=24081)
- Unsourced marketing figures to avoid citing as fact: "semantic layer takes text-to-SQL from ~40% to ~90%" (Udemy course listing); Atlan's "closes 8–16 points" and "60–70% DIY plateau" (attributed to Reddit). — [Udemy](https://www.udemy.com/course/agent-ready-data-platform-mcp/); [Atlan](https://atlan.com/know/ai-agent/data-for-ai/text-to-sql-for-enterprise/)

### Inferences
- The dbt study is the most citable because the repo, dataset, and per-run data are public; its design (same model, same questions, ±context) is exactly the "BOW harness vs raw agent on same DB" design, and it already includes GPT-5.3 Codex and Claude Sonnet/Opus 4.6, so BOW can borrow its question set and extend it.
- Across sources the biggest single lever is *domain/business definitions* (BIRD evidence, ISE "domain hints", Hex "five revenue definitions"), not raw schema; the second biggest is *learned corrections* (ISE +19.3 pp). Both map to BOW's instruction store and self-improving loop.
- Expect the "refuse vs guess" trade-off to appear: dbt's SL scored 0% on out-of-scope questions by design. An eval should separate "wrong answer" from "declined to answer."

### Gaps
- No controlled study found isolating *few-shot golden queries* vs *prose instructions* vs *metric definitions* as separate factors; ISE comes closest (hints vs clarification tool vs revised instructions) but doesn't give n.
- Snowflake's 57→78 BIRD figure was not found on a Snowflake-owned page.
- Denodo's numeric results not retrieved.

## Key Question 4 — MCP-based evaluation: do MCP benchmarks involve database/analytics tools?

### Takeaway
Five MCP benchmarks exist (MCP-Universe, MCPMark, MCP-Atlas, LiveMCPBench, MCP-Bench) plus ModelScope's MCPBench; only MCPMark (Postgres environment), MCP-Atlas (a "databases" category among 36 servers), MCP-Universe (financial-analysis domain, not SQL) and ModelScope MCPBench ("Database Query" servers seeded with SQL-Eval samples) touch databases. None evaluates analytics/BI MCP servers or dashboard-building, and top scores remain low (MCPMark top pass@1 52.56%, pass^4 33.86%).

### Cited Findings
- **MCPMark** (arXiv 2509.24002, submitted 2025-09-28): 127 tasks across Notion, GitHub, Filesystem, **Postgres**, Playwright; top model gpt-5-medium **52.56% pass@1, 33.86% pass^4**; claude-sonnet-4 and o3 below 30% pass@1 and 15% pass^4; avg 16.2 turns / 17.4 tool calls per task; tasks emphasize CRUD-rich interactions. Leaderboard trackers disagree on current top (BenchLM: Kimi K2.7 Code 81.1%; benchmarklist: 92.9% as of 2026-06-12). — [arXiv 2509.24002](https://arxiv.org/abs/2509.24002); [BenchLM](https://benchlm.ai/benchmarks/mcpMarkVerified); [benchmarklist](https://benchmarklist.com/benchmarks/mcpmark_verified/)
- **MCP-Universe** (arXiv 2508.14704): 231 tasks, 6 domains (Location Navigation, Repository Management, **Financial Analysis**, 3D Design, Browser Automation, Web Searching), 11 MCP servers; no database domain. — [arXiv 2508.14704](https://arxiv.org/abs/2508.14704v1)
- **MCP-Atlas** (Scale AI, arXiv 2602.00933): 1,000 manually verified tasks across 36 servers / 220 tools, claims-based grading instead of holistic LLM-judge; leaderboard summary lists categories "search, code execution, **databases**, APIs, and productivity tools" (307 tools / 500 prompts in that version; Gemini 2.5 Pro default judge; pass threshold 0.75). SQL-specific task details not retrieved. — [arXiv 2602.00933](https://arxiv.org/pdf/2602.00933); [Steel leaderboard](https://leaderboard.steel.dev/registry/benchmarks/mcp-atlas)
- **LiveMCPBench** (arXiv 2508.01780): large MCP toolset for everyday tasks; MCP-Atlas critiques it and MCP-Bench for holistic LLM-as-judge style bias. No DB focus found. — [arXiv 2508.01780](https://arxiv.org/pdf/2508.01780)
- **ModelScope MCPBench**: evaluates MCP *servers* in three types — Web Search, **Database Query**, GAIA; DB datasets use synthetic data and samples from Defog's SQL-Eval; measures task accuracy, latency, token consumption under identical LLM/agent configs. — [modelscope/MCPBench README](https://cdn.jsdelivr.net/gh/modelscope/MCPBench@main/README.md)
- Supabase Evals runs coding agents with the Supabase MCP server and skills (see KQ2) and found Codex agents read docs ~4x more than Claude Code. — [Supabase](https://supabase.com/blog/supabase-evals)
- Databricks' Genie Code baseline reportedly was "a leading coding agent paired with the Databricks MCP server" (32.1%). — [iThome](https://www.ithome.com.tw/news/174454)

### Inferences
- No existing MCP benchmark measures an *analytics* MCP server (semantic layer, governed metrics, dashboards). A BOW eval that pits "Claude Code + BOW MCP gateway" against "Claude Code + plain Postgres MCP server" on the same questions would be the first public artifact of its kind that I could find.
- MCPMark's pass^4 metric (all 4 runs pass) is a ready-made way to report BOW's reproducibility advantage; ModelScope MCPBench's latency/token accounting is a template for cost reporting.

### Gaps
- Per-environment (Postgres-only) scores for MCPMark were not in the abstract page; need the paper body or GitHub.
- MCP-Atlas database-category task content and per-category scores not retrieved.
- MCP-Bench primary documentation not found; only cited secondhand via MCP-Atlas.

## Key Question 5 — Evidence on self-improving loops / automatic instruction optimization

### Takeaway
Peer-reviewed results exist for context/prompt self-optimization (GEPA at ICLR 2026: +6 pp avg over GRPO, up to +19–20 pp, 35x fewer rollouts; ACE at ICLR 2026: +10.6% on AppWorld, +8.6% on finance, large latency/rollout reductions vs GEPA/Dynamic Cheatsheet), plus an applied text-to-SQL data point (Microsoft ISE: stored corrected SQL patterns lifted Genie 69.23→88.50) and Databricks' ALHF (4–32 feedback records quadruple answer quality on docs QA). None is specifically a text-to-SQL self-improving instruction loop with public numbers.

### Cited Findings
- **GEPA** (Reflective Prompt Evolution; ICLR 2026 poster; arXiv 2507.19457): v2 abstract "Across six tasks, GEPA outperforms GRPO by 6% on average and by up to 20%, while using up to 35x fewer rollouts"; ICLR version states "6 percentage points on average and by up to 19pp"; v1 (July 2025, four tasks) had claimed 10% avg. Base models include Qwen3 8B and GPT-4.1 Mini. — [alphaxiv v2](https://www.alphaxiv.org/abs/2507.19457v2); [ICLR 2026 poster](https://iclr.cc/virtual/2026/poster/10009493); [arXiv PDF](https://arxiv.org/pdf/2507.19457v2)
- **ACE — Agentic Context Engineering** (Stanford/SambaNova/Berkeley; arXiv 2510.04618; submitted 2025-10-06, v3 2026-03-29, ICLR 2026): Generator/Reflector/Curator maintain an itemized "playbook" with incremental edits to avoid "brevity bias" and "context collapse"; **+10.6% on agent benchmarks (AppWorld), +8.6% on finance (FiNER/Formula)**; ACE 59.5% on AppWorld, matching the top public leaderboard entry (IBM-CUGA on GPT-4.1) with open-source DeepSeek-V3.1; vs GEPA "reduced adaptation latency by up to 86.9% and rollouts by more than 75%" (InfoQ); works without labels using execution feedback. One documented failure of a prior method: Dynamic Cheatsheet context collapsed from 18,282 tokens to 122 in one step. No text-to-SQL task included. — [arXiv 2510.04618](https://arxiv.org/abs/2510.04618); [InfoQ](https://infoq.com/news/2025/10/agentic-context-eng); [VentureBeat](https://venturebeat.com/ai/ace-prevents-context-collapse-with-evolving-playbooks-for-self-improving-ai)
- Independent ACE replication: a 2026 Chalmers master's thesis applied ACE to a threat-intelligence search agent; best variant without ground truth achieved +15.1 pp pass@1. — [Chalmers ODR](https://odr.chalmers.se/bitstreams/2f2b058e-6ca8-48f5-b192-1046d03f5deb/download)
- **Microsoft ISE applied text-to-SQL**: "Feedback mechanism storing SQL patterns and joins from 3 iterations" raised Genie from 69.23% to **88.50%** (+19.27 pts), the highest score in the study; authors note the loop was "largely manual." — [Microsoft ISE](https://devblogs.microsoft.com/ise/llm-sql-query-generation/)
- **Databricks ALHF** (Agent Learning from Human Feedback): on DatabricksDocsQA, answer quality rises "with as few as 4 feedback records" and "with just 32 feedback records, we more than quadruple the answer quality over the static baselines"; mechanism stores natural-language feedback and retrieves/injects it. Document QA, not SQL. Databricks' Genie docs state benchmarks are "for evaluation only — Genie does not use benchmark questions or SQL to improve its context"; Genie Code "updates its internal instructions automatically based on past interactions." — [Databricks ALHF case study](https://www.databricks.com/blog/agent-learning-human-feedback-alhf-databricks-knowledge-assistant-case-study); [Genie Agents concepts](https://docs.databricks.com/aws/en/genie-agents/concepts); [W&B explainer](https://wandb.ai/site/articles/training-ai-agents-with-alhf/)
- **Hex**: Evals product exists to "test context changes before they ship" via a sandboxed "Context Preview"; Hex frames its moat as a "context flywheel" but publishes no before/after numbers. — [Hex Evals](https://hex.tech/blog/evals/); [Hex evaluate-data-agents](https://hex.tech/blog/evaluate-data-agents/)
- **Supabase**: rewriting a skill's *description* alone raised activation from ~10% to 60% of sessions — evidence that instruction wording, not just content, is a tunable variable. — [Supabase Evals](https://supabase.com/blog/supabase-evals)
- **GenEdit** (arXiv 2503.21602, "Compounding Operators and Continuous Improvement to Tackle Text-to-SQL in the Enterprise") appeared in search as a text-to-SQL continuous-improvement paper; contents not retrieved. — [arXiv 2503.21602](https://arxiv.org/pdf/2503.21602)

### Inferences
- A BOW launch can cite GEPA/ACE as the academic basis for "instructions that evolve from execution feedback," and the ISE +19.3 pp and ALHF 4–32-record results as evidence that *few* corrections matter. The honest framing is that no public, reproducible number exists yet for a self-improving text-to-SQL instruction loop — which is an opening for BOW to publish one (e.g., accuracy after 0 / 10 / 50 feedback events on a fixed held-out set).
- ACE's "context collapse" finding argues for an itemized, append-mostly instruction store with curation rather than LLM-rewritten monolithic instructions; worth stating as a design principle in the eval write-up.

### Gaps
- No paper or post found that measures a self-improving instruction loop specifically on text-to-SQL/analytics with public data; GenEdit (arXiv 2503.21602) may, but was not read.
- Exact GEPA-vs-ACE per-task numbers were not extracted cleanly (chart text garbled); consult the ACE paper tables.
- No Anthropic or OpenAI first-party post on "evals-driven improvement loops" with numbers was found in this pass (Anthropic's finance posts give only internal deltas).
