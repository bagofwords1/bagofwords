# Glassbox yields replay links, not APIs

A second, much deeper pass still found **no public endpoint, auth scheme, schema or MCP tool list for reading data out of Glassbox**, but it changed what can be built without one. Glassbox's own web-detector and mobile SDK code, read from its anonymously readable Artifactory, reveals the console's replay deep-link formats and a `field:value` session-search grammar, the session identifiers customers already propagate into their own systems, and the full client-side event and struggle taxonomy ([Glassbox Artifactory, React Native package](https://glassbox.jfrog.io/artifactory/api/npm/glassbox-npm/@glassbox/react-native-storyboard/-/@glassbox/react-native-storyboard-7.3280.0.tgz)). That makes one route buildable today on verified facts: query the customer's warehouse or log platform for a Glassbox session-ID column through connectors Bag of Words already ships, and teach the agent, through an instruction and with no code, to construct replay links. The Glassbox MCP Server, announced 29 July 2026, remains a press release with no technical documentation three and a half months later; if it turns out to be a remote HTTP endpoint with a conventional auth mode, it works through the repo's generic MCP tile with zero code, and a branded preset is a four-file change with one structural snag, the per-tenant URL ([PR Newswire](https://www.prnewswire.com/news-releases/glassbox-turns-digital-experience-into-real-time-digital-operational-intelligence-for-enterprise-ai-302837278.html)). The Custom API route is a no-code probe that is viable only if the gated REST API uses a static credential or authorization-code OAuth, and a native connector remains unspecifiable. The recommended sequence is stitching guidance now, the generic MCP tile and a Custom API probe against the first real tenant, a branded preset once the tool list is known, and a native connector only if the REST API proves to return row-level data the MCP Server withholds. Everything past the first phase is gated on material that only Glassbox or a licensed customer can supply, listed at the end.

This report supersedes the earlier "Glassbox analytics integration research" report and stands alone; corrections to that report are stated in the final section. Statements carry one of four labels. **Verified** means read directly in a primary artifact, page or repo file on 2026-11-17. **Snippet-level** means seen only in a search-result summary or through a page the tools could not open. **Inference** means reasoning from verified facts. **Unknown** means searched for and not found, or gated. A string recovered from compiled SDK code is verified as a literal; how the code fills its placeholders is inference unless stated. Repo references are paths relative to `/home/user/bagofwords`. No Glassbox or customer host was contacted, and nothing in the repo was run.

## The capture plane is now mapped; the read plane is still dark

The headline absence is firmer than before. Glassbox's Artifactory was crawled in full: 15 repositories, 5,973 files, and **no PDF, OpenAPI file, Postman collection, server tool, API client or admin CLI** among them (verified; [Glassbox Artifactory](https://glassbox.jfrog.io/artifactory/api/repositories)). A grep of every unpacked artifact and binary for `/api/`, `/rest`, `swagger`, `Authorization`, `Bearer` and `apikey` found one hit only: an `x-api-key` header in a shell script that uploads iOS crash symbols to a signed S3 URL ([GlassboxAnalytics pod](https://glassbox.jfrog.io/artifactory/Glassbox-Pods/GlassboxAnalytics/7.3280.0/GlassboxAnalytics.tar.gz)). Roughly 34 GitHub code-search queries for server-side paths, deployment manifests and component names returned nothing relevant ([GitHub code search](https://github.com/search?q=%22webinterface%2Fapi%22+glassbox&type=code)). The help centre remains login-gated, the web archive was blocked in the research environment, and no leaked guide surfaced. The only public code that extracts data from Glassbox is still a Selenium scraper, now seen in more detail: it opens each session in a customer's console and reads three panels, GIA insights, an "Expert View" of client events (title, URL, duration, events) and a "Server View" of requests (time, URL, status, total time in milliseconds) (verified; [Sagewatch scraper](https://github.com/harapriya1704/Sagewatch_final/blob/HEAD/glassbox_scraper.py)). The console therefore serves that data over internal HTTP calls under its web root, but none is visible publicly, and building against undocumented console calls is not a supportable route (inference).

### Hostnames and tenant structure

Glassbox separates a **report host** (ingest and SDK configuration) from a **console host** (the analyst UI). Mobile SDKs send everything to one customer-specific report URL under a `/thickclient/` path family: report, configuration and key endpoints each take the application ID, with an optional tenant prefix giving the shape `<reportUrl>/[<cuid>/]thickclient/report/<appId>` (verified literals; [Android SDK AAR](https://glassbox.jfrog.io/artifactory/Glassbox-Android-Sdk/com/clarisite/mobile/android/glassbox/7.3280.0/glassbox-7.3280.0.aar)). The application ID is a GUID validated by a strict regular expression, and the iOS public header documents `cuid` as a "Multi Tenant cuid, 8 characters string" ([iOS xcframework](https://glassbox.jfrog.io/artifactory/glassbox-kmp-plugin/com/clarisite/mobile/ios/glassbox-xcframework/7.3280.0/glassbox-xcframework-7.3280.0.zip)). The addressing scheme is thus one report host per tenant or environment, an 8-character tenant code on multi-tenant clusters, and one GUID per application; that single-tenant and on-premises URLs omit the `cuid` segment is inference. Observed host patterns are `report.<tenant>.gbqofs.io` and `report.<tenant>.glassboxdigital.io` for ingest, `cdn.gbqofs.com/<tenant>/` and `cdn2.gbqofs.com/<tenant>/` for the web tag, and `console.<tenant>.glassboxdigital.io` or a customer-owned hostname, sometimes on port 8443, for the console ([CCS buyer UI template](https://github.com/Crown-Commercial-Service/ccs-scale-cat-buyer-ui/blob/HEAD/src/main/views/template.njk), [C3PA dataset page](https://github.com/MaazBinMusa/C3PA_Dataset/blob/HEAD/Htmls/WS/82.html), [Sagewatch config](https://github.com/harapriya1704/Sagewatch_2/blob/HEAD/config.yml)). The console application root is `/webinterface/webui/`, confirmed by the SDK's sample remote configuration, where the only server-side pointer is an integrations entry whose domain is the console's sessions URL ([React Native package](https://glassbox.jfrog.io/artifactory/api/npm/glassbox-npm/@glassbox/react-native-storyboard/-/@glassbox/react-native-storyboard-7.3280.0.tgz)).

The capture plane authenticates with application identity, not user credentials: cookies carrying the session and app IDs, custom `X-Glassbox-*` headers, and an anti-tamper challenge. The configuration endpoint needs only identifiers that ship inside every customer app (verified literals; the conclusion that it is unauthenticated is inference). It is not a place a connector should read analytics from, and it returns capture settings, not data. The sample configuration also carries a customer ID and a session-quota mechanism, which indicates per-customer session-volume licensing enforced server-side (inference).

### Console replay deep links and search syntax

The most useful recovery is that the web detector's public API builds console links itself, so the formats below come from vendor code and not from a single customer page. All are verified as strings; the binding of the mobile form's first placeholder to the console sessions URL is inferred from adjacent literals and the sample configuration.

| Form | Shape | Evidence |
|---|---|---|
| Web, by attribute and absolute window | `https://<console>/webinterface/webui/#/sessions/<attr>:<value>/replay?from=<epoch ms>&till=<epoch ms>`; attribute defaults to `cls_s`, value to the current session ID, window to now minus and plus 22 hours | Vendor detector `getSessionReplayLink` ([RN package](https://glassbox.jfrog.io/artifactory/api/npm/glassbox-npm/@glassbox/react-native-storyboard/-/@glassbox/react-native-storyboard-7.3280.0.tgz)); independently in a U-Haul page using minus 22 h to plus 2 h ([C3PA dataset](https://github.com/MaazBinMusa/C3PA_Dataset/blob/HEAD/Htmls/WS/82.html)) |
| Web, multiple attributes | Same path with the query `cls_s:<sessionId> AND <key>:<value> ...` | Vendor detector `getSessionReplayLinkByMultipleAttributes` |
| Web, short link | `https://<console>/s/<attr>:<value without dashes>/<time bucket>` or `https://<console>/s/<sessionId without dashes>/<time bucket>`, the bucket being the window start divided by 100,000 | Vendor detector, short option |
| Mobile, by integration ID | `<console sessions URL>/integration_id:<integrationId>/replay?timeframe=month_1` | String constant in Android and iOS binaries ([Android AAR](https://glassbox.jfrog.io/artifactory/Glassbox-Android-Sdk/com/clarisite/mobile/android/glassbox/7.3280.0/glassbox-7.3280.0.aar)) |
| By internal session ID | `https://<console>/webinterface/webui/sessions/<32 hex>/replay/mobile?sessionStartTime=<epoch ms>&source_node=0` | One published incident page ([incident page](https://github.com/llatin10/llatin10.github.io/blob/HEAD/production-issues-insights.html)) |

Three conclusions follow, all inference. The console's session search accepts a **field-prefixed query language with `AND`**, with at least `cls_s` (web session cookie) and `integration_id` (mobile) as searchable keys and either an absolute `from`/`till` window or a relative `timeframe`. The short form implies a redirect service on the console host. And a time window is part of the lookup, which a reviewer corroborates by describing entering a session ID "along with the proper timing to minimize search duration" ([AWS Marketplace reviews](https://aws.amazon.com/marketplace/reviews/reviews-list/B09ZVL2TQB?page=18)). Whether the same query grammar is accepted by any REST endpoint is unknown. The vendor's marketing names further search keys without syntax: user ID, browser, Struggle Score, customer-defined attributes and free text over any captured value ([Glassbox session replay](https://glassbox.com/platform/session-replay)). Replay links almost certainly require a Glassbox login with tenant access, since sharing is framed as "with colleagues" and reviewers ask to share outside the tool (inference); link expiry and permission rules are unknown.

### Session identifiers and how customers already carry them

Four identifiers matter for joining. On the web, the session is the **`_cls_s` cookie** and the visitor is the `_cls_v` cookie with a five-year default expiry; both are verified in the detector configuration, in a tag-debugging extension that parses Glassbox beacons, and in customer scripts that read the cookie ([RN package](https://glassbox.jfrog.io/artifactory/api/npm/glassbox-npm/@glassbox/react-native-storyboard/-/@glassbox/react-native-storyboard-7.3280.0.tgz), [Omnibug provider](https://github.com/MisterPhilip/omnibug/blob/HEAD/src/providers/Glassbox.js), [JS dataset](https://github.com/Nun0Alv3s/JS_DATASET/blob/HEAD/files/web_20904.js)). The browser also exposes the value as `_detector.sessionId`. On mobile, every platform SDK exposes a session ID, an **integration ID** described as usable "for crashlytics integration for example", and a `generateSessionLink` function; an `integrationTokens` call returns the app ID, session ID, session link and report URL for Crashlytics and AppsFlyer ([iOS xcframework](https://glassbox.jfrog.io/artifactory/glassbox-kmp-plugin/com/clarisite/mobile/ios/glassbox-xcframework/7.3280.0/glassbox-xcframework-7.3280.0.zip), [Capacitor plugin](https://glassbox.jfrog.io/artifactory/api/npm/glassbox-npm/@glassbox/capacitor-plugin/-/@glassbox/capacitor-plugin-7.3280.0.tgz)). Hybrid apps bridge the two worlds through a `gbSessionId` hand-off into webviews. User identity is an optional startup `identity` plus arbitrary user properties sent with session events; how the server stitches users across sessions and devices is unknown.

Public code shows customers pushing these identifiers outward in at least four ways, all verified: into New Relic as `GlassboxSessionId` and `GlassboxSessionReplay` attributes on JavaScript error events ([New Relic quickstart](https://github.com/newrelic/newrelic-quickstarts/blob/main/dashboards/glassbox/dashboard.json)); into Google Tag Manager's data layer and a home-built replay link for chat agents ([C3PA dataset](https://github.com/MaazBinMusa/C3PA_Dataset/blob/HEAD/Htmls/WS/82.html)); into a CRM form field named `glassboxSessionId` ([JS dataset](https://github.com/Nun0Alv3s/JS_DATASET/blob/HEAD/files/web_20904.js)); and into a customer's own back-end request header, which lands the ID in server logs ([reverse-engineering notes](https://github.com/FezVrasta/ha-unipolsai/blob/HEAD/docs/FINDINGS.md)). Partner integrations follow the same pattern or push data into Glassbox from the browser; Kameleoon and VWO call detector methods, Survicate adds a "Glassbox URL" column to exports, Blue Triangle shows a per-session Glassbox link, and none exposes a server-to-server Glassbox endpoint or credential ([Kameleoon source](https://github.com/Kameleoon-new/custom-analytics-integrations/blob/HEAD/glassbox/glassbox.js), [VWO](https://vwo.com/integrations/glassbox/), [Survicate help](https://help.survicate.com/en/articles/3942551-glassbox-integration), [Blue Triangle help](https://help.bluetriangle.com/help-center/blue-triangle-and-glassbox)). Glassbox's roughly twenty-five named integrations include no BI tool, warehouse or customer data platform ([Glassbox integrations](https://www.glassbox.com/platform/integrations/)). The session ID is the practical join key, and it usually lives in the customer's systems already.

### Product modules, metrics and limits

The public module list is twelve named modules: Customer Journey Analytics, Mobile App Analytics, Session Replay, Performance Analytics, Product Analytics, Interaction Maps and Heatmaps, Glassbox Accessibility, Rapid Response, Glassbox Insights Assistant (GIA), Funnel Analysis, Struggle and Error Analysis, and Voice of the Silent ([Glassbox blog navigation](https://www.glassbox.com/blog/feature-matrix/)). The metrics a customer will expect an AI analyst to speak about are these. The **Struggle Score** is proprietary, built from "more than 30" frustration behaviours, usable as a filter across modules, with no published formula ([Struggle and error analysis](https://glassbox.com/platform/struggle-error-analysis)); its 0-to-1 scale is snippet-level ([Glassbox struggle analysis blog](https://www.glassbox.com/blog/struggle-analysis/)). The **Experience Score** is customer-configured per behaviour ([Struggle and experience scores](https://glassbox.com/blog/struggle-and-experience-scores)). Journeys carry conversions, drop-offs, struggles, errors and customer-configured revenue metrics, filterable by "over 25 standard dimensions" that are not listed ([Customer journey analytics](https://glassbox.com/platform/customer-journey-analytics)). Funnels come in ad-hoc, retroactive and monitored forms with conversion, abandonment, revenue impact and affected-user counts ([Funnel analysis](https://glassbox.com/platform/funnel-analysis)). Interaction maps give per-element click rate, focus time, errors, struggles and revenue impact ([Interaction Maps blog](https://www.glassbox.com/blog/glassbox-interaction-maps/)). Product analytics, sold as the CX Engage add-on, provides DAU, WAU, MAU and their ratios, adoption and conversion by segment, and a cross-session User Timeline, retained 13 months; no public page shows retention curves or cohorts, so it should be read as engagement and adoption by segment and not as a Mixpanel equivalent ([User Insights blog](https://glassbox.com/blog/user-insights), [Product analytics](https://glassbox.com/platform/product-analytics/)). Revenue figures depend on tenant configuration and are not comparable across tenants (inference).

Analysis objects such as attributes, actions, goals and business flows are defined after capture and apply retroactively, which reviewers confirm ([Tagless data capture](https://glassbox.com/platform/tagless-data-capture), [Software Finder reviews](https://softwarefinder.com/analytics-software/glassbox/reviews?page=2)). Reporting is the product's weak area by reviewer account: a Wells Fargo reviewer in July 2026 cites caps on dashboard widgets, days of data and table rows, others cite slow-loading sessions and reports, and 2023 reviews cite an 8-day report range and 30-day session storage ([AWS Marketplace reviews](https://aws.amazon.com/marketplace/reviews/reviews-list/B09ZVL2TQB?page=18), [Software Finder reviews](https://softwarefinder.com/analytics-software/glassbox/reviews?page=2)). Current numeric caps are unknown. Plan-bound retention is short: session replay one to three months and analysis data one to thirteen months ([Glassbox pricing](https://www.glassbox.com/platform/plans-pricing/)), with policy-driven longer retention for sessions placed in Session Vault ([Digital record keeping](https://glassbox.com/platform/digital-record-keeping)). No API-based route can backfill long history. Deployment is multi-tenant cloud, single-tenant cloud on AWS or Azure, or on-premises, with granular role-based access, a full audit log and SAML 2.0 single sign-on; API users, service accounts and IP restrictions are mentioned nowhere public ([Glassbox data privacy and security](https://glassbox.com/platform/data-privacy-security)).

## The MCP Server is still a press release

Three and a half months after launch, the only primary source on the Glassbox MCP Server is the 29 July 2026 release. It says Glassbox Pulse is an "AI-powered operational intelligence engine" that "applies machine learning first" to surface "only the issues that require attention", answers natural-language questions with evidence spanning customer behaviour, journey impact, errors, network logs and server-side failures, and that the MCP Server gives enterprise AI systems "governed access" to this context "without ingesting a raw stream of digital journey data" ([PR Newswire](https://www.prnewswire.com/news-releases/glassbox-turns-digital-experience-into-real-time-digital-operational-intelligence-for-enterprise-ai-302837278.html)). The release contains no availability wording, named AI client, auth detail, example question, sample output, price or deployment statement (verified by reading). As of 17 November 2026, glassbox.com's platform navigation, AI page, GIA page and pricing page do not mention Pulse or the MCP Server ([Glassbox platform](https://www.glassbox.com/platform/), [Glassbox pricing](https://www.glassbox.com/platform/plans-pricing/)). Every press article found is a rewrite of the release; a competitor notes there are "no public demos or customer proof points" ([Quantum Metric blog](https://www.quantummetric.com/blog/glassbox-alternatives)). No registry or directory lists the server, and every "glassbox" MCP project found belongs to an unrelated publisher; the directories were covered by web search and one partial directory tool, so this is "not found", not "confirmed absent". Endpoint, transport, authentication, tools, limits, supported clients, licensing, on-premises availability and masking behaviour over MCP are all unknown.

Context around it is firmer. Glassbox's acquisition of the anomaly-detection company Anodot on 4 November 2025 and Guy Perry's appointment as CEO in October 2025 are confirmed on Glassbox's own news pages ([Glassbox news, Anodot](https://glassbox.com/news/glassbox-anodot-acquisition/), [Glassbox news, CEO](https://www.glassbox.com/news/glassbox-names-new-ceo/)). That Pulse is built on Anodot's engine is inference from timing and matching descriptions; no Glassbox source says so. GIA is built on Microsoft's Azure OpenAI Service and has no documented API ([Glassbox Insights Assistant](https://www.glassbox.com/platform/glassbox-insights-assistant/)), and in September 2026 Glassbox earned a Microsoft certified-software designation for financial-services AI ([Channel Insider](https://www.channelinsider.com/channel-business/glassbox-earns-new-designation-in-microsoft-ai-cloud-partner-program/)). Whether GIA, Pulse or the MCP Server run on on-premises deployments is unstated. The lack of any product page, pricing row or docs link suggests the server is sold through direct account engagement, possibly in limited availability (inference).

Competitors show the likely shape. Fullstory's developer documentation, read directly, describes OAuth by default with an API-key alternative, an admin toggle without which the server connects with zero tools, and named clients including Claude and Cursor ([Fullstory developer docs](https://developer.fullstory.com/mcp/introduction/)). Quantum Metric's product page describes saved and ad hoc analytics queries, session summaries, replay links, funnels and alerts under the user's existing permissions ([Quantum Metric MCP](https://www.quantummetric.com/platform/mcp)). Snippet-level listings for Contentsquare, Amplitude, Mixpanel, PostHog, Pendo and LogRocket converge on the same pattern: a hosted streamable-HTTP endpoint, OAuth browser sign-in inheriting user permissions, often a service-account or key alternative, regional hosts, and tools that return tabular aggregates as well as session evidence ([Mixpanel docs](https://docs.mixpanel.com/docs/mcp), [PostHog docs](https://posthog.com/docs/model-context-protocol)). Microsoft Clarity is the outlier with a local process ([Clarity MCP mirror](https://glama.ai/mcp/servers/@microsoft/clarity-mcp-server)). The benchmark expectation for Glassbox is therefore a remote HTTP endpoint with OAuth sitting in front of SAML single sign-on, most likely per tenant or per region given single-tenant and on-premises deployments, with a findings-first tool surface narrower than its peers. All of that is inference, and it argues for runtime tool discovery over any hard-coded assumption.

## Five routes, each blocked by a different fact

The routes deliver different products and depend on different unknowns. The repo findings below are verified against the working tree unless marked; Glassbox is mentioned nowhere in the repo's code.

| Route | What the agent gets | Repo work | What blocks it |
|---|---|---|---|
| Stitching plus replay links via instructions | Session IDs and clickable Glassbox links beside the customer's own data | None; an instruction and a docs recipe | Whether the customer stores session IDs anywhere queryable; the customer's console host |
| Warehouse or data-lake landing via Glassbox Data Export | Glassbox session attributes and events as ordinary tables | None | Whether the customer licenses the export; its schema and destination are unknown |
| Generic MCP tile | Whatever tools the Glassbox server lists | None | Server URL, transport and auth unknown; unsupported if stdio or exotic auth |
| Branded Glassbox MCP preset | Same, with a catalog tile and pre-filled form | Four edits, plus a form change if the URL is per tenant | Same as above, plus the per-tenant URL mismatch |

### Stitching and warehouse landing work on connectors that already exist

Snowflake, BigQuery, Databricks SQL, Redshift, Athena, ClickHouse, Elasticsearch, Azure Data Explorer, PostgreSQL and Splunk are all registered connection types (`backend/app/schemas/data_source_registry.py:783`, `:810`, `:1778`, `:1455`, `:844`, `:1272`, `:1215`, `:1330`, `:646`, `:1237`). A customer whose warehouse or log platform holds a Glassbox session ID, whether from a data-layer push, a CRM field, back-end request logs, survey exports or a licensed Data Export feed, can query it today. New Relic, Adobe Analytics, Datadog and Dynatrace have no connector, and Google Analytics has a client file but no registry entry, so the one third-party tool with a verified Glassbox attribute, New Relic, is reachable only through a generic MCP or Custom API connection that was not verified.

Teaching the agent the link pattern needs no code. The instruction system supports free-text instructions scoped to an organization or agent, loaded always or retrieved by keyword, and attachable to a specific table and column (`backend/app/models/instruction.py:66-98`, `backend/app/models/instruction_reference.py:7-15`, `backend/app/ai/context/builders/instruction_context_builder.py:53-66`). An instruction naming the session-ID column, the customer's console host and the appropriate link form from the table above lets generated SQL or pandas emit a replay-URL column. Two repo details were not traced and should be checked before this is documented as a recipe: whether instruction text reaches the code-generation prompt or only the planner, and whether report tables render a URL column as a clickable link. The link forms are now verified from vendor code, but which identifier a given customer stores (web cookie, mobile session ID or integration ID) decides which form applies, and the window parameters require a timestamp column near the session time.

This route's limit is unchanged: without Data Export it returns pointers to Glassbox, not Glassbox's behavioural data. With Data Export landing in a warehouse it becomes the strongest route of all, since the data arrives as tables under the customer's own governance with no Glassbox API dependency, but nothing about that feed can be designed for until a customer shows its schema.

### The generic MCP tile needs zero code if the server is conventional

The repo's MCP client supports exactly two transports, SSE and streamable HTTP; stdio is "planned for later" and any other value raises an error (`backend/app/data_sources/clients/mcp_client.py:254-259`, `:812-831`). The generic `mcp` type offers six auth variants: none, bearer token, API-key header, basic, an admin-configured OAuth client, and per-user OAuth through dynamic client registration (`backend/app/schemas/data_source_registry.py:2786-2815`). OAuth is always per user, with tokens stored encrypted per user and refreshed near expiry, and the redirect URI derives from the deployment's configured base URL (`backend/app/routes/connection_oauth.py:224`, `backend/app/services/connection_oauth_service.py:1182-1233`). OAuth client-credentials is not offered; a machine-to-machine setup would have to use a static bearer token (inference from the variant list). If Glassbox's server is remote HTTP with one of these modes, an administrator connects it today through the "MCP Server" tile.

What happens next is well defined. Tools are discovered through `tools/list`, stored per connection with an enable flag and a policy, and exposed to the model as native tools, the first 50 per run by default with the rest reachable through search (`backend/app/data_sources/clients/mcp_client.py:317-358`, `backend/app/ai/tools/mcp_tool_registry.py:11-16`). A tool the server marks read-only starts on "allow"; any other, including one with no annotations, starts on "ask", so a Glassbox server that omits read-only hints prompts for approval on every call until an admin changes the policy (`backend/app/data_sources/clients/mcp_client.py:91-101`). Every successful call saves the full result to a session file; a tabular JSON result can be charted and joined in pandas with a warehouse query in a single data-creation step, while a prose result can be quoted but not charted (`backend/app/ai/tools/implementations/execute_mcp.py:499-522`, `backend/app/ai/tools/schemas/create_data.py:51-75`). Generated Python can never call the connection itself, result pagination is left to the model, and a result over five million characters is saved raw (`backend/app/data_sources/clients/mcp_client.py:12-22`). The value of this route therefore turns on one Glassbox fact: whether tools return structured records or only Pulse narratives.

Reachability is a network question more than a code one. Egress for MCP uses an IP policy, not a host allow-list: private and loopback hosts are allowed by default and refused only when `security.block_private_outbound` is on, with no per-host exception (`backend/app/core/egress.py:167-177`, `backend/app/settings/bow_config.py:403`). A self-hosted Bag of Words reaches an on-premises Glassbox by default; a hosted instance reaches only what the customer's firewall admits. TLS options for servers behind a private certificate authority were not found in the MCP configuration and were not searched for elsewhere.

### A branded preset is four edits plus one structural snag

A preset is one literal in the preset list that always resolves to the generic `mcp` type, carrying branding and form defaults only (`backend/app/schemas/data_source_registry.py:489-521`, `:3017-3131`). The repo's skill states it needs "no client, no config/credentials schema, no per-type tests, no new dispatch sites" (`.agents/skills/add-connection-type/SKILL.md:101-108`). The minimum is the registry entry, an icon file, one line in the icon map (`frontend/components/DataSourceIcon.vue:89-103`), and assertions in the presets unit test (`backend/tests/unit/test_mcp_presets.py`); convention adds a README row, changelog and version bump, a feedback-loop document and screenshots. No locale keys are needed, since title and description come from the registry. None of the existing tests asserts a total preset count, so an addition breaks nothing; that is from reading the assertions, not from a test run. Eleven presets exist, all with a fixed vendor URL and streamable HTTP, and none is an analytics vendor.

The snag is the URL. The preset model holds a single fixed `server_url`. The form lets a user overwrite it under "Advanced", but both the form in edit mode and the backend recognise a preset by **exact URL match**, so a tenant-specific Glassbox URL loses its brand icon and auth gating after save (`frontend/components/MCPConnectionForm.vue:532-546`, `backend/app/services/data_source_service.py:36-58`). The backend already honours a `catalog_key` in the saved configuration, but the form never writes one (`frontend/components/MCPConnectionForm.vue:649`, `:690`). If Glassbox serves MCP per tenant, a useful preset requires a small, unscoped frontend change to persist and read that key, with the UI evidence the repo mandates. If Glassbox requires an auth mode outside the six, the size reference is the commit pair that added basic auth: about 360 lines across 14 files. A preset's sample tool list should be filled from a live `tools/list`, as the HubSpot precedent insists: "discovered names, not guesses" (`docs/feedback-loops/hubspot-mcp-preset.md`).

### Custom API is a probe, bounded by auth and pagination

The Custom API type turns an admin-typed base URL, static headers and endpoint definitions into tools that run through the same execution path as MCP tools (`backend/app/schemas/data_source_registry.py:2884-2929`). It supports none, bearer, basic, API-key header and per-user authorization-code OAuth. It has **no OpenAPI import, no pagination loop, no retry or rate-limit back-off, no response shaping and no table catalog**, and it cannot do OAuth client-credentials, cookie-session login or request signing (`backend/app/data_sources/clients/custom_api_client.py:431-511`). Endpoint timeouts cap at 120 seconds, and a POST used for searching defaults to "ask" unless the admin overrides it (`:65-67`, `:128-133`). A customer holding the gated API reference could wire up a few endpoints against their console host with no Bag of Words release, provided the auth fits; paginated endpoints work only by exposing the cursor to the model, at one model turn per page. Because there is no catalog, the endpoint descriptions the admin writes are the entire semantic layer. A pre-filled Custom API preset is possible in principle and has the same fixed-URL problem as an MCP preset, on top of requiring the endpoints to be known. This route's real value is as the cheapest way to see actual Glassbox payloads before committing to anything larger.

### A native connector remains feasible in shape only

The contract a client must satisfy is small: a description, a connection test, schema discovery, a prompt-schema rendering and a query method returning a dataframe (`backend/app/data_sources/clients/base.py:165-188`). The repo offers two archetypes: pass a vendor query language through, as PostHog does with HogQL, or declare a static catalog of virtual tables and translate a JSON query spec into paged calls, as CrowdStrike does (`backend/app/data_sources/clients/posthog_client.py:246-263`, `backend/app/data_sources/clients/crowdstrike_client.py:66-110`). The tenant host belongs in a recognised URL field so the egress check sees it (`backend/app/core/egress.py:718-764`). Real scope, measured by CrowdStrike's introducing commit, is a client of about 750 lines, schema and registry edits, unit and integration tests, a vendor API simulator, a feedback-loop document, an icon and evidence, plus two enforcement tests that fail until updated (`backend/tests/unit/test_connector_egress.py:269-272`, `backend/tests/unit/test_query_params.py:567-612`). The second pass adds a vocabulary for what the virtual tables would be called, sessions, page or screen views, interactions, struggles, errors and crashes, network calls, custom events, survey responses, but not one endpoint to fill them from. ClickHouse in the backend makes a report-execution or query endpoint plausible and nothing more. A simulator built without customer documentation would encode invention. This route is justified only if the REST API returns row-level data the MCP Server withholds and customers want an indexed, schedulable catalog or access from generated code, which neither tool route provides.

## A phased sequence that spends nothing until a tenant exists

**Phase 0, now, no Glassbox access.** Publish stitching guidance: a recipe for connecting the warehouse or log platform that holds session IDs, and an instruction template covering the three link families and their identifiers. Before publishing, close the two repo gaps noted above (instruction reach into code generation, clickable URL cells). This phase rests entirely on verified facts and existing connectors. In parallel, open the access channel: a design-partner customer and a Glassbox partner or sales contact, with the question list below.

**Phase 1, first real tenant.** Three zero-code probes, run together. Connect the Glassbox MCP Server through the generic MCP tile and capture the live tool list, annotations, result shapes and sizes. If the customer can share the API reference, define two or three read endpoints through Custom API and inspect real payloads. Ask whether the customer licenses Data Export and, if so, connect the landing store and read its schema. Each probe answers a decision question the others cannot: narrative or records, static credential or not, tables already landed or not. Choose a multi-tenant SaaS customer for speed if one is available, while recognising that results will not transfer automatically to on-premises banks.

**Phase 2, once the MCP facts are known.** Ship a branded preset if the server is remote HTTP with a supported auth mode: four edits if the URL is global, plus the `catalog_key` form change if it is per tenant. If the endpoint is per tenant and the form change is not wanted, ship a documentation recipe on the generic tile instead. If the server is stdio-only or uses unsupported auth, this phase becomes platform work and should be re-scoped.

**Phase 3, conditional.** Build a native connector only if Phase 1 shows a REST read API with row-level data, an auth or paging model Custom API cannot serve, and customer demand for indexed tables or scheduled queries. Select the archetype from what the API actually exposes, and build the simulator from the customer-supplied reference. If instead Data Export proves common among customers, invest in documented schemas and instructions for that feed, which costs no connector at all.

The steelman for building the native connector first is that it alone gives Bag of Words ownership of the catalog and makes its agent, not Pulse, the analyst. That argument is sound and currently unactionable: there is nothing to call.

### Corrections to the earlier report

The earlier report's central conclusions hold: nothing public describes the read API or the MCP Server, and stitching is the only route with verified mechanics. Seven specifics change. First, the replay deep link is no longer "verified from a single public example"; three further forms are verified from Glassbox's own SDK code, along with a search grammar the earlier report did not know. Second, the earlier statement that no named bulk-export product was found is superseded: "Glassbox Data Export" is a named capability and a vendor case study confirms real-time streaming to a customer data lake, though details remain unknown. Third, the Medallia `_cls_s` mapping cited earlier is not on Medallia's current page, which now says only to contact support ([Medallia docs](https://docs.medallia.com/medallia-digital-feedback/medallia-digital-web/analytics-solution/session-recording-software/glassbox)); the underlying fact that `_cls_s` is the web session cookie is now verified independently. Fourth, the Anodot acquisition and CEO change, previously snippet-level, are confirmed on Glassbox's site. Fifth, the SDK release note needs precision: 7.3280.0 of 5 November 2026 is the highest version, but a 7.3278.1 patch was published on 9 November 2026 ([Glassbox Artifactory](https://glassbox.jfrog.io/artifactory/Glassbox-Android-Sdk/com/clarisite/mobile/android/glassbox/7.3278.1/)). Sixth, the open repo question on per-tenant preset URLs is answered: the URL is editable, but exact-match recognition breaks branding unless the form is changed to persist a catalog key. Seventh, the earlier description of four preset auth modes understates the generic MCP type, which offers six variants, and a preset needs an icon-map line in addition to the icon; the earlier list of stitching-capable connectors (Snowflake, BigQuery, Splunk) extends to ten registered types. The earlier statement that the event taxonomy and identifier formats are unknown now applies only to the server side.

## Conclusion

The deep dive moved the boundary between what needs Glassbox's cooperation and what does not. Glassbox's client code documents, in effect, the one integration contract the vendor has always supported: an identifier and a console link handed to other systems. Bag of Words can honour that contract today with instructions alone, and in accounts that license Data Export the same warehouse connection carries the behavioural data too, which makes the customer's data estate, not Glassbox's API, the most promising integration surface. That reframes the native connector from the default ambition to a last resort.

The MCP question is now narrower than it looked. The repo side is solved to the point of a checklist, and the decision reduces to three facts from a live server: where it lives, how it authenticates, and whether its tools return records or prose. A single session against a real tenant through the generic tile answers all three, so the scarce resource is not engineering time but a design partner. Choosing that partner deliberately matters, because Glassbox's regulated, often self-hosted customer base means the first tenant that is easy to reach is not representative of the tenants that matter most.
