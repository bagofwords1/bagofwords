# PBIRS hides its engine; query SSAS instead

No Power BI Report Server (PBIRS) API executes DAX, and the Analysis Services engine PBIRS embeds is a loopback-only, unsupported process, so the bagofwords connector cannot run live DAX against a .pbix hosted on PBIRS through any sanctioned route. The complete PBIRS REST v2.0 specification (143 paths) contains **zero occurrences of "dax", "export", "pbix", "executequer" or "xmla"**, and the only data-returning actions (`Model.GetData`, `/Data`, `Model.GetAggregatedValue`) belong to the shared paginated-report `DataSets` entity, never to `PowerBIReports` ([SwaggerHub PBIRS 2.0](https://api.swaggerhub.com/apis/microsoft-rs/PBIRS/2.0)). The embedded engine listens on `localhost:5132`, which Microsoft documents solely for SQL Profiler tracing; its `Port` and `PrivateProcess` settings are rewritten on every launch, models are evicted after 60 idle minutes, and a Microsoft-affiliated poster states "You cannot connect to that from other machines and you cannot deploy custom models to that instance" ([Microsoft Learn](https://learn.microsoft.com/en-us/power-bi/report-server/scheduled-refresh-troubleshoot); [Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Is-SSAS-service-included-in-Power-BI-Report-Server-on-premise/m-p/1959739/highlight/true)). The sanctioned alternative is Microsoft's own recommendation: host the model in standalone SQL Server Analysis Services, have the PBIRS report live-connect to it, and query SSAS over XMLA through IIS `msmdpump.dll`, which a Linux/Python backend can do today with Basic-over-TLS or NTLM/Kerberos plus `EffectiveUserName` for row-level security, reusing the existing `XmlaClient`/`AnalysisServicesClient` code. Meanwhile the current download-and-parse path is worse than the codebase assumes: Microsoft states explicitly that a downloaded .pbix is "the original file you uploaded" and server refreshes are not reflected in it, pbixray shipped silent-wrong-value bugs on large tables as recently as August 2026, RLS roles are extracted as metadata but never enforced, and DirectQuery/live reports yield no data at all. The decision-ready verdict is: fix the REST misuse now, build an SSAS/XMLA path as the only honest "live DAX" story, and stop implying that the PBIX cache reflects current server data or respects RLS.

## No PBIRS API runs DAX, and the embedded engine is a loopback diagnostic port

The absence of a query path is not an oversight in the connector; it is structural to the product. The PBIRS swagger describes itself as "programmatic access to the report server catalog" and lists its only Power BI additions since 2017 as `DataModelParameters` (October 2020) and `DataModelRoles`/`DataModelRoleAssignments` (January 2019) ([SwaggerHub PBIRS 2.0](https://api.swaggerhub.com/apis/microsoft-rs/PBIRS/2.0)). The full `/PowerBIReports` tree is 16 paths: CRUD, `AllowedActions`, `CacheRefreshPlans`, `Comments`, `Content/$value`, `DataModelParameters`, `DataModelRoleAssignments`, `DataModelRoles`, `DataSources`, `Model.CheckDataSourceConnection`, `Model.Upload`, `Policies`, `Properties`. There is no query, execute, export or data sub-resource, and the Microsoft Learn operation list matches exactly ([Learn: Power BI Reports operations](https://learn.microsoft.com/en-us/rest/api/power-bi-report/power-bi-reports)). The SOAP surface (`ReportService2010`, `ReportExecution2005`) is equally silent: `Render` only maps to paginated rendering extensions (CSV, PDF, XML, EXCEL and so on) and applies to .rdl items ([Learn: ReportExecutionService.Render](https://learn.microsoft.com/en-us/dotnet/api/reportexecution2005.reportexecutionservice.render?view=sqlserver-2016)). The cloud `executeQueries` DAX endpoint and `ExportTo` live at `api.powerbi.com` and have no PBIRS counterpart ([Learn: Reports - Export To File](https://learn.microsoft.com/en-us/rest/api/power-bi/reports/export-to-file)). The one caveat on epistemics: no Microsoft page says "DAX execution is unsupported on PBIRS" in those words; the conclusion rests on exhaustive absence from the spec, on the data-sources matrix that marks "Power BI dataset in Power BI Report Server" as unsupported for cached, scheduled-refresh and live use alike ([Learn: data sources](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)), and on repeated community statements that PBIRS "does not expose an XMLA endpoint" ([Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Retrieving-report-content-from-API-or-tables-associated-from/td-p/3994850)).

The embedded engine is real but deliberately private. Official documentation confirms that "an Analysis Services process will be running with Power BI Report Server" and that it is launched from `<install>\PBIRS\ASEngine\workspaces`, with `msmdsrv.ini` there "rewritten whenever the Analysis Services process launches" ([Learn: scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/scheduled-refresh); [Learn: troubleshoot scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/scheduled-refresh-troubleshoot)). The same page lists `ConfigurationSettings\Port` and `ConfigurationSettings\PrivateProcess` among settings that are "reset when ever the Analysis Services process is launched. Any changes you make to these are ignored", and gives `localhost:5132` as the server name for a Profiler trace, the only client connection Microsoft documents. `PrivateProcess` is the same mechanism Power BI Desktop and Power Pivot use to make their engines private, so the inference that the listener is intended for local use only is strong, though no source demonstrates whether it binds to 127.0.0.1 or merely relies on the "remote connections are not allowed by default" behaviour that one community thread reports ([Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Is-SSAS-service-included-in-Power-BI-Report-Server-on-premise/td-p/754288)). Microsoft's general position compounds this: "External tools aren't supported in Power BI Desktop for Power BI Report Server" ([Learn: External tools](https://learn.microsoft.com/en-us/power-bi/transform-model/desktop-external-tools)).

Even a local, unsupported connection would be operationally hostile. The engine is a cache, not the system of record: the model is streamed from the ReportServer catalog database on first view or refresh (ExecutionLog `ASModelStream`), and the report server, not SSAS, evicts it after `ModelExpirationMinutes` (**default 60**), checked every `ModelCleanupCycleMinutes` (**default 15**) ([Learn: troubleshoot scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/scheduled-refresh-troubleshoot)). Because loading is driven by `RSPowerBI.exe` through the Tabular Object Model (`AnalysisServicesServer.RefreshDatabase`, `TOMWrapper.RefreshModel` appear in official log excerpts), an external DAX query cannot trigger a load; if nobody has opened the report in the last hour, there is no database to query. Databases carry GUID names with no documented mapping back to a report. Putting `msmdpump.dll` in front of `localhost:5132` is conceivable, since the pump's target is just a `<ServerName>host:port</ServerName>` string, but Microsoft scopes the pump page to standalone SQL Server Analysis Services, the pump binaries ship only with an SSAS install, and the research found zero blog posts or threads of anyone attempting it against PBIRS ([Learn: Configure HTTP Access](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)). The honest grading is: REST/SOAP live DAX, impossible; embedded engine over TCP, undocumented hack that is local-only, GUID-addressed, eviction-prone and breaks on upgrade (msmdsrv.ini "settings reset when you upgrade the report server"); msmdpump against the embedded engine, untested by anyone, unsupported by Microsoft.

## SSAS live connection plus msmdpump is the sanctioned route, and Python on Linux can drive it

Microsoft's guidance for anything that needs a reusable, queryable on-premises model is unambiguous: "we recommend hosting the model in an Analysis Services instance and using a live connection to the model in the report" ([Learn: scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/scheduled-refresh)). PBIRS officially supports Power BI reports with a live connection to SQL Server Analysis Services (cached, scheduled refresh and live all marked supported) and to Azure Analysis Services, with Windows, username/password and integrated authentication options ([Learn: data sources](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)). A Power BI team member summarised the on-prem position as "the only option currently for an on-prem solution is to install an Analysis Services server and host your model there, then you could connect your pbix file in live connect mode" (community snippet, Microsoft-affiliated) ([Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Connect-to-PBI-model-in-PBIRS/m-p/911467/highlight/true)). In this topology the .pbix on PBIRS holds only layout and a connection string; every measure and every row lives in SSAS, which is XMLA-native, supports roles and RLS, and is reachable from SSMS, DAX Studio and Tabular Editor with standard, supported tooling. Distributed deployments need Kerberos constrained delegation for "as the user viewing the report" identity flow, with SPNs `HTTP/<host>` for the report server and `MSOLAPSvc.3/<host>` for SSAS ([Learn: Configure Kerberos](https://learn.microsoft.com/en-us/power-bi/report-server/configure-kerberos-powerbi-reports)).

For a Linux backend, the only Microsoft-documented transport is XMLA/SOAP over HTTP(S) through IIS `msmdpump.dll`. Microsoft gives this as a design reason for the pump: "Client applications can't use the Analysis Services client libraries (for example, a Java application running on a UNIX server). If you can't use the Analysis Services client libraries for data access, you can use SOAP and XML/A over a direct HTTP connection" ([Learn: Configure HTTP Access](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)). Direct TCP on port 2383 is closed to Linux: the official client-library page states "TCP based connectivity is supported for Windows computers only" for ADOMD.NET Core, and a real user hit `System.NotSupportedException: This feature is supported for a .NET Core client only on Windows systems` from Linux; DAX Studio's author replied that on-prem server\instance connections "require Windows authentication - which is not available on Linux" and suggested the HTTP pump with Basic auth ([Learn: client libraries](https://learn.microsoft.com/en-us/analysis-services/client-libraries); [Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/233745/can-adomd-net-core-connect-to-an-ssas-endpoint-fro)). No open-source implementation of the SSAS TCP protocol exists, and commercial Linux drivers (CData ODBC/JDBC) are themselves HTTP clients to `msmdpump.dll` ([CData](https://www.cdata.com/kb/tech/ssas-odbc-python-linux.rst)). The Python library landscape is bleak: `xmla` is Python 2 from 2013 with an archived repo, `pyadomd` is a Windows pythonnet wrapper with unresolved .NET Core requests and open issues through 2025, and `pymsasdax` needs the Windows-only MSOLAP COM provider ([xmla on PyPI](https://pypi.org/project/xmla/); [Pyadomd issues](https://github.com/S-C-O-U-T/Pyadomd/issues)). This is exactly why bagofwords' hand-rolled `XmlaClient` (SOAP `Discover`/`Execute`, `Format=Tabular`, `_xHHHH_` decoding) is the right foundation rather than a liability.

Authentication is where the current `XmlaClient` falls short, and the gap is well defined. The pump supports "Windows authentication (Kerberos or NTLM); Basic authentication; Anonymous authentication", and Microsoft warns that Anonymous, when enabled, is "always used first" ([Learn: Configure HTTP Access](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)). Under Basic, "IIS will try to impersonate the user using the provided credentials when connecting to MSMDPUMP, but the credentials won't be delegated to Analysis Services"; the credentials must be a Windows domain account. Two hardening facts change the deployment checklist: **starting with SQL Server Analysis Services 2025, HTTP connections through msmdpump.dll are disabled by default** and must use HTTPS unless `<RequireSecureChannel>false</RequireSecureChannel>` is set for test environments, and the client libraries require TLS 1.2 minimum ([Learn: Configure HTTP Access](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0); [Learn: client libraries](https://learn.microsoft.com/en-us/analysis-services/client-libraries)). For Windows Integrated auth from Python, `requests-ntlm` 1.3.0 (June 2024, built on `pyspnego`) and `requests-kerberos` 0.15.0 (June 2024, with `principal`+`password` TGT acquisition and `delegate=True`) are maintained ([requests-ntlm](https://pypi.org/project/requests-ntlm/); [requests-kerberos](https://pypi.org/project/requests-kerberos/)). NTLM authenticates connections rather than requests, so a single `requests.Session` per identity is mandatory and intermediaries without connection pinning produce spurious 401s ([curl #4499](https://curl.haxx.se/bug/?i=4499); [Broadcom KB 444070](https://knowledge.broadcom.com/external/article/444070/ntlm-authentication-fails-with-401-unaut.html)). The PBIRS connector already uses `HttpNtlmAuth` on a shared session, so the pattern is proven in this codebase; it simply has not been wired into `XmlaClient`. Note the gap honestly: no published end-to-end example of Python `requests` plus `requests-ntlm` posting a DAX `Execute` to `msmdpump.dll` was found; the pieces are individually documented but the combination needs lab verification.

Row-level security maps cleanly onto connection properties. `EffectiveUserName` ("For SSAS, specify in a domain\user format. To use this property, the caller must have administrative permissions in Analysis Services") makes the engine evaluate roles as the named user; `Roles` restricts a connection to a comma-delimited role list, with `Roles=' '` meaning no membership; `CustomData` passes a string readable via the `CUSTOMDATA()` DAX function for dynamic security ([Learn: Connection string properties](https://learn.microsoft.com/en-us/analysis-services/instances/connection-string-properties-analysis-services)). Microsoft confirms this works through the pump: with Basic auth, "if you are passing credentials via EffectiveUserName on the connection string, then the application pool identity must have administrator rights on the Analysis Services instance" ([Learn: Configure HTTP Access](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)). The SharePoint precedent describes the same pattern as enabling "per-user identity without the requirement to configure Kerberos delegation" ([Learn: EffectiveUserName in PerformancePoint](https://learn.microsoft.com/en-nz/sharePoint/administration/use-effectiveusername-in-performancepoint-services)). The practical design for bagofwords is therefore a single service identity that is an SSAS server administrator, HTTPS to the pump, and every `Execute` carrying `<PropertyList><Catalog/><Format>Tabular</Format><EffectiveUserName>DOMAIN\enduser</EffectiveUserName></PropertyList>` derived from the signed-in bagofwords user. Two cautions: this concentrates privilege in one highly trusted account, and no source lists `EffectiveUserName`/`Roles`/`CustomData` as XMLA PropertyList element names, since Microsoft documents them as connection-string properties; confirm against `DISCOVER_PROPERTIES` on a live server before relying on it (inference). If IIS and SSAS sit on different hosts and you insist on per-user Windows identity instead, NTLM fails on the second hop and Kerberos constrained delegation becomes mandatory; Microsoft's own advice is that Basic over SSL is "the most common solution" ([Learn: Configure HTTP Access](https://learn.microsoft.com/en-us/analysis-services/instances/configure-http-access-to-analysis-services-on-iis-8-0)).

Response handling has known limits. The XMLA rowset returns every cell as a named element, with invalid XML name characters encoded as `_xHHHH_` and the original name preserved in the schema's `sql:field` attribute; nulls appear as missing elements or `xsi:nil='true'` ([Rowset Data Type (XMLA)](https://learn.microsoft.com/en-us/previous-versions/sql/sql-server-2012/ms187127(v=sql.110))). Binary/XPRESS compression is proprietary to MSOLAP/ADOMD, so a plain SOAP client receives verbose text and should stream-parse and page with `TOPN` plus key filters, since DAX has no `SKIP` (community pattern) ([Fabric Community](https://community.fabric.microsoft.com/t5/Developer/SKIP-Alternative-for-EXECUTE-QUERIES-API-pagination/m-p/3674013/highlight/true)). The only hard server cap Microsoft documents is `MaxIntermediateRowsetSize` (**default 1,000,000 rows**), which chiefly bites DirectQuery models ([Learn: DAX properties](https://learn.microsoft.com/en-us/analysis-services/server-properties/dax-properties)). Tabular metadata should come from `$SYSTEM.TMSCHEMA_*` DMVs (36 of them at compatibility level 1200+) rather than `DISCOVER_CSDL_METADATA` alone, which `AnalysisServicesClient` already partly does ([SQLServerCentral](https://www.sqlservercentral.com/blogs/documenting-your-tabular-or-power-bi-model)).

## Download-and-parse returns stale, unsecured and sometimes silently wrong data

The most consequential finding for the current connector is an official Microsoft statement that invalidates its cache-invalidation design: "You can open and edit Power BI report (.pbix) files from the server, but you get back the original file you uploaded. If the data has been refreshed by the server, the data won't be refreshed when you first open the file" ([Learn: What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)). The refreshed Vertipaq model is persisted, since the refresh status sequence ends with "Saving model to the catalog — the refreshed model is being saved back to the report server catalog database", but it is stored separately from the uploaded blob ([Learn: Configure scheduled refresh](https://learn.microsoft.com/en-us/power-bi/report-server/configure-scheduled-refresh)). Community evidence places it in `dbo.CatalogItemExtendedContent` as a `DataModel` row alongside `CatalogItem` and `PowerBIReportDefinition` rows; a user on the May 2021 build confirmed "the web view shows updated visuals, but the downloaded PBIX is still the old version" and was told "it is not supported to download .pbix file with the latest data" (community snippets) ([Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Visual-updated-in-scheduled-refresh-PBIX-still-old/td-p/2280996); [Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/How-is-data-stored-in-Report-Server-between-scheduled-refreshes/m-p/1454162)). The implication for bagofwords is direct: keying the Parquet cache on the catalog item's `ModifiedDate` is correct for detecting re-uploads, but every scheduled refresh on the server leaves `ModifiedDate` unchanged and the cached data frozen at upload time, so the warm-up job faithfully refreshes stale data. A user who sees different numbers in the PBIRS portal and in bagofwords is seeing a design property, not a bug to patch. Reading the refreshed `DataModel` blob straight from the ReportServer database would in principle fix this (pbixray reads `.abf`), but a Power BI team member warned extracting it "is not supported and could put you data/catalog in a bad state", the schema is officially undocumented, and whether refresh "just overwrites the data blob" is a poster's assumption ([Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/How-Report-server-store-and-run-the-Power-BI-reports/m-p/1709036); [Redgate Simple Talk](https://www.red-gate.com/simple-talk/databases/sql-server/bi-sql-server/insights-from-the-ssrs-database/)).

pbixray is actively maintained (**32 releases, latest 0.15.5 on 27 August 2026**) and explicitly scoped as "a read-only extractor for the data model" that does not evaluate DAX, run a query engine, or parse the report layer ([pbixray on PyPI](https://pypi.org/project/pbixray/#history); [pbixray README](https://github.com/Hugoberry/pbixray)). The 2026 issue stream is the concern: #37 "get_table() silently drops data for tables with >1M rows (multi-segment VertiPaq not supported)" (closed May 2026), #59 "Uncompressed dictionary pages decode their NUL padding as entries, shifting data ids of all later pages (silent wrong values)" (closed August 2026), #53 "String column values misaligned when decoding bit-packed VertiPaq runs (large multi-segment table, >8M rows)" (**still open**), and #64 relationships dropped to legitimate hidden tables (**open, September 2026**) ([pbixray issues](https://github.com/Hugoberry/pbixray/issues?q=is%3Aissue)). Silent misalignment and silent row loss are the worst failure modes for an analytics backend whose output is an LLM-written SQL aggregate: no exception fires, the number is just wrong. Because the PBIX format is "undocumented and reverse-engineered" and each PBIRS release pairs with a new Desktop-for-RS build (2.158 in September 2026), the decoder is perpetually catching up. Memory is a second ceiling: `MaxFileSizeMb` defaults to 1000 MB with a hard 2 GB maximum, and the DataModel is Xpress-compressed, so the parsing host needs several gigabytes of RAM for large models even with 0.15's chunked `iter_table` ([Learn: What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)). The connector's 200 MB download cap therefore silently excludes a slice of legitimate reports rather than protecting correctness.

Row-level security is simply absent on this path. pbixray extracts "row-level security, object-level security, roles, and role memberships" alongside the decoded table contents, which means the role filter expressions are readable text sitting next to the unfiltered data they were meant to constrain ([pbixray README](https://github.com/Hugoberry/pbixray)). PBIRS enforces RLS in the hosted engine at view time, and the January 2019 release introduced it specifically so that administrators can "restrict data access for given users" ([Learn: What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)). A downloaded .pbix bypasses that entirely, and because no offline DAX evaluator exists on any platform (every tool found is a lexer/parser or a client to a Microsoft engine), the connector cannot re-apply the role expressions it can see ([sidemantic-dax](https://pypi.org/project/sidemantic-dax/0.13.0/); [pbi_parsers](https://douglassimonsen.github.io/pbi_parsers/)). The permission model makes this worse: viewing a report with RLS requires only the Browser role's "View reports" task (Read Content, Read Properties), whereas reading a report definition is a Consume/Manage-level task, so the service account bagofwords configures necessarily holds more privilege than the users it serves ([Learn: Item-level tasks](https://learn.microsoft.com/en-us/sql/reporting-services/security/tasks-and-permissions-item-level-tasks)). Whether `Content/$value` specifically demands Read Report Definition could not be confirmed from the official reference (gap), but the direction is clear: the current design hands every bagofwords user the whole model.

The approach also degrades silently for two supported report types. Live-connection .pbix files contain no `DataModel` at all, and pbixray fails with "DataModel not found in the archive" ([pbixray issue #7](https://github.com/Hugoberry/pbixray/issues/7)); DirectQuery files carry metadata and M/native SQL but no Vertipaq rows. PBIRS supports both modes against SQL Server, SSAS, Oracle, PostgreSQL, Teradata, SAP and others ([Learn: data sources](https://learn.microsoft.com/en-us/power-bi/report-server/data-sources)). For live reports, the correct target is the upstream SSAS that the pbix merely points to, discoverable through `/PowerBIReports({id})/DataSources` where `DataModelDataSource.Kind` is `AnalysisServices` and `Type` is `Live` ([SwaggerHub PBIRS 2.0](https://api.swaggerhub.com/apis/microsoft-rs/PBIRS/2.0)). The connector does fetch `/DataSources` today, so the classification data is already in hand; it is not used to branch. Finally, measures remain source text everywhere, and the system prompt's instruction to rewrite DAX as SQL is tractable only for additive SUM/COUNT measures; CALCULATE and filter-context semantics have no faithful SQL translation, and no DAX-to-SQL project surfaced in the research (inference from absence).

## The REST surface the connector misreads or leaves unused

Beyond the big architectural gaps, the research exposes several concrete REST-level defects and omissions that are cheap to fix. The table below separates what the spec actually defines from what the connector does.

| Endpoint or field | What the spec defines | Connector today | Fix |
|---|---|---|---|
| `GET /Reports({id})/Export/{fmt}` | Does not exist; the complete `/Reports` tree (25 paths) has no `Export` | Tried first, then falls back to URL access | Delete the call; go straight to `/ReportServer?{path}&rs:Format=CSV&rc:ExcelMode=false&rc:UseFormattedValues=false&rs:Command=Render` |
| `POST /DataSets({id})/Model.GetData` | Returns JSON `{Name, Columns:[{Name,Type}], Rows:[[string,...]]}`; optional `MaxRows` is a query parameter; body `{Parameters:[{Name,Value}]}` | Parses result as CSV/JSON heuristically; sends `maxRows` in body | Parse the documented shape; coerce types from `Columns[].Type`; move `MaxRows` to the query string |
| `GET /DataSets({id})/Data` | OData feed of rows as open types (PBIRS-only path) | Unused | Simpler alternative to `Model.GetData` for non-parameterised shared datasets |
| `GET /System` → `ProductType` | Enum `PowerBiReportServer` or `SqlServerReportingServices` | Warm-up call made, field ignored | Gate `/PowerBIReports`, `/ExcelWorkbooks`, `/CacheRefreshPlans({id})/History` on it; same client then serves SSRS 2017+ |
| `GET /PowerBIReports({id})/CacheRefreshPlans`, `GET /CacheRefreshPlans({id})` (`LastRunTime`, `LastStatus`), `GET /CacheRefreshPlans({id})/History` (`SubscriptionStatus` Completed/InProgress/Failed, `StartTime`, `EndTime`, `Message`, `Details`), `POST /CacheRefreshPlans({id})/Model.Execute` | All present; `/History` is PBIRS-only | Unused | Surface "server data last refreshed at" next to "cache built from upload at"; drive or detect refreshes |
| `GET /PowerBIReports({id})/DataModelRoleAssignments` | `{GroupUserName, DataModelRoles:[uuid]}` joined to `DataModelRoles` `{ModelRoleId, ModelRoleName}` | `DataModelRoles` fetched, assignments not | Resolve which roles apply to the signed-in user; at minimum warn or block when any role exists |
| `DataModelDataSource.Type` / `.Kind` on `/DataSources` | `Type` ∈ Unknown/Live/DirectQuery/Import; `Kind` ∈ AnalysisServices, SQL, ... | Fetched but not used to branch | Skip the PBIX download for Live/DirectQuery; route Live+AnalysisServices to the SSAS path |
| `$top`, `$skip`, `$filter`, `$count`, `$orderBy`, `$select` | Declared on collection GETs; `$expand` not wired; `$search` absent (use `POST /Folders({id})/Model.SearchItems(searchText='...')`) | Not used | Page large catalogs; filter by `Type eq 'PowerBIReport'`; expect N+1 for sub-resources |
| `POST /PowerBIReports({id})/Model.CheckDataSourceConnection` | Body `DataSourceName`; returns `{IsSuccessful, ErrorMessage}` | Unused | Pre-flight data-source health in the connection test |

All rows derive from the PBIRS 2.0 specification and the Learn reference ([SwaggerHub PBIRS 2.0](https://api.swaggerhub.com/apis/microsoft-rs/PBIRS/2.0); [Learn: Data Sets - Get Data Set Data](https://learn.microsoft.com/en-us/rest/api/power-bi-report/data-sets/get-data-set-data); [Learn: Get Cache Refresh Plan History](https://learn.microsoft.com/en-us/rest/api/power-bi-report/cache-refresh-plans/get-cache-refresh-plan-history)). Two caveats remain gaps: the spec does not enumerate `CacheRefreshPlan.LastStatus` string values (its description text is a copy-paste error) or document server-side paging defaults such as `@odata.nextLink` and maximum `$top`, so paging behaviour must be observed on a real server. The CSV rendering fallback is sound for paginated reports, but note that no `rc:` selector exists for a single data region; multi-region reports flatten into blocks that must be split client-side, and the whole `Render` output is held in memory on the server ([Learn: CSV device information settings](https://learn.microsoft.com/en-us/sql/reporting-services/csv-device-information-settings); [Learn: Export a paginated report to CSV](https://learn.microsoft.com/en-us/sql/reporting-services/report-builder/exporting-to-a-csv-file-report-builder-and-ssrs)). A community suggestion of `api/reports/{id}/data?rs:Format=CSV` appears in no spec and should be ignored ([Fabric Community](https://community.fabric.microsoft.com/t5/Report-Server/Export-all-filtered-data-or-All-visuals-from-Power-BI-Report/m-p/3670232)). The portal's own per-visual export (150K-row .xlsx since October 2020) goes through an undocumented internal endpoint that nobody has published; replaying it would tie the connector to an unversioned private API ([Learn: What's new in PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/whats-new)).

## PBIRS is durable but maintenance-grade, and every competitor stops at the catalog

Investment sizing depends on whether PBIRS has a future and whether anyone has solved this better. On the first point, PBIRS is more strategic in 2026 than it was in 2023. Microsoft states that "Starting with SQL Server 2025, Microsoft is consolidating all on-premises reporting services under Power BI Report Server (PBIRS). No new versions of SQL Server Reporting Services (SSRS) will be released", and that PBIRS "is available for customers running SQL Server 2025 Enterprise and Standard editions" using the same key ([Learn: Reporting Services Consolidation FAQ](https://learn.microsoft.com/en-us/sql/reporting-services/reporting-services-consolidation-faq?view=sql-server-ver17)). After Premium P-SKU retirement, licensing continues via Fabric F64+ reserved instances and SQL Server core licenses, with PBIRS explicitly "not included with any F SKUs under F64" ([Learn: What is PBIRS](https://learn.microsoft.com/en-us/power-bi/report-server/get-started); [Learn: Premium migration overview](https://learn.microsoft.com/en-us/power-bi/support/premium-migration-overview)). The Microsoft Lifecycle page shows "In Support" under the Modern Lifecycle Policy with no retirement date, and the cadence is three releases a year (January, May, September), with **September 2026 v1.27.9770.30560** current ([Microsoft Lifecycle](https://learn.microsoft.com/en-us/lifecycle/products/power-bi-report-server); [Learn: Change log](https://learn.microsoft.com/en-us/power-bi/report-server/changelog)). Standard-edition rights widen the install base, so PBIRS is a durable target for at least the SQL Server 2025 lifecycle.

The character of that investment matters more than its existence. The 2024–2026 changelog is visual roll-ups, security hardening and removal of legacy dependencies: `DisableMSRBConnect`, `EnableRefererValidation`, jQuery upgrades, Office Online Server removal (January 2026), Access Database Engine removal from setup (September 2026), 64-bit-only Desktop, AVX requirement, SCOM management packs unsupported after January 2027 ([Learn: Change log](https://learn.microsoft.com/en-us/power-bi/report-server/changelog); [Microsoft Tech Community](https://techcommunity.microsoft.com/blog/sqlserver/deprecation-announcement-ssrspbirs-and-ssas-management-packs-for-scom/4486497)). No new platform API has appeared since `DataModelParameters` in October 2020. The official comparison page lists composite models, "Host and connect to Power BI shared semantic models", Analyze in Excel, Q&A, preview features and dashboards as unsupported, and has no row at all for XMLA, DAX REST or Copilot ([Learn: Compare PBIRS and the service](https://learn.microsoft.com/en-us/power-bi/report-server/compare-report-server-service)). The JavaScript embedding API is likewise absent; embedding is iframe-only via `?rs:embed=true` plus URL `filter=`, with the JS API request sitting in Fabric Ideas as "under review" (community snippet) ([Learn: Embed a PBIRS report](https://learn.microsoft.com/en-us/power-bi/report-server/quickstart-embed); [Fabric Ideas](https://community.fabric.microsoft.com/t5/Fabric-Ideas/Power-BI-JavaScript-API-support-for-Report-Server/idi-p/4476728)). There is no public roadmap; the inference is that an integrator should not expect server-side query capabilities to arrive, and should plan for the two paths that exist today.

Competitors confirm the ceiling. Every catalog and lineage vendor found reaches PBIRS through REST v2.0 and downloads the .pbix for model internals, and all of them disclaim the result. Talend/Qlik calls the APIs "very limited" and extracts connection names only; Collibra states "there is no technical lineage for the reports"; Alation's separately licensed "Power BI On-Prem" connector gets dimensions and measures from the PBIX files but "DAX expressions are not available" and "Column-level lineage is not available because Microsoft provides no API for the required data source information"; DataHub (Beta) maps datasets and data sources to "N/A" "because of REST API limits"; OpenMetadata/Collate ships a BETA connector ([Talend/Qlik](https://help.qlik.com/talend/en-US/talend-data-catalog/8.0/Content/MIRMicrosoftPowerBIReportServerImport.htm); [Collibra](https://productresources.collibra.com/docs/collibra/latest/Content/CollibraDataLineage/DataSources/SSRS-PBRS/ref_ssrs-pbrs-steps.htm); [Alation](https://docs.alation.com/en/latest/fde/EnhancedConnectors/PBIOnPremOCFConnector/PBIOnPremOCFConnectorOverview.html); [DataHub](https://docs.datahub.com/docs/generated/ingestion/sources/powerbi-report-server)). Microsoft Purview has no PBIRS connector at all. No BI tool, migration product or NL-to-DAX vendor claims to run DAX against a PBIRS-hosted model, and none has built on the embedded engine, which is itself strong evidence that it is not a viable integration surface. Measured against this field, bagofwords' decoding of actual Vertipaq rows into Parquet is already more than any catalog vendor attempts; the problem is not ambition but the claims attached to it.

## Prioritised recommendations: fix, build, and stop claiming

The quick fixes are REST hygiene with immediate correctness payoff and should ship first. Remove the non-existent `/Reports({id})/Export/{fmt}` call and render paginated reports directly via URL access with `rc:ExcelMode=false&rc:UseFormattedValues=false`. Replace the heuristic `Model.GetData` parser with the documented `{Name, Columns, Rows}` JSON shape, coerce types from `Columns[].Type`, and pass `MaxRows` as a query parameter. Read `ProductType` from the `/System` warm-up call you already make and gate PBIRS-only paths on it. Call `/PowerBIReports({id})/CacheRefreshPlans` and `/CacheRefreshPlans({id})/History`, and show users two timestamps for every PBIX-backed source: when the server last refreshed the model (`LastRunTime`/`EndTime`) and when the Parquet cache was built from the uploaded file. Use the `DataModelDataSource.Type` you already fetch to skip downloads for `Live` and `DirectQuery` reports and surface a clear "this report has no embedded data" message instead of a pbixray exception. Fetch `DataModelRoleAssignments` and, until RLS can be enforced, refuse to serve or at least prominently warn on any report whose model defines roles. Add `$filter=Type eq 'PowerBIReport'` and `$top/$skip` paging to the catalog walk. Pin pbixray to a version at or above 0.15.5 and add a regression check on row counts per table against `TMSCHEMA` statistics, since the known failure modes are silent.

The new path is an SSAS/XMLA connector reachable from Linux, and it is the only route that can honestly be called "live DAX". It largely extends code that exists. `XmlaClient` needs pluggable auth (`HTTPBasicAuth`, `HttpNtlmAuth`, `HTTPKerberosAuth`) on a persistent `requests.Session`, HTTPS enforcement to match SSAS 2025's `RequireSecureChannel` default, and `EffectiveUserName`/`Roles`/`CustomData` in the `Execute` PropertyList. `AnalysisServicesClient` should become the target for PBIRS live-connection reports: when `/DataSources` reports `Kind=AnalysisServices, Type=Live`, derive the SSAS server from `ConnectionString`/`ModelConnectionName` and run DAX there with the signed-in user's `DOMAIN\user` as `EffectiveUserName`, which restores engine-enforced RLS and evaluated measures without per-user Windows credentials or Kerberos delegation. Documentation should tell customers with import-mode .pbix files that Microsoft's own recommendation is to publish the model to SSAS Tabular and live-connect the report, and that bagofwords then queries it live; this is the deployment-side half of the feature. Treat the embedded engine on `localhost:5132` as out of scope: it is local-only, GUID-named, evicted after 60 idle minutes, reset on upgrade, unsupported by Microsoft and untouched by every vendor. If a customer ever insists, the only defensible experiment is a Windows-side agent on the PBIRS host, and it should be labelled unsupported in the product.

Several current claims should be withdrawn or reworded. Stop implying the PBIX cache reflects current server data; it reflects the upload, and `ModifiedDate` cannot detect server refreshes. Stop presenting PBIX-backed sources as RLS-aware; the configured service account sees everything and so does every bagofwords user. Stop describing measures as queryable; they are text, and the DAX-to-SQL rewrite instruction to the LLM is reliable only for additive measures. Stop treating the 200 MB cap as a safety limit; it is an arbitrary exclusion below the product's 1 GB default and 2 GB maximum, and the real limit is parser memory. Finally, retire the notion that the PBIRS connector mirrors the cloud `PowerBIClient`'s `executeQueries` blueprint; the honest mirror of that design on-premises is SSAS over XMLA, not PBIRS at all.

## Conclusion

The research reframes the problem: the question was never whether bagofwords missed a PBIRS endpoint for DAX, because none exists and Microsoft has added no platform API since 2020. The real asymmetry is that PBIRS is a report host whose data layer is either a private cache nobody may query or an external SSAS that anyone may. Every architectural choice follows from accepting that split: the download path is a metadata-and-snapshot tool that competitors use only for catalog names, and it should be presented as such, while the SSAS/XMLA path is the one place where "live", "fresh" and "secure" can all be true at once on Linux.

Two uncertainties deserve a lab before any public claim. The combination of Python `requests` with NTLM or Kerberos against `msmdpump.dll` carrying `EffectiveUserName` in the XMLA PropertyList is assembled from individually documented pieces but has no published end-to-end confirmation, and PBIRS's own OData paging and `LastStatus` vocabulary are undocumented. Both are cheap to verify against a test server, and both are far better bets than continuing to invest in decoding a file Microsoft says is already out of date the moment the server refreshes it.
