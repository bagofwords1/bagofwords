# Glassbox hides its API; MCP leads

A Glassbox integration cannot be designed to completion from public sources: **no endpoint path, base URL, auth scheme, pagination rule, rate limit, response schema or MCP tool list for reading Glassbox data is published anywhere on the open web**, and all technical documentation sits behind the customer login at `support.glassbox.com` ([Glassbox integrations](https://glassbox.com/platform/integrations), [support.glassbox.com](https://support.glassbox.com/hc/en-gb/articles/5832981277073-Flutter-Plugin-Installation)). Three routes are nonetheless viable, and they differ sharply in how much they depend on that gated material. The **Glassbox MCP Server**, announced 29 July 2026, is the vendor's stated direction for AI agents and maps onto Bag of Words as a single MCP preset with no client code, but its URL, transport, auth and tools are undisclosed ([Glassbox news](https://www.glassbox.com/news/glassbox-pulse-mcp-server-operational-intelligence/)). A **native REST connector** fits the repo's existing "virtual tables plus JSON query spec" pattern (CrowdStrike is the closest precedent) and is the only route that yields an indexed table catalog, yet every Glassbox-specific design decision in it is currently a guess. **Session-ID stitching through the customer's warehouse** is the only route with publicly verified mechanics (session identifiers and replay links pushed into New Relic, Medallia, Survicate and similar tools) and needs no new connector, but it delivers deep links back to Glassbox, not Glassbox's behavioural data. The practical recommendation is to treat this as a discovery problem before an engineering one: secure a licensed customer or a Glassbox partner contact, obtain the API reference and MCP Server specification, and only then choose between the preset and the native connector. Until then, nothing beyond the stitching route can be built against verified facts.

Throughout this report, statements are labelled **verified** (read directly on a primary source or in the repo on 2026-11-17), **snippet-level** (seen only in a search-result summary, the page itself unread), **inference**, or **unknown**. Repo references are paths relative to `/home/user/bagofwords`.

## Public evidence stops at the login wall

The headline fact is an absence, and it is well corroborated. Glassbox's integrations page advertises an "open API" that integrates "most non-native solutions in just two clicks" but links to no reference, developer portal or specification, only to the Customer Portal ([Glassbox integrations](https://glassbox.com/platform/integrations)). The pricing page lists **"Unlimited API access" on all three plans** without saying what the API does ([Glassbox pricing](https://www.glassbox.com/platform/plans-pricing/)). Anonymous requests to the help centre return HTTP 401 and redirect to a login page ([support.glassbox.com](https://support.glassbox.com/hc/en-gb/articles/5832981277073-Flutter-Plugin-Installation)). The API-catalogue site API Tracker records no docs URL, auth type, OpenAPI file or MCP server for Glassbox ([API Tracker](https://apitracker.io/a/glassbox)). GitHub code search finds no API client, no Singer tap, no Airbyte source, no Terraform provider and no Postman or OpenAPI artefact, and Glassbox has no discoverable public GitHub organisation ([GitHub code search](https://github.com/search?q=%22source-glassbox%22&type=code)). All of this is verified. Whether `docs.glassbox.com` or `developers.glassbox.com` exist is unknown: the research environment got a DNS failure on one attempt and a proxy error on another, which settles nothing.

Two pieces of public evidence cut against the marketing claim that data flows out easily. The only public code that extracts data from Glassbox is **a Selenium script that scrapes the sessions grid of a customer's self-hosted console by XPath**, which suggests at least one enterprise user found no usable API for what they needed (verified; [Sagewatch glassbox_scraper.py](https://github.com/harapriya1704/Sagewatch/blob/HEAD/glassbox_scraper.py)). A Splunk Community thread reports that no option existed to export session events and no documentation for extracting them could be found (snippet-level, date unconfirmed; [Splunk Community](https://community.splunk.com/t5/Monitoring-Splunk/integration-of-splunk-with-glassbox/m-p/660054)). Against that, the vendor-authored AWS Marketplace listing describes an "event streaming pipeline" and "fully automated data pipelines", and a sibling listing mentions integration with "chosen tools or data warehouses", though neither names a single destination, format or cadence ([AWS Marketplace](https://aws.amazon.com/marketplace/pp/prodview-waapo3vlxej2o), [AWS Marketplace B09ZVL2TQB](https://aws.amazon.com/marketplace/pp/B09ZVL2TQB)). The conflict is unresolved. No named bulk-export product, and no Snowflake, BigQuery, Redshift, Databricks, S3, Kafka or webhook destination, was found on any Glassbox page. One caution on the phrase "API access" itself: Glassbox's 2022 terms use "API Calls" to mean the **captured client-server traffic of the customer's own application**, a billing unit, not calls to a Glassbox API ([Glassbox T&Cs 2022](https://www.glassbox.com/glassbox-general-terms-conditions-effective-july-15-2022/)). It is an inference, but a material one, that "Unlimited API access" on the pricing page may not mean what a connector builder hopes it means; this needs a direct answer from Glassbox.

What is verified comes from the capture side. Glassbox distributes its SDKs through an anonymously readable vendor Artifactory, not public registries; fifteen repositories cover Android, iOS, Flutter, React Native, Cordova, Capacitor, NativeScript, Xamarin, MAUI and Kotlin Multiplatform, all on one version line whose latest release, 7.3280.0, was published on 5 November 2026 ([Glassbox Artifactory](https://glassbox.jfrog.io/artifactory/api/repositories)). These SDKs only send data to Glassbox and expose no read API. Their value is vocabulary. They establish, as verified facts, that a deployment is addressed by a per-tenant report URL and an application GUID, that an optional customer identifier (`cuid`) exists, that custom events carry a name and a flat map of primitive values, that sessions can be paused, excluded and split into named screens, and that the mobile SDK can return the current session ID to the host app ([Flutter plugin package](https://glassbox.jfrog.io/artifactory/api/pub/pub-local-glassbox/packages/glassbox_flutter_plugin/versions/7.3280.0.tar.gz), [Cordova plugin package](https://glassbox.jfrog.io/artifactory/api/npm/glassbox-npm/@glassbox/glassbox-client-recording-plugin/-/@glassbox/glassbox-client-recording-plugin-7.3280.0.tgz)). Ingest hostnames follow `report.<tenant>.gbqofs.io` with the tag served from `cdn2.gbqofs.com/<tenant>/` ([CCS buyer UI template](https://github.com/Crown-Commercial-Service/ccs-scale-cat-buyer-ui/blob/HEAD/src/main/views/template.njk)). The console is served under a `/webinterface/webui/` application root, on `console.<tenant>.glassboxdigital.io` for SaaS and on customer-owned hostnames (sometimes port 8443) for self-hosted deployments, and a replay deep link takes a 32-hex-character session ID plus a session start time in epoch milliseconds ([published incident page](https://github.com/llatin10/llatin10.github.io/blob/HEAD/production-issues-insights.html), [Sagewatch config.py](https://github.com/harapriya1704/Sagewatch/blob/HEAD/config.py)). That the read API lives under the same `/webinterface/` root is an inference, not a finding.

The surrounding constraints are better documented than the API. Glassbox sells multi-tenant cloud, single-tenant cloud on AWS or Azure, and on-premises deployments, with on-prem, cloud and hybrid offered on every plan ([Glassbox data privacy & security](https://glassbox.com/platform/data-privacy-security), [Glassbox pricing](https://www.glassbox.com/platform/plans-pricing/)). Retention is short and plan-bound: **session replay is kept one to three months and analysis data one to thirteen months** depending on plan ([Glassbox pricing](https://www.glassbox.com/platform/plans-pricing/)). Sensitive values are masked by default at capture and can be omitted entirely; access is governed by role-based controls with an audit log and SAML single sign-on ([Glassbox data privacy & security](https://glassbox.com/platform/data-privacy-security)). The vendor claims seven of the ten largest US banks as customers ([Glassbox news](https://www.glassbox.com/news/glassbox-pulse-mcp-server-operational-intelligence/)). Three inferences follow and shape every route: the API host must be a customer-supplied setting, not a hard-coded one; a meaningful share of deployments will not be reachable from a hosted Bag of Words instance without customer network work; and any data read out will carry masked placeholders where the customer chose not to capture values. A fourth consequence is arithmetic, not inference: with replay retention capped at three months, no API-based route can backfill long history.

## Three routes, three different products

The routes are not interchangeable implementations of one feature. Each gives the Bag of Words agent a different kind of access, and each depends on a different unknown.

| | Glassbox MCP Server | Native REST connector | Warehouse / session-ID stitching |
|---|---|---|---|
| What the agent gets | Curated "context and evidence" and Pulse answers, as tools | Queryable virtual tables (sessions, events, errors, and so on) | Session IDs and replay links alongside the customer's other data |
| Publicly verified today | That it exists and was announced 29 July 2026 | Nothing about the read API | Session-link pattern in New Relic, Tealium, Survicate; replay URL shape |
| Blocking unknown | URL, transport, auth, tool list, GA status, licensing, on-prem availability | Entire API surface | Whether a given customer has stitched IDs into a warehouse at all |
| Fit with Glassbox's roadmap | Aligned | Against the grain | Neutral |
| New Bag of Words code | One preset entry, icon, one test assertion | Client, schemas, registry entry, tests, simulator, docs | None |
| Raw analytical queries | Probably not (inference) | Yes, if the API returns row-level data | Only on the non-Glassbox data |

### The MCP Server is the vendor's intended door for agents

Glassbox's July 2026 release is explicit about direction. The MCP Server "provides enterprise AI systems with governed access to Glassbox digital experience intelligence", so that agents get Glassbox context and evidence "without ingesting a raw stream" of journey data; it shipped alongside Glassbox Pulse, an engine that applies machine learning to flag meaningful changes and answers operational questions in natural language with links to evidence spanning customer behaviour, journey impact, errors, network logs and server-side failures ([Glassbox news](https://www.glassbox.com/news/glassbox-pulse-mcp-server-operational-intelligence/)). Glassbox says it will keep expanding both. Everything a builder needs is missing from the release: tool names and schemas, endpoint, transport, authentication, supported clients, general-availability status, pricing and whether on-premises customers get it at all. No public repository, package or registry listing for the server was found, and every "glassbox" MCP project on GitHub and npm is an unrelated product ([GitHub search](https://github.com/search?q=glassbox+mcp&type=repositories)).

Two inferences matter for product fit. First, the "without a raw stream" framing implies the server returns aggregated or pre-interpreted evidence, so an analyst who wants to compute a funnel their own way will likely be unable to. Second, since the in-product assistant GIA runs on Microsoft's Azure OpenAI Service ([Glassbox Insights Assistant](https://www.glassbox.com/platform/glassbox-insights-assistant/)), cloud-dependent AI features plausibly lag or differ on self-hosted deployments, which is where much of Glassbox's banking base sits. Neither is confirmed.

### A native connector is feasible in shape and unspecifiable in detail

The case for a native connector is that only it produces an indexed catalog, tracked queries and table-shaped results inside Bag of Words. The case against building it now is that nothing public describes what it would call. One machine-generated catalogue file on GitHub asserts bearer-token auth, cursor pagination and webhooks for a Glassbox REST API, but it gives no endpoint, cites a bare hostname as its spec and should not be treated as evidence ([Assay catalogue entry](https://github.com/Assay-Tools/assay/blob/HEAD/evaluations/glassbox-api.json)). No ELT vendor ships a Glassbox connector that could serve as prior art; searches across Airbyte, Fivetran, Singer and similar catalogues found none, though those catalogues were checked by web search and not page by page, so this is "not found", not "confirmed absent".

The data model can be sketched only conceptually. A session begins when an end user arrives and ends on close or after twenty minutes of inactivity ([Glassbox T&Cs 2022](https://www.glassbox.com/glassbox-general-terms-conditions-effective-july-15-2022/)); Glassbox says it captures and indexes all digital events, averaging more than a thousand per session ([Glassbox for data & analytics teams](https://www.glassbox.com/solutions/data-analytics/)); reviewers describe struggle scores, journeys, segments, heatmaps, alerts and search by session or correlation ID ([AWS Marketplace B09ZVL2TQB](https://aws.amazon.com/marketplace/pp/B09ZVL2TQB)). A grain of session, then page or screen, then event is a reasonable inference. Field names, identifier formats, the event taxonomy, the struggle-score scale and whether funnels or segments exist as API objects are all unknown.

### Stitching is the only route with verified mechanics, and it returns links

Every third-party integration that could be inspected follows one pattern: the Glassbox session identifier or a replay link is pushed into the other tool. New Relic's Glassbox quickstart queries New Relic's own JavaScript error events for custom attributes named `GlassboxSessionId` and `GlassboxSessionReplay` (verified; [New Relic quickstart dashboard](https://github.com/newrelic/newrelic-quickstarts/blob/main/dashboards/glassbox/dashboard.json)). Tealium's tag deploys the Glassbox capture script and syncs nothing out (verified; [Tealium docs](https://docs.tealium.com/client-side-tags/glassbox-detector-tag/)). Survicate adds a "Glassbox URL" column to survey exports ([Survicate help](https://help.survicate.com/en/articles/3942551-glassbox-integration)). Medallia reportedly reads the web session from a `_cls_s` cookie (snippet-level; the page blocked automated reading; [Medallia docs](https://docs.medallia.com/medallia-digital/medallia-digital-web/analytics-solution/session-recording-software/glassbox)). Glassbox's own list of roughly twenty-five named integrations contains web analytics, tag managers, APM, voice-of-customer, A/B testing and ticketing tools, and **no BI tool, warehouse or customer data platform** ([Glassbox integrations](https://www.glassbox.com/platform/integrations/)).

The inference is that, in many accounts, the most accessible "Glassbox data in the warehouse" is a session-ID or replay-URL column riding along in Adobe Analytics feeds, GA4 exports, survey responses or log platforms. That is useful to an AI analyst in a specific way: an answer about failed checkouts can end with links to the recordings. It is not Glassbox analytics. Whether Glassbox supports the reverse flow for a given tool, and whether any particular customer has done the stitching, is knowable only per account. One reviewer's complaint that a Google Analytics link was still not working two years after launch is a reminder not to assume it ([AWS Marketplace reviews](https://aws.amazon.com/marketplace/pp/prodview-waapo3vlxej2o)).

## How each route lands in the connector architecture

The repo has a clean answer for each route, and they differ by roughly two orders of magnitude in effort. The following is verified against the working tree unless marked otherwise. Glassbox is not mentioned anywhere in the repo's code, docs or commit history, so this is a greenfield addition.

**The MCP route is a preset, not a connector.** The `add-connection-type` skill states that an MCP server is added as a named preset that resolves to the generic `mcp` type, with no client class, no config schemas and no per-type tests beyond an assertion in the presets unit test (`.agents/skills/add-connection-type/SKILL.md:101-108`). The preset model supports two transports, streamable HTTP and SSE, and four auth modes: OAuth via dynamic client registration, a pre-registered OAuth app, a per-user bearer token, and basic (`backend/app/schemas/data_source_registry.py:489-503`). This turns the vendor unknowns into a short compatibility checklist. If Glassbox's server is a remote HTTP endpoint using one of those auth modes, the integration is a registry entry and an icon. If it is a locally run process, or sits behind auth the preset model does not offer, the route needs platform work that the notes did not scope. A preset also needs a server URL, and Glassbox URLs are per tenant, so whether the preset form lets a user supply their own host is an open repo question that should be checked before committing to this route. The trade-off is recorded in the repo's own HubSpot design doc: a preset exposes tools with no catalog ownership, while a native connector exposes tables with a shared, indexed catalog and tracked queries (`docs/design/hubspot-connector.md`).

**The native route follows the CrowdStrike pattern unless Glassbox has a query language.** The repo has two archetypes for REST sources. Where the vendor exposes a query language over HTTP, the client passes the string through, as PostHog does with HogQL (`backend/app/data_sources/clients/posthog_client.py:246-263`). Where the vendor has only resource endpoints, the client declares a static catalog of virtual tables and accepts a JSON query spec that it translates into paged calls, as CrowdStrike does (`backend/app/data_sources/clients/crowdstrike_client.py:66-110`, `:535-566`). No evidence for or against a Glassbox query language exists, so the choice cannot be made yet; the HubSpot doc records the cost of guessing, where a plan built on the JSON-spec archetype had to be re-scoped after a live sign-in revealed the vendor exposed SQL. PostHog remains the reference for product-analytics framing: it is the only registered product-analytics source, sits in the services category, and already models sessions and session-replay events as tables (`backend/app/schemas/data_source_registry.py:1701-1719`).

The contract a Glassbox client must satisfy is small and fixed: a description, a connection test, schema discovery, a prompt-schema rendering and a query method that returns a dataframe (`backend/app/data_sources/clients/base.py:165-188`). The agent needs no changes. Generated code calls the client's query method through a dictionary of clients, and the only per-connector prompt text is the client's own description, so all Glassbox-specific guidance to the model lives in the client file (`backend/app/ai/prompt_formatters.py:6-19`, `backend/app/ai/agents/coder/coder.py:489-496`). The form is generated from the Pydantic config and credentials schemas, so no Vue code changes; a PNG icon named after the type needs no mapping either (`frontend/components/datasources/ConnectForm.vue:594-607`, `frontend/components/DataSourceIcon.vue:89-157`).

Three repo mechanics bear directly on the Glassbox unknowns. The client is built by merging config and credentials into keyword arguments filtered to the constructor's signature, and an egress policy check runs on recognised host and URL keys before construction, so the tenant host should be carried in a field with a recognised name such as `base_url` (`backend/app/services/connection_service.py:2814-2874`, `backend/app/core/egress.py:718-764`). Because the auth scheme is unknown, the registry's support for several auth variants per type is the natural hedge; existing SaaS connectors with API keys offer both system and per-user scopes, and Glassbox's role-based access model argues for deciding the user scope deliberately. And the integration harness asserts a non-zero table count, so the virtual-table catalog cannot be empty (`backend/tests/integrations/ds_clients.py:25-27`).

The skill's file list understates the work. CrowdStrike's introducing commit is the best measure of real scope: a client of about 750 lines, schema and registry edits, a unit test that fakes only the HTTP boundary with a scripted in-test server, an integration-harness entry, a feedback-loop document, an icon, evidence screenshots and a vendor API simulator under `tools/` (`git show --stat 8e941c3d`). Two enforcement tests not mentioned in the skill will fail until updated: one requires every HTTP-based connector to have a row in the egress matrix and to obtain sessions only through the pinned egress helper, the other requires each client to be listed deliberately in the query-parameter literal-rule table (`backend/tests/unit/test_connector_egress.py:269-272`, `backend/tests/unit/test_query_params.py:567-612`). The README connector table, changelog and version also move. If a setup guide is translated, the strings must be added to all ten locale catalogs in `locales/`, not the three the root guide names. One precedent deserves attention: CrowdStrike's feedback loop openly records that its simulator was derived from the official SDK and "not verified against a real tenant" (`docs/feedback-loops/crowdstrike-connector.md:5-30`). Glassbox has no public SDK for its read side, so a simulator built without customer documentation would encode invention, not a contract.

**The stitching route needs no connector at all.** Snowflake, BigQuery and Splunk are already registered connection types (`backend/app/schemas/data_source_registry.py:783`, `:810`, `:1237`), so a customer whose warehouse or log platform holds a Glassbox session-ID column can query it today. What Bag of Words would add is knowledge, not code: guidance to the agent on recognising those columns and composing replay links from a tenant host, session ID and start time. That link format is verified from a single public example and should be confirmed against a customer's console before it is relied on.

A fourth option sits between the routes and is worth naming. The repo's generic Custom API type lets an administrator define REST endpoints as callable tools with bearer, basic, API-key or OAuth-app auth (`backend/app/schemas/data_source_registry.py:2884-2929`). A customer holding the portal documentation could wire up a handful of Glassbox endpoints this way with no release from Bag of Words. It is an inference that this works for Glassbox, since the auth scheme is unknown, but it is the cheapest way to learn what the API actually returns before committing to a native connector.

## What to obtain before any code is written

The unknowns reduce to a list of things only Glassbox or a licensed customer can supply. No amount of further public research closes them; the support portal, the Trust Center and several partner pages resisted automated reading, and the web archive and the individual marketplace catalogues were not checked, so a human with a browser can still harvest some marginal detail, but not an API reference.

| Needed | From | Why it gates the work |
|---|---|---|
| API reference from the customer portal: endpoints, base-URL pattern, versioning, request and response shapes | Customer login or Glassbox partner team | Without it the native route has nothing to call |
| Whether "open API" / "Unlimited API access" covers reading sessions, events, reports, funnels and struggle data, or only administration and capture | Glassbox | Decides whether a native connector is possible at all |
| Whether any query language or report-execution endpoint exists | Glassbox | Selects the PostHog or the CrowdStrike archetype |
| Auth scheme, service-account support, token lifetime, scopes and roles, IP allow-listing | Glassbox and customer admin | Defines the credential variants and the user-scope decision |
| Pagination, rate limits, concurrency and export size caps | Glassbox | Defines paging and back-off behaviour; none is published |
| MCP Server specification: URL per tenant, transport, auth, tool and resource list, GA status, licensing, deployment-model coverage | Glassbox | Decides whether a preset suffices |
| Field-level data dictionary: identifiers, event taxonomy, custom-field model, struggle-score definition | Glassbox | Defines the virtual-table catalog and the agent prompt |
| Whether masking applies identically to API, export and MCP output, and whether any role can unmask | Glassbox and customer security | Sets what the agent can ever see |
| Existence, destinations, format and cadence of any bulk export or streaming product | Glassbox | Confirms or kills a first-party warehouse path |
| Customer's deployment model, console hostname, plan and retention | Customer | Determines reachability and how much history exists |
| Which downstream systems already carry Glassbox session IDs, and under what column names | Customer data team | Makes the stitching route concrete |
| A non-production tenant or sandbox, with test credentials | Customer or Glassbox | Required for the repo's live verification pass and integration harness |
| Security and legal sign-off for third-party read access | Customer | Regulated customers will treat any of the three routes as a data-sharing event (inference) |
| Confirmation of the replay deep-link format | Customer console | Verified from one public example only |

Several items in this report rest on weaker evidence than the rest and should be re-verified if they become load-bearing: the Medallia cookie detail, the Splunk thread, Glassbox's reported November 2025 acquisition of the anomaly-detection firm Anodot ([Business Wire](https://www.businesswire.com/news/home/20251104734652/en)) and the details of its 2024 take-private by Alicorn Venture Partners ([Glassbox news](https://www.glassbox.com/news/glassbox-to-be-acquired-by-alicorn-venture-partners/)) were all seen as search snippets only. The contract terms reviewed date from 2022 and are marked superseded.

## Conclusion

The research changes the shape of the question. The brief assumed three engineering routes to compare; the evidence shows one vendor-endorsed route with no public specification, one conventional route with no public API to build against, and one indirect route that works today but delivers pointers to Glassbox, not its data. The decisive variable is not architecture but access: a single customer login to the Glassbox portal would resolve most of the table above in an afternoon, and the repo's Custom API type offers a way to probe a real tenant before any connector is designed.

Two implications stand out. Glassbox's stated strategy is to give agents curated evidence and withhold raw streams, which means a Bag of Words integration via MCP would make Glassbox Pulse, not the Bag of Words agent, the analyst of record for behavioural questions; whether that is acceptable is a product decision to take before the technical one. And because Glassbox's customers are concentrated in regulated industries with self-hosted options and short retention, the first design partner matters more than usual: an integration proven on a multi-tenant SaaS account will not automatically reach the banks that make up the vendor's core base. The sensible sequence is to ship stitching guidance now at near-zero cost, pursue the MCP specification and the API reference in parallel through a customer or partner channel, and commit to a native connector only if the API proves to return row-level data that the MCP Server withholds.
