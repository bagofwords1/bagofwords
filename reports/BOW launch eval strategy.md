# Publish the Analytics Eval Incumbents Refuse to Run

Bag of Words should launch on one original, fully open benchmark that no incumbent has been willing to publish, rather than on a public text-to-SQL leaderboard. The core launch artifact is a **"same model, two harnesses" comparison**: Claude Code and Codex connected to a plain database MCP server versus the same agents connected through BOW's MCP gateway (and BOW's native chat), on an analyst-authored question set with double-annotated gold answers, execution-based grading, five trials per cell, pass@1 *and* pass^5, Wilson confidence intervals, and cost per correct answer. That same question set becomes a cross-model leaderboard (10–12 models, each at two or three effort settings) that fills a documented gap: no independent evaluator today publishes a SQL or data-analysis index with cost ([Vals](https://www.vals.ai/benchmarks); [Artificial Analysis](https://artificialanalysis.ai/leaderboards/models)). The public boards are a liability, not a trophy: Spider 1.0 has been frozen since February 2024 ([Spider](https://yale-lily.github.io/spider)), 52.8% of BIRD Mini-Dev and 62.8% of Spider 2.0-Snow gold labels are wrong ([arXiv 2601.08778](https://arxiv.org/html/2601.08778v3)), and DABstep's hard split has 16 entries at 100% including throwaway accounts ([benchmarklist snapshot](https://benchmarklist.com/benchmarks/dabstep/)). The one public board worth a launch-day submission is **LiveSQLBench**, because it is unsaturated (top 48.00), issues a "Verified" badge after re-running your code, and already lists Claude Code and OpenHands rows to compare against ([LiveSQLBench](https://livesqlbench.ai/)). Two original benchmarks let BOW own uncontested ground: an **instruction-learning benchmark** (does the self-improving loop learn reusable rules without memorizing record-level facts, and how fast does accuracy climb per correction?) built from the existing `overfit_suite.yaml`, and a **multi-turn dashboard benchmark** built from the existing `artifact_iteration/` scenarios, both measuring things Snowflake and Databricks explicitly say their eval tooling cannot ([Snowflake docs](https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst-evaluations); [Databricks docs](https://docs.databricks.com/aws/en/genie-agents/monitor)). The hard truth to print alongside: raw Codex and Claude Code are strong on data work (Codex scored 90.9% and Claude Code 78.0% in the only named multi-vendor BI test, beating Hex, Julius and Snowflake Cortex) ([Basedash BI Bench](https://www.basedash.com/bi-bench)), so BOW's margin will appear on hard business-logic questions, multi-turn consistency, reliability (pass^k), cost, and governance, not on simple SQL. The existing 35.6% Spider 1.0 run must never be published.

## Public SQL leaderboards cannot carry the launch

The incumbents have already shown what a launch built on unverifiable numbers earns. Snowflake's Cortex Analyst post claimed "90%+ SQL accuracy" on 150 internal questions against single-prompt GPT-4o at 51% ([Snowflake](https://snowflake.com/en/engineering-blog/cortex-analyst-text-to-sql-accuracy-bi)) and produced **zero Hacker News discussion** ([HN Algolia](https://hn.algolia.com/api/v1/search?query=Cortex%20Analyst%20text-to-SQL&tags=story)). Databricks' Genie One launch reported 84.5% against "the strongest general-purpose coding agent" at 52.4% on a **28-question** suite with competitors anonymized ([Databricks](https://www.databricks.com/blog/introducing-genie-one-genie-ontology-and-genie-agents)), and the only third-party reaction was "no independent verification yet" ([Pebblous](https://blog.pebblous.ai/blog/databricks-genie-one-governed-data/en/)). Snowflake's Cortex Sense post (24.1% to 86.3%, $1.76 to $0.59 per query) disclosed no question count at all ([Snowflake](https://www.snowflake.com/en/blog/enterprise-ai-agents-grounded-context/)). These vendors get coverage through press reach; a startup gets attention only through reproducibility. The counter-example is instructive: an unknown open-source agent that topped Terminal-Bench with a public repo drew a **393-point Show HN**, the highest-scoring Terminal-Bench story found ([HN Algolia](https://hn.algolia.com/api/v1/search?query=Terminal-Bench&tags=story)), and debunk threads (Reflection-70B's wrapper exposure at 250 points, "Composer 2 is just Kimi K2.5" at 276) routinely out-score the launches they attack ([HN Algolia](https://hn.algolia.com/api/v1/search?query=Reflection%2070B&tags=story); [HN Algolia](https://hn.algolia.com/api/v1/search?query=Cursor%20Composer&tags=story)).

The obvious alternative, a Spider or BIRD score, is now worse than useless because any critic has a ready-made rebuttal. The UIUC audit found annotation errors in **62.8% of Spider 2.0-Snow** examples with public gold and **52.8% of BIRD Mini-Dev**; re-scoring 16 BIRD agents on corrected labels moved scores by −7% to +31% and ranks by up to nine positions, with a Spearman correlation of only 0.32 between original and corrected rankings ([arXiv 2601.08778](https://arxiv.org/html/2601.08778v3); [CIDR 2026](https://www.vldb.org/cidrdb/papers/2026/p5-jin.pdf)). Bridgewater independently reached the same 52.8% figure for BIRD Mini-Dev ([Bridgewater AIA Labs](https://www.bridgewater.com/aia-labs/putting-task-expertise-into-rl-to-achieves-state-of-the-art-on-text-to-sql)). Spider 1.0 stopped accepting submissions in February 2024 at 91.2% ([Spider](https://yale-lily.github.io/spider)), which makes the repo's `spider_results.jsonl` (158/444 execution matches, 42 questions with no predicted SQL, 9 errors, mean 66.5 seconds per question) doubly unpublishable: it is an unfinished run on a dead benchmark whose exact-match scorer penalizes the richer answers BOW's agent produces. Spider 2.0-Snow has saturated to 96.70% and is dominated by vendor marketing entries ([Spider 2.0](https://spider2-sql.github.io/)), and its shared Snowflake evaluation account was suspended in August 2026 ([xlang-ai/Spider2](https://github.com/xlang-ai/Spider2)). Classic BIRD is near its human ceiling (82.95 vs 92.96), takes about ten days by email, and is SQLite-centric ([BIRD](https://bird-bench.github.io/)). DABstep grades instantly with no verification and its hard split now has 16 entries at 100%, several from accounts named "test" or "aa" ([benchmarklist snapshot](https://benchmarklist.com/benchmarks/dabstep/)).

That leaves a short list of public boards where a submission adds credibility rather than exposure. The table below is the triage.

| Benchmark | Verdict | Why |
|---|---|---|
| **LiveSQLBench** (BIRD team, 600 PostgreSQL tasks) | **Run at launch** | Top only 48.00 (C3 AI DIA); "Verified" badge after the BIRD team re-runs your code; Claude Code (MiniMax M3) 40.17, OpenHands + Opus 4.6 38.00 and per-task costs ($0.05–$0.67) already on the board; test-case grading, not exact match ([LiveSQLBench](https://livesqlbench.ai/)) |
| **BIRD-Interact** (a-Interact mode) | Run within 60 days | ICLR 2026 Oral; agent decides when to ask the user simulator; GPT-5 at 17.00% success, so any credible result is newsworthy; Verified badge; $0.06–$0.60/task ([BIRD-Interact](https://bird-interact.github.io/); [arXiv 2510.05318](https://arxiv.org/abs/2510.05318)) |
| **Spider 2.0-Lite** | Optional, 60–90 days | Still has headroom (76.23 top) and the single most relevant comparator row, "Claude Code Agent + Sonnet" at 61.20; but requires own BigQuery billing, no verification flags, no row dates ([Spider 2.0](https://spider2-sql.github.io/)) |
| **Spider 2.0-DBT** | Optional, cheap | 68 DuckDB tasks, free, only 16 entries (top 65.60); code-agent setting, not ad-hoc analytics ([Spider 2.0](https://spider2-sql.github.io/)) |
| **Argo-Bench** (TextQL) | 90+ days | Most launch-relevant newcomer (7.49B-row warehouse, FP&A and dashboard tasks, Opus 5.5 only 34.8% solved) but $0.49–$4.89 per task plus BigQuery, and official scores need TextQL's private grader ([arXiv 2610.02122](https://arxiv.org/html/2610.02122v1)) |
| **DABstep** | Internal regression only | Saturated, unverified; full run costs $2–$435 depending on model, so it is a cheap smoke test ([HF blog](https://huggingface.co/blog/dabstep)) |
| **Spider 1.0, classic BIRD, TableBench** | Avoid | Frozen, mis-annotated, or small-table QA rather than warehouse analytics |
| **OpenRCA, ITBench, ORCA-bench** | Avoid | SRE telemetry root cause, 80 GB+ data, not business-metric RCA ([microsoft/OpenRCA](https://github.com/microsoft/OpenRCA)) |

LiveSQLBench deserves the launch slot for a structural reason beyond its headroom: it is the only text-to-SQL board that distinguishes "Verified" from "Reported" entries and publishes cost per task, which lets BOW's row be compared on both axes against coding-agent rows without BOW having to run those agents itself ([LiveSQLBench](https://livesqlbench.ai/)). A Base-Full run costs roughly $60–$400 in model spend at the published per-task rates. The Large-v1 variant (480 tasks, ~84K-token prompts, "Business Rule Drift") is the public benchmark whose design most rewards learned context over raw model capability, and therefore the natural second submission once the self-improving loop has a measured effect.

## Two original benchmarks let BOW own uncontested ground

No incumbent publishes multi-turn accuracy, dashboard quality, paraphrase consistency, governance leakage, or cost per correct answer on a shared dataset, and two of them say so in their documentation: Snowflake's Cortex Analyst evaluations state "Follow-up or multi-turn conversation evaluation is not supported" ([Snowflake docs](https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst-evaluations)), and Databricks' Genie benchmarks "run as new conversations" without threaded context ([Databricks docs](https://docs.databricks.com/aws/en/genie-agents/monitor)). Hex, the most eval-literate peer, published its methodology but explicitly no overall score ([Hex](https://hex.tech/blog/evaluate-data-agents/)). BOW already has partial instruments for exactly these gaps in `backend/tests/evals/`, which means the cost of owning the niche is mostly expansion and rigor, not invention.

The first original benchmark is an **instruction-learning benchmark**, and it has no public precedent. The repo's `benchmarks/overfit_suite.yaml` already scores, by regex over database rows in a fresh org per trial, whether the self-learning harness persists record-level facts it must not (four bait cases) while capturing reusable rules it must (two control cases). The literature supports the premise but has never measured it for analytics: ACE (ICLR 2026) raised DeepSeek-V3.1 from 42.4 to 59.5 on AppWorld purely through evolving context and documented "context collapse" when a prior method's playbook shrank from 18,282 tokens to 122 in one step ([ACE](https://arxiv.org/html/2510.04618)); Microsoft ISE found that storing corrected SQL patterns over three iterations was the single largest lever in its study, lifting Genie from 69.23% to 88.50% ([Microsoft ISE](https://devblogs.microsoft.com/ise/llm-sql-query-generation/)); Databricks' ALHF showed answer quality quadrupling with 32 feedback records, but on docs QA, not SQL ([Databricks](https://www.databricks.com/blog/agent-learning-human-feedback-alhf-databricks-knowledge-assistant-case-study)). The launch version should expand to roughly 30 bait and 30 control cases, add a **learning curve** (held-out accuracy after 0, 10, 25 and 50 correction events on a fixed test slice, with the test slice never used for learning), and report two numbers: generalization gain and overfit rate. This is the eval that makes "CI for agents" and "instructions as commits" concrete, and it directly pre-empts the obvious critique of any self-improving system, which is that it memorizes the test.

The second is a **multi-turn dashboard benchmark**. The repo's `artifact_iteration/` already holds three scenarios (a 12-turn memory gauntlet, a complex one-shot dashboard, an 8-turn destructive gauntlet) with an architecture-neutral scorer, and a before/after result of 0.801 to 0.952 with Claude 4.5 Haiku at n=1 per cell. That n=1 result is directional only and must not be published as-is; the launch version needs at least five trials per cell, three or more models, and an end-state grading design, which Anthropic recommends for stateful agents ([Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)). The only academic analog, DV-World (260 tasks including dashboard building and clarification, state of the art below 50%), has no leaderboard ([arXiv 2604.25914](https://arxiv.org/html/2604.25914)), so a product run would be first-mover. Because dashboard quality is partly subjective, the headline metric should be deterministic (did the final artifact contain the right charts over the right result sets after N turns, and did destructive instructions get refused?) with blind pairwise human preference as a secondary GDPval-style measure, published with grader agreement rates ([GDPval](https://arxiv.org/html/2510.04374v1)).

Two cheaper additions round out the niche. A **paraphrase-consistency metric** (the same business question asked in four phrasings; percentage of identical result sets) targets the single most-reported practitioner complaint about Genie, that "rephrasing the same question could produce different SQL and different answers" ([Apex Systems](https://www.apexsystems.com/insights/article/how-do-we-make-databricks-genie-reliable-enough)), and Databricks itself recommends two to four phrasings per benchmark question without publishing a consistency number ([Databricks docs](https://docs.databricks.com/aws/en/genie-agents/monitor)). A **governance suite** (row-level-security leakage: can a restricted persona extract a forbidden aggregate through any phrasing or follow-up?) measures something no vendor has ever disclosed. Both are scored deterministically and both can reuse the question set from the main benchmark. The existing `docs/design/query-acceleration-benchmarks.md` measurements (3.3x and 6.0x scan reduction, 886x and 2,126x latency reduction, break-even at 1.8 and 1.0 questions on BigQuery and Snowflake) belong in the launch as a cost-per-correct-answer footnote, not a headline, because they depend on question repeat rates the eval does not control.

## Same model, two harnesses: the comparison that beats a strawman

The industry's preferred baseline is now a "frontier coding agent with raw MCP access" scoring 20–30%: Snowflake reports 23% for coding agents with its MCP connector and 24.1% without a context layer ([Snowflake](https://www.snowflake.com/en/blog/snowflake-cowork-personal-work-agent/); [Snowflake](https://www.snowflake.com/en/blog/enterprise-ai-agents-grounded-context/)), Databricks reports 25% and 32.1% ([Databricks](https://www.databricks.com/blog/introducing-genie-one-genie-ontology-and-genie-agents); [Databricks](https://databricks.com/blog/introducing-genie-code)). The problem is that the one test that names the agents contradicts this: in Basedash's BI Bench, **Codex scored 90.9% and Claude Code 78.0%**, beating Hex (80.6% for Codex only), Julius (46.1%), Sigma (35.2%) and Snowflake Cortex (19.2%) ([Basedash BI Bench](https://www.basedash.com/bi-bench)). On Spider 2.0-Lite a plain "Claude Code Agent + Sonnet" lands at 61.20, mid-table rather than bottom ([Spider 2.0](https://spider2-sql.github.io/)). BOW must design for the strong version of the baseline, and the design that survives scrutiny is Terminal-Bench's: every row is an (agent, model) pair, run at least five times with 95% confidence intervals, next to a deliberately minimal neutral reference scaffold so that nobody can call the baseline a strawman ([Terminal-Bench paper](https://arxiv.org/html/2601.11868)). That design produced the cleanest "harness matters" exhibit in the field, GPT-5.4 mini at 66.1% in Codex CLI versus 36.9% in the neutral Terminus 2 scaffold on identical tasks ([tbench.ai](https://www.tbench.ai/news/terminal-bench-2-1)), and in the SQL domain the same phenomenon is visible on Spider 2.0-Snow, where Claude Sonnet 4.5 ranges from 67.28 to 90.49 across four harnesses ([Spider 2.0](https://spider2-sql.github.io/)).

The recommended matrix has four arms on one pinned model, repeated for at least two models (one Anthropic, one OpenAI, so each coding agent is tested on its native model). Arm A is the **neutral reference**: the model, one `run_sql` tool, a raw schema dump, no instructions, published as a 100-line script anyone can run; this is the analytics transplant of Terminus 2. Arm B is **Claude Code or Codex plus a plain database MCP server** (Postgres, Snowflake or BigQuery official server), the baseline the incumbents use but named rather than anonymized. Arm C is **the same coding agent plus BOW's MCP gateway**, which is the product's cleanest story because the agent and model are identical and only the tool surface changes. Arm D is **BOW's native chat**, which adds BOW's own orchestration. The gap between B and C isolates context and tools; the gap between C and D isolates orchestration; the gap between A and B shows how much the coding agent itself adds over a bare loop. Supabase's finding that Claude Code consults documentation in fewer than 40% of sessions even with skills loaded ([Supabase Evals](https://supabase.com/blog/supabase-evals)) is the citable mechanism for why B-to-C should show a gap: pointing an agent at context is not the same as a harness that injects it.

The second chart is an **ablation ladder** on one cheap model, following the Microsoft ISE template (raw agent 66.7% with metadata only, 80.8% with domain hints; Genie 9.5% empty, 69.2% with descriptions and instructions, 88.5% with learned corrections) ([Microsoft ISE](https://devblogs.microsoft.com/ise/llm-sql-query-generation/)) and ACE's table layout (one base model, one row per context method, one external reference row for a frontier model run raw) ([ACE](https://arxiv.org/html/2510.04618)). The rungs are: raw schema, plus column descriptions, plus metric definitions and instructions, plus execution with error feedback and verification, plus instructions learned from 25 corrections. The honest headline this design supports is the one ACE and Factory used: "matches the frontier model on average, exceeds it on the hard multi-table split, at a fraction of the cost," because every source shows harness gains concentrate on harder tasks and mid-tier models ([Factory](https://factory.com/news/terminal-bench); [ACE](https://arxiv.org/html/2510.04618)). One finding from dbt's open benchmark should be conceded up front: most of the gain in its study came from data modeling rather than the semantic layer (Sonnet 4.6 text-to-SQL rose from 64.5% to 90.0% after adding three models, the semantic layer added about eight more points), and the semantic layer scored 0% on out-of-scope "too many hops" questions because it refused rather than guessed ([dbt Labs](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026)). BOW's grading must therefore separate "wrong answer" from "declined to answer," and report both.

Terms of service shape which arms can be named. For the LLM vendors, Anthropic's Commercial Terms forbid using the service "to build a competing product or service, including to train competing AI models" but contain no clause on benchmarking or publishing evaluations ([Anthropic Commercial Terms](https://www.anthropic.com/legal/commercial-terms)); comparative evaluation is ordinary API usage, and BOW should document that no outputs are used for training. Claude Code and Codex consumer or subscription terms were not verified in this research and should be checked by counsel before launch, which is one reason to run arms B and C through the API-backed CLI modes with pinned model IDs. For warehouses, the DeWitt-clause era is largely over: Snowflake's Acceptable Use Policy permits publishing benchmark results of its AI features provided results are shared with Snowflake "reasonably in advance" and the disclosure "includes all information necessary to replicate the Test," with Preview-feature results confidential ([Snowflake AUP](https://www.snowflake.com/legal/acceptable-use-policy/)); Databricks adopted a reciprocal "DeWitt Embrace" clause in 2021 that permits naming it when it may name you back ([Databricks](https://www.databricks.com/blog/2021/11/08/eliminating-the-dewitt-clause-for-database-benchmarking.html)), though the current MCSA text should be confirmed. Google BigQuery, Oracle and Microsoft still condition publication on consent ([Cube](https://cube.dev/blog/dewitt-clause-or-can-you-benchmark-a-database)), and Basedash reports excluding some tools because their terms prohibit benchmarking ([Basedash BI Bench](https://www.basedash.com/bi-bench)). The practical consequence is that the launch-day comparison names Claude Code and Codex (public models, public harnesses, the ToS-friendliest comparison available) and defers Genie, Cortex, Hex and Julius to a second wave once each vendor's clause is cleared and each has been offered the results in advance. When a competitor cannot be named, the write-up should say which clause prevents it; anonymization without explanation reads as hiding.

## A cost-per-correct-answer leaderboard fills a gap no evaluator covers

Running the same question set through BOW with many models produces the second launch asset, and the market has an opening for it: Vals publishes 30-plus live benchmarks with accuracy, cost per test and duration but none for SQL or data analysis ([Vals](https://www.vals.ai/benchmarks)); Artificial Analysis reports cost per task and effort tiers across 204 models but has no SQL component ([Artificial Analysis](https://artificialanalysis.ai/leaderboards/models)); LiveSQLBench and Spider 2.0 mix bare models with agent systems and publish no latency ([LiveSQLBench](https://livesqlbench.ai/); [Spider 2.0](https://spider2-sql.github.io/)). The only vendor-run cross-model SQL benchmark with cost, ClickHouse's 201-question test (Claude Fable 5.1 at 76.6% for a $52 full run versus DeepSeek V4 Flash at 65.7% for $1), keeps its questions private and uses an LLM committee as ground truth ([ClickHouse](https://clickhouse.com/blog/agentic-analytics-benchmark-data-agent-mnist)). A "Data Agent Index" with open questions, human-verified gold, and cost would be a first.

The presentation grammar should copy what the credible evaluators converged on. **One row per model × effort setting**, because effort moves a single model's score and cost more than most model swaps: Claude Opus 5.5 scores 58, 56, 54 and 51 on the AA index at $5.98, $3.46, $1.82 and $1.34 per task across max, xhigh, high and medium ([Artificial Analysis](https://artificialanalysis.ai/leaderboards/models)), Anthropic's own docs say "tuning effort is often a better lever than switching models" ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model)), and defaults differ by model (`high` on Fable 5.1 and Sonnet 5.5, `medium` on Opus 5.5 and Haiku 5.5), so "default settings" are not comparable ([Anthropic models](https://platform.claude.com/docs/en/about-claude/models/overview)). HAL found higher reasoning effort reduced accuracy in the majority of its runs ([HAL](https://arxiv.org/abs/2510.11977)) and LiveSQLBench shows GPT-5.5 at low effort (33.50) edging xhigh (33.33) ([LiveSQLBench](https://livesqlbench.ai/)), so an effort sweep on at least one model per vendor is itself a finding worth publishing. **Columns**: pass@1 with a Wilson interval, pass^5, cost per correct answer, p50 and p90 wall-clock latency, tool-call or format error rate, and abstention rate, with harness, prompt version, temperature, date and model snapshot ID in a methodology footer. The signature visual is a Pareto scatter of accuracy against cost per correct answer with the frontier drawn, which Vals and RouteLLM both use ([Vals Finance Agent](https://www.vals.ai/benchmarks/finance_agent); [RouteLLM](https://lmsys.org/blog/2024-07-01-routellm/)), bucketed Cursor-style into cheap, mid and frontier tiers so that "cheap model plus BOW harness" sits visibly next to "frontier model raw."

**Cost per correct answer** (total spend divided by correct answers, not per-token price and not cost per attempt) is the right unit for three reasons. Per-token prices now span two orders of magnitude at the frontier, from $0.10/$0.50 for Haiku 5.5 and GPT-6 Luna to $10/$50 for Fable 5.1 and GPT-6 Astra ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing); [OpenAI pricing](https://developers.openai.com/api/docs/pricing)), yet Claude 4.7+ models produce roughly 30% more tokens for the same text ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)), Gemini and xAI re-rate whole requests above 200K tokens ([Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing); [xAI](https://docs.x.ai/docs/models)), and several prices are promotional with announced expiry dates, so per-token comparison is meaningless. Kilo's KiloBench made the same argument for coding, that headline token prices understate real cost "by 5x to 30x" ([Kilo](https://blog.kilo.ai/p/kilobench-because-your-benchmark)). Cost should be computed from provider-reported usage with the cache-hit rate stated and the price snapshot dated. The candidate roster for launch is Haiku 5.5, Sonnet 5.5, Opus 5.5 and Fable 5.1; GPT-6 Luna, GPT-6.1 Sol and GPT-6 Astra; Gemini 3.8 Flash and 3.1 Pro; and the open-weight tier of GLM-5.3-Flash ($0.15/$0.50), DeepSeek V4.1 Flash ($0.30/$1.20), Kimi K2.7 and Qwen3-Coder-Plus ([Z.ai](https://docs.z.ai/guides/overview/pricing); [DeepSeek](https://api-docs.deepseek.com/quick_start/pricing)). Open-weight models already sit at or above mid-tier proprietary models on the public SQL boards (GLM 5.2 tops Spider 2.0-Lite inside Tencent's harness; MiniMax M3 inside Claude Code beats Gemini 3.1 Pro on LiveSQLBench) ([Spider 2.0](https://spider2-sql.github.io/); [LiveSQLBench](https://livesqlbench.ai/)), so the "cheap open model plus harness" row is likely to be the most-shared result.

**pass^k is the reliability metric a BI audience needs**, and no analytics vendor reports it. Sierra introduced pass^k (all k trials succeed) with τ-bench, where GPT-4o's retail score collapsed from roughly 61% at pass^1 to below 25% at pass^8 ([Sierra](https://sierra.ai/blog/benchmarking-ai-agents); [τ-bench](https://arxiv.org/pdf/2406.12045)), and Anthropic's agent-evals guide recommends it for customer-facing agents with the worked example 0.75³ ≈ 42% ([Anthropic](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)). MCPMark reports pass^4 alongside pass@1 for its Postgres environment (52.56% vs 33.86% for the top model) ([arXiv 2509.24002](https://arxiv.org/abs/2509.24002)). A wrong number in a dashboard is a reliability failure, not a discovery problem, so the launch chart should show pass@1 and pass^5 side by side for every row; the gap between them is itself a harness quality signal, and a harness that narrows it has a legitimate claim no accuracy number alone can make. Five trials is the Terminal-Bench de facto minimum ([Terminal-Bench paper](https://arxiv.org/html/2601.11868)); hosted inference is nondeterministic even at temperature 0 because of batch-size-dependent kernels ([Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference)), so fewer trials cannot be defended.

Statistical honesty constrains what the leaderboard can claim. With fewer than a few hundred items, normal-approximation intervals are wrong near 0 or 1 and Wilson or Clopper-Pearson intervals are required ([arXiv 2503.01747](https://arxiv.org/pdf/2503.01747)); for two-system claims the strongest presentation is a paired per-task difference with its interval, because systems agree on which questions are hard ([Miller](https://arxiv.org/pdf/2411.00640)). An audit of 254 SWE-bench submissions found paired McNemar tests at α=0.05 "separate none of the 29 adjacent Verified top-thirty pairs" ([arXiv 2609.17394](https://arxiv.org/abs/2609.17394)), and Terminal-Bench's top ten sit within overlapping ±2–3 point intervals at 89 tasks × 5 trials ([Snorkel](https://snorkel.ai/leaderboard/terminal-bench-2-0/)). At 150–200 questions, BOW can defend 8–10 point gaps and should not claim 3-point ones; ThoughtSpot's BIRD post, the only incumbent post with an interval, conceded that its 3.9-point margin "has not yet cleared a paired per-question test" ([ThoughtSpot](https://www.thoughtspot.com/blog/ai-analyst-accuracy-bird-benchmark)), and that candor is the model to follow.

## Disclosure checklist, grading design and budget

The launches that were attacked each omitted one of four disclosures: the task subset, the compute or parallelism, the trial count and variance, or the harness named per column ([GPT-5 System Card](https://arxiv.org/pdf/2601.03267); [Factory](https://factory.com/news/terminal-bench); [Cursor](https://cursor.com/blog/composer)). The checklist below is synthesized from Anthropic's evals guide, Miller's error-bars paper, Terminal-Bench and HAL reporting norms, GDPval, and Snowflake's replication clause; every item should appear on the chart or in a methodology footer directly beneath it, not in a separate page.

| Item | Standard | Source |
|---|---|---|
| Harness, model snapshot ID, effort and date per bar | Named on the figure, never "a leading coding agent" | [Scale Labs](https://labs.scale.com/leaderboard); [Sukhareva](https://msukhareva.substack.com/p/how-a-small-open-model-beat-a-frontier) |

Grading deserves one further design note. Using Claude to grade a comparison in which Claude is also a contestant invites the self-preference critique ("GPT-4 showed a significant self-preference bias") ([arXiv 2410.21819](https://arxiv.org/pdf/2410.21819)), and BOW's own eval infrastructure uses LLM judges for accuracy and instruction coverage. For the launch, every headline number must be deterministic (execution match, regex over persisted instructions, end-state artifact checks); LLM judging should be confined to the dashboard-quality secondary metric, run with a judge from a vendor not in that chart, and calibrated against roughly 100 human-labeled examples with the agreement rate reported, following Hamel Husain's guidance that below about 60 labels the intervals become uninformative ([validate-evaluator](https://skills.sh/hamelsmu/evals-skills/validate-evaluator)). Anthropic's distinction between capability evals (start low, measure progress) and regression evals (near 100%, guard releases) ([Anthropic](https://anthropic.com/engineering/demystifying-evals-for-ai-agents)) maps onto the repo: the twelve `sanity_*.yaml` suites are regression evals and should be described as such in the launch, not presented as benchmark results.

The budget is dominated by trials and model count, not by any one benchmark. The estimates below combine published per-task costs with the repo's measured 66.5 seconds per question in the Spider 1.0 run; they are order-of-magnitude figures, and BOW's own agent will make more LLM calls per task than the 3.5 that ReFoRCE reports ([ReFoRCE](https://arxiv.org/pdf/2502.00675)).

## Hard truths the launch post must print

**Raw Codex and Claude Code are strong on data work, and simple SQL will not separate BOW from them.** The only named multi-vendor test puts Codex at 90.9% and Claude Code at 78.0%, ahead of most BI products ([Basedash BI Bench](https://www.basedash.com/bi-bench)); a plain Claude Code agent sits mid-table on Spider 2.0-Lite at 61.20 ([Spider 2.0](https://spider2-sql.github.io/)); and on DABstep Claude Code with Opus 4.5 reached 66.93% on the hard split, with the harness advantage showing up as 30x faster wall-clock (20 seconds vs 10 minutes per task) rather than as a wide accuracy gap once scores saturated ([NVIDIA](https://huggingface.co/blog/nvidia/nemo-agent-toolkit-data-explorer-dabstep-1st-place)). Expect the single-table, single-turn slice of the benchmark to be a near tie, and expect BOW's native chat to be slower than a coding agent on those questions. The margin, if it exists, will be on multi-table business-logic questions, on pass^5, on cost, on multi-turn state, and on governance.

**The field's own conclusion is that model choice usually matters more than harness.** The Terminal-Bench authors state that "model selection is usually more important than agent scaffold" ([Terminal-Bench paper](https://arxiv.org/html/2601.11868)); the same-model harness spread is largest for small models (GPT-5.4 mini +29 points) and smallest at the top (GPT-5.5 within 2.5 points across three harnesses) ([tbench.ai](https://www.tbench.ai/news/terminal-bench-2-1); [Snorkel](https://snorkel.ai/leaderboard/terminal-bench-2-0/)); and scaffolds can hurt, as when GPT-5-Nano fell from 44.0% to 14.0% under a richer scaffold ([Live-SWE-agent](https://arxiv.org/html/2511.13646v3)). Harness deltas are also fragile to task quality: Terminus 2 beat Claude Code on Opus 4.6 in Terminal-Bench 2.0 and lost to it in 2.1 after 28 tasks were fixed ([tbench.ai](https://www.tbench.ai/news/terminal-bench-2-1)). The defensible framing is that the harness is the lever a platform controls and is worth roughly a model generation for mid-tier models, reported per model tier, not as a blanket claim.

**BOW's own gold labels will contain errors.** If audits find 52.8% to 62.8% error rates in benchmarks built by expert teams ([arXiv 2601.08778](https://arxiv.org/html/2601.08778v3)), a 200-question set authored in a few weeks will have mistakes too. Double annotation, a published disagreement rate, versioned corrections, and an invitation to file label disputes are the only defense; a benchmark-as-product play lives or dies on this, and the CIDR paper raised the bar.

**The existing in-repo numbers are not publishable.** The Spider 1.0 run (35.6%, 42 null predictions, 9 errors) is unfinished on a frozen benchmark. The artifact-iteration improvement (0.801 to 0.952) is n=1 per cell on one model. The overfitting benchmark has six cases. The query-acceleration measurements are real but cover two warehouses and depend on repeat rates. Each is a seed, none is a result.

**No public number exists yet for a self-improving text-to-SQL loop, which means BOW's will be scrutinized as a first.** GEPA and ACE provide the academic basis ([GEPA](https://arxiv.org/pdf/2507.19457); [ACE](https://arxiv.org/html/2510.04618)) and ISE's +19.3 points from stored corrections is the closest applied datapoint ([Microsoft ISE](https://devblogs.microsoft.com/ise/llm-sql-query-generation/)), but the learning curve must be measured on a held-out slice the loop never sees, or the result will be read as test-set memorization, which is precisely the failure the overfit benchmark exists to catch.

**Small samples cannot support small claims.** At 150–200 questions a 3-point lead is noise; the SWE-bench audit separated none of 29 adjacent top-thirty pairs ([arXiv 2609.17394](https://arxiv.org/abs/2609.17394)). If BOW's native chat beats Claude Code plus BOW MCP by three points, the honest statement is a tie.

**Competitor products depend on setup effort, and "default settings" is attackable.** Basedash's 19.2% for Snowflake Cortex at defaults ([Basedash BI Bench](https://www.basedash.com/bi-bench)) is exactly the kind of result Snowflake can dismiss, and Databricks' own 13-question walkthrough shows Genie going from 0% to 100% as metadata and instructions are added ([Databricks](https://www.databricks.com/blog/how-build-production-ready-genie-spaces-and-build-trust-along-way)). Any competitor arm needs matched context-engineering effort (same descriptions, same metric definitions, same time budget) and both configurations reported, or it should not run.

**Cost claims expire at every model release.** Prices are promotional (GPT-5.6 Sol through November 21, 2026; Gemini 3.6–3.8 Flash doubling January 1, 2027) ([OpenAI pricing](https://developers.openai.com/api/docs/pricing); [Gemini pricing](https://ai.google.dev/gemini-api/docs/pricing)), tokenizers change, and Anthropic itself advises to "recheck at every model release" ([Anthropic](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)). The leaderboard must be a living page with dated snapshots, not a one-time chart.

## Conclusion

The strategic insight is that the eval *is* the launch, and its value does not depend on BOW winning every row. The analytics category has roughly ten vendor-blog "comparisons" and not one reproducible cross-vendor number; the incumbents converged on an opaque template (private questions, anonymized "coding agent" baselines at 20–30%, no intervals, no cost) precisely because none of them wants a comparable figure in the open. An open-source entrant that publishes the question set, the gold-annotation process, a neutral reference scaffold, per-trial transcripts, pass^k and cost per correct answer becomes the citation of record for the whole category, and every later vendor post will be measured against it. That position is worth more than a leaderboard rank, and it is available because the incumbents' own documentation concedes the gaps (no multi-turn, no consistency, no cost) that BOW's existing in-repo instruments already partly measure.

The second insight is that BOW's product thesis and its eval methodology are the same argument. A platform whose pitch is "the harness is the product and the model is a dial" should be the first to publish a matrix where the model is literally a dial: one question set, many models, many effort levels, a cheap open-weight row sitting on the Pareto frontier next to a frontier model run raw. If that chart holds up under five trials and Wilson intervals, it demonstrates the thesis more convincingly than any accuracy headline; if it does not, BOW learns that before its customers do, which is the point of having evals in the first place.
