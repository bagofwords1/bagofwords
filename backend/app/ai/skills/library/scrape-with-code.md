This org has **Browser in code** on: code generated by `create_data` can be
given a headless Playwright-backed `browser` (and, when **Web fetch in code**
is on, an `http` client). Pages read by the code never pass through you —
only counts and a preview come back. A 40-page catalog done this way costs
one tool call; done with your own browser tools it costs 40+ calls and fills
your context with page text.

## 1. Is this a code job?

| Situation | Do |
|---|---|
| 1–3 pages, a quick answer | your own browser tools / `web_fetch` (browse-web skill) |
| More than ~3 pages or ~20 rows, pagination, "load more", every item of a list | **one `create_data` call** — this skill |
| Plain HTML, no JavaScript needed | still `create_data`, but tell it to use `http` (much faster than the browser) when `http` is offered |

`browser` is only offered when the conversation's agent has a **browser
connection**: the code may only open URLs in that connection's allowlist.
If `create_data` reports no `browser` helper, fall back to `http` for static
pages, or tell the user a browser connection is needed.

## 2. Look once, then delegate

Open the start page **once** with `browser_navigate` (and a single
`browser_snapshot` or `browser_extract` if needed) to learn:

- the selector of one repeated item (`.product-card`, `table tr`, `li.result`),
- the selectors of the fields inside it (title, price, link, date, tags),
- how more results appear: a "Next" link/button, a "Load more" button,
  infinite scroll, or a `?page=N` URL,
- when it ends (Next disappears/disabled, Load more stops adding items, an
  empty page).

Never loop `browser_navigate` / `browser_extract` / `browser_act` over pages
yourself, and never write scraped rows by hand into a `submit_<list>` tool.

## 3. Write the `create_data` prompt

No `tables_by_source` is needed. The coder only knows what you write, so the
`interpreted_prompt` must state:

1. **Start URL** (and any filter or tab to set first).
2. **Item + fields**: "one row per `.product-card`; fields name=`.title`,
   price=`.price`, url=`a@href`, tags=list of `.tag` texts" — this maps
   directly to `browser.query_all('.product-card', fields={...})`, one call
   per page.
3. **Pagination and stop rule**: "click `text=Next` until it is gone", "click
   'Load more' until the item count stops growing", "scroll until no new
   items", or "build `?page=1..N` URLs and fetch them with `http.batch_get`".
   Tell it to check optional controls with `query_all` before clicking (a
   missing element raises after a timeout) and to `wait_for` the item
   selector after each click.
4. **Limit**: a page/row cap if the user gave one. The org also caps page
   loads per run (Max browser pages per code run); a crawl bigger than that
   must be split by section or date range across several calls.
5. **Output**: column names and types, cleaning (strip currency, parse
   dates), dedupe key (usually the item URL), and the source URL as a column
   so every row is traceable.
6. **Agent List** (only when the user asked to fill one): the list slug, and
   "submit each page's rows with `lists.submit` as you go".

## 4. Rules the code runs under

- **Read-only by default.** Unless "Allow form submissions from code" is on,
  POST/PUT/PATCH/DELETE are blocked: the code can click, type into search
  boxes and filters, but cannot log in, submit forms, or post. Don't plan a
  task that needs it; tell the user what setting it would take.
- **Allowlist.** Only URLs in the browser connection's allowlist load;
  everything else is refused.
- **No re-scraping on refresh.** `browser` (and `lists`) exist only in your
  own `create_data` run. A rerun or a dashboard refresh of that step does not
  drive the browser again — the result is a snapshot of the site at scrape
  time. Say so when you put scraped data on a dashboard; if the user needs it
  to refresh and the pages are plain HTML, build the step on `http` instead,
  which works on reruns.

## 5. Check and report

Read `sandbox_activity` on the result: `browser_pages_loaded`,
`browser_requests_blocked`, `urls_fetched`, and list rows queued. Then:

- Compare the row count to what the site showed (e.g. "128 results"). A
  shortfall usually means the stop rule fired early or a selector missed —
  fix the prompt and run again rather than patching rows yourself.
- Spot-check 2–3 rows against the preview for empty or shifted fields.
- Tell the user: pages loaded, rows collected, anything blocked or skipped,
  and that the data is as of now.
